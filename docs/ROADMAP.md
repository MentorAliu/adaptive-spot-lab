# Implementation roadmap

## Scope and gates

Implement one reviewed milestone at a time. This is a complete target architecture, not permission to implement or activate everything at once. Do not reopen answered owner questions. Missing future settings do not block an honest foundation. Each gate requires actual evidence; a document, model assurance or mocked success cannot mark it passed.

M0–M4 retain the original financial foundation. M5–M8 replace the previous selector-only agent sequence. Existing implementations must reconcile actual progress under the pack-era [MIGRATION.md](archive/pack-2.0.0/MIGRATION.md) (archived 2026-10-20), not relabel old work as passing the new gates.

M9 is the owner's requested extension after M0–M8 completion, M8 acceptance and verified normal-local deployment. Since 2026-10-19 it is planned under M8's rules ([ExecPlan 0032](archive/plans/0032-m9-news-and-events-the-agents-trade-on.md)), approved on 2026-10-19 by the owner's go-ahead, which also accepted M8 ([DECISIONS](DECISIONS.md#2026-10-19--m8-accepted-m9-built-under-execplan-0032)). It does not alter an earlier milestone's policy or approvals.

M10 follows M9 acceptance and verified normal-local deployment, with a separate implementation instruction. It separates broader asset discovery/research from controlled additional-coin paper eligibility. Its future specification does not expand the current BTC/SOL operating scope or approve any new asset, source or policy.

## M0 — Docker, source verification and frontend foundation

Create or reconcile the monorepo, containerized bootstrap/build/test paths, TanStack Start app using the exact shadcn preset, actual official skill discovery, locked compatible dependencies, lint/types/tests, FastAPI and PostgreSQL/migration skeleton, owner-access design and honest status/empty UI. Establish request-scoped Query integration, same-origin/server-only boundaries and typed API generation. Preserve all supplied documentation.

Use [plans/0001-foundation.md](archive/plans/0001-foundation.md). Plan later agent/research process boundaries, but do not build their features, fund the account, start experiments, authenticate a runtime model, or contact a paid provider. Gate: actual clean Docker build/start and baseline checks, observed versions, verified skill discovery and unambiguous unimplemented status. Inability to run a check leaves its gate unpassed.

## M1 — Ledger, account, virtual funding and owner authorization

Implement exact-decimal journal, one-time 10,000 virtual-USDT initialization, reservations, projections, unitized NAV, confirmed top-ups, owner sessions, immutable approvals/audit records and funding UI. Approval infrastructure authenticates the owner; model-authored text is never approval.

Gate: arithmetic/property/concurrency/idempotency tests, deposits neutral to P&L/NAV, correct pending valuation, reconciliation and restart. No market-dependent fills yet. Risk/reference counters must not reset on deposit or restart.

## M2 — Public market data and charts

Implement symbol/status/filter validation, public REST/streams, finalized candles/warm-up, execution quotes/depth as required, point-in-time provenance, quality/gap recovery and retention. Add markets/health UI and Lightweight Charts using its official skill plus shadcn composition. Evidence schemas may be scaffolded; no unapproved external source is silently enabled.

Gate: provider availability/schema evidence, offline fixtures plus explicit public smoke checks, chart lifecycle/browser tests, stale/gap handling and no credentials or fabricated fallback. A working chart does not authorize trading.

## M3 — Deterministic paper broker and reference strategy

Implement order/fill transitions, cost model, independent risk gate, immutable position mandates, TREND_REFERENCE_V1, deterministic event ordering and isolated replay. Add orders/positions/risk UI. No live broker or hidden live switch. Unknown fees/execution assumptions stay unset until verified or approved as labeled scenarios.

Gate: quantity/filter/partial-fill/cost/stop tests, fencing/reservation/forced-kill reconciliation, no fictitious funds and clear modeled execution labels. Tests must show a gapped stop can exceed planned loss. No automatically started forward experiment.

## M4 — Evaluation and fixed-strategy forward pilot

Implement immutable run manifests, chronological evaluation, matched-flow baselines, flow-neutral returns/drawdown, uncertainty/cost reporting and owner start/pause/resume/flatten controls. Freeze the protocol before using its results. Obtain actual approval of denomination, risk profile, reference strategy and execution assumptions before a forward pilot.

Gate: benchmark/calculation correctness, point-in-time inputs, approval enforcement, local-downtime recovery and complete evidence. The fixed pilot can be negative or inconclusive. It is a comparison/control, not a prerequisite to proving profitability before building agent infrastructure.

## M5 — Subscription runtime, application tool loop and security boundaries

Implement recorded/Codex provider abstraction, explicit protected owner login, finite `AgentStep` action loop, typed dispatcher, role grants, durable jobs/results, deadlines/concurrency/budgets, revocation, effective native-tool restriction and secret redaction. Begin with read/assessment tools and positive/negative fixture workflows. Add agent run/tool/auth/quota UI. No API fallback.

Gate: actual capability probes demonstrate application tools work while native shell/file/browser/MCP/delegation routes are unavailable under the chosen profile. Verify token refresh, timeout/late-output behavior, provenance, role binding, idempotency and denial of unauthorized side effects. (Owner decision of 2026-10-03: M5 was closed on the live capability probes; token refresh is verified in isolation, and its live observation is a follow-up check, see [DECISIONS](DECISIONS.md#2026-10-03--m5-closed-on-the-capability-probes-live-token-refresh-becomes-a-follow-up-execplan-0020).) Owner-authorized provider smoke calls are distinct from offline tests. Recorded responses are test/replay inputs, never fresh forward decisions. M5 alone does not authorize agent-driven main trading.
