IMPLEMENTED on 2026-10-22 ([ExecPlan 0037 §4](../plans/0037-clear-values-in-local-time.md#4-design)), on the owner's ask of that day for values "formatted for best ux" and shown "on my local time". Display only: requests, forms and caches keep the API's exact decimal strings and UTC instants.

- **One format per kind of value** (`src/lib/display.ts`, with units in `src/execution/parts.tsx`), from the exact string through `Intl.NumberFormat`, never through a float: USDT amounts to the cent (small ones to two significant digits; gains and losses signed), prices to five significant digits with at least two decimals, coin quantities exact with their coin, NAV to four decimals, percentages from the exact fraction (differences in percentage points), counts grouped, large volumes short with the exact value on hover, sizes, delays and durations in their units. A value that is not a decimal string is shown as the API sent it.
- **Exact and aligned** where the digits are the point: the candle table and the top-ups, padded so the decimal points line up. Home's balances read to the cent with the exact figure on hover.
- **Times** in the viewer's time zone (the browser's own), "22 Oct, 13:58:04" with the year only outside the current one, as a `<time>` element (`DateTime`, `src/components/date-time.tsx`) whose hover text gives the zone's offset and the instant in UTC. The sidebar's footer, and the page's footer on phones, say which zone. No column header says "(UTC)"; a rule that runs on the UTC day says so and gives its moment on the viewer's clock.
- **Server rendering** (TanStack Start's Hydration Errors guide): the server writes the zone the `asl_time_zone` cookie names, UTC until the browser has set it; `TimeZoneProvider` hydrates with the server's zone, then the browser's own takes over and the cookie remembers it.
- **Charts**: the time axis and crosshair through `tickMarkFormatter` and `localization.timeFormatter` in the viewer's zone; the candle chart's price axis to the closes' price decimals.
- **Browser tests** run in UTC (`timezoneId` in `playwright.config.ts`); `e2e/local-time.spec.ts` runs in Budapest.

## Server-state ownership

TanStack Query owns fetched server data and mutation state; Router owns navigation and validated URL search state; RHF owns form state; React state owns transient local interaction. Financial authority stays in the backend.

All current and future user-selected filters on a view belong in validated Router search params. Changing one filter retains the others, so the selected view survives refresh, sharing and browser history. Keep only temporary interaction state in React state. Format display values and timestamps for readability without changing canonical decimal strings, provenance or UTC event identity.

Implement Start's current official Query SSR integration with a fresh QueryClient per router/server request and a stable client for browser navigation [TS-01](REFERENCES.md#ts-01). Do not construct a module-global server cache or independently dehydrate the same data twice. Keep server-only credentials and backend clients out of client bundles [TS-03](REFERENCES.md#ts-03).

Define shared query options and keys containing account/experiment identity, resource, symbol, timeframe, filters and version where they affect results. Router loader dependencies must match validated search inputs. Query freshness is a UI policy, not permission to trade on stale data. Record a rationale for freshness intervals rather than copying documentation sample numbers.

For Query-backed I/O, consume the `queryFn` context's `signal` and forward it through the supported transport, including Start server-function call options; document any downstream cancellation boundary that cannot receive it. M0 constructs `QueryClient` without `defaultOptions` and uses TanStack Query's built-in defaults. If a later feature needs app-wide overrides, configure them at `QueryClient` initialization rather than repeating them in shared `queryOptions`. Use `select` when an observer needs a derived slice or transformation while the cache should retain the canonical response; do not add an identity projection when callers use the complete payload. Check the installed TanStack versions and official Query/Start guidance when composing these APIs, including documented Suspense cancellation limits.

On an owner-confirmed mutation, reconcile with the authoritative response and invalidate the actual affected Query keys. Do not optimistically add funding, fills, approvals, or risk-state changes to financial totals. Idempotency prevents repeated clicks/retries from posting twice. Clear private caches and route auth context on sign-out; scope experiment changes so data never leaks from a shadow account into the main account.

## Transport and incremental updates

Use same-origin Start server functions/routes as the BFF to the private API. Authorize on the server; enforce origin/CSRF controls for mutations. Private account responses must not be publicly cached. Do not expose internal API addresses, service credentials or DB access to the browser.

Start with canonical snapshots and bounded polling; add one account-scoped event stream through the BFF when needed. Stream events carry monotonically ordered IDs or an explicit snapshot cursor. The browser detects gaps/reconnects, refetches a snapshot, and does not double-apply financial events. Clean up subscriptions when route/account changes. Do not open a Binance WebSocket for every component.

The dashboard reports last successful observation and last valuation separately from page render time. A cached value is never relabeled fresh merely because the UI rerendered.

## Forms

Use the official shadcn/RHF pattern compatible with the generated base and installed versions [UI-05](REFERENCES.md#ui-05). Use Zod through the compatible resolver; distinguish input/output types if transformations occur. Server-side Pydantic/domain validation remains authoritative.

For RHF forms, use `formState.isSubmitting` for the submission request, Zod/`FieldError` for field validation, and `setError("root.server", …)` for safe form-wide server failures. Clear stale server errors when an input changes. Keep post-review financial confirmation, unknown-outcome resolution and other independent account actions in their own state; a prepared top-up draft is not a posted contribution. Reset the top-up input only after the authoritative result is `POSTED`.

Financial amounts remain canonical decimal strings; do not round-trip through `Number`, `parseFloat`, or `valueAsNumber` before posting. Reject NaN/infinity, negative/zero top-ups, unsupported precision and malformed locale input. Show explicit validation rather than guessing whether a comma was a decimal or grouping separator.

Top-ups require a confirmation showing amount, `USDT (virtual)`, account identity and no-real-money notice. Use a stable idempotency key for retries of the same submission. Risk-profile/strategy approvals show immutable versions and their consequences. Do not make a model job completion equivalent to clicking Approve.

## Tables and chart composition

Use TanStack Table's headless API with shadcn Table and controls [UI-06](REFERENCES.md#ui-06). Define typed columns and stable row IDs. Financial sorting must use authoritative numeric/order keys, not lexicographic formatted strings. Paginate large histories on the server; filter/sort parameters are validated and bounded. Virtualization is optional after measurement, not a default dependency.

Lightweight Charts runs only in a client-safe boundary. Guard DOM access, create charts in the correct React lifecycle, clean up listeners/ResizeObserver/chart instances, and handle Strict Mode remounts. Test resizing, route transitions, empty/error states and the installed chart API. Do not assume old series-creation signatures [FE-02](REFERENCES.md#fe-02), [FE-04](REFERENCES.md#fe-04).

Use UTC in storage and event identity; a chart shows its times in the viewer's zone through its formatters (`chartTime` in `src/lib/chart-time.ts`), never by shifting the timestamps. Convert milliseconds/seconds explicitly to the chart's expected time representation. Keep chart points sorted/unique; handle provisional candle updates separately from final bars. Convert decimal strings to finite JavaScript numbers only at the visual rendering boundary; those numbers must never return as financial inputs. Preserve gaps and stale intervals instead of drawing them as confirmed executable prices. Show required TradingView attribution and license notices.

## Accessibility and honest presentation

Use preset semantic tokens; color must not be the only indicator of profit/loss, feed status, or order state. Support keyboard navigation, focus return, chart text/table alternatives, readable precision, reduced motion and responsive layouts. Use existing shadcn primitives for alerts, dialogs, loading and empty states.

Differentiate zero from unknown and provisional from final. Label synthetic tests. Since 2026-10-30 the pages carry no disclaimer: no PAPER badge, no "paper" or "virtual" wording, and no notice that fills are modeled or that a page changes nothing ([below](#no-disclaimers-on-the-pages--2026-10-30)). Equity growth caused by contributions must be visibly separated from profit. Show realized and unrealized P&L and fees without double-counting. If daily return cannot be validly computed, show unavailable with reason—not `0%`.

A profile's diff is grouped by what the changed paths bind (definitions, generation 2 budgets, generation 1 budgets, runtime identity). The workflow page marks tool results, completions, artifacts and a candidate review's target that rest on the holdout or a shadow; an artifact's mark comes from the workflow's own list and does not wait for the artifact's document.
- **System** adds the Research and Evidence sources rows; a field the API does not send reads "not reported by this API release".
- **Navigation** gains Research and Evidence after Experiments (eleven links, wrapping at 390 px).

Rules, each with a unit or browser test ([TESTING](../TESTING.md#m6-b8-owner-pages-and-same-origin-functions-execplan-0023)):
- **States.** Every read goes through `ReadState`: loading; error with nothing shown; a named pending state; not found; and loaded. Each list has its own empty state.
  - A refresh that fails after a successful read keeps the earlier values, marks them stale and shows when they were read. They are never relabeled as current, and every owner action drawn from them is disabled until a read succeeds.
  - A read that has failed and not succeeded since stays an error while it is tried again; it does not flip to the loading placeholder between attempts.
  - The research status is one read. The overview's stores and staging gaps are drawn from it and state no second read state.
- **Pending is not an error.** Before migration 0008 the API answers `503 RESEARCH_SCHEMA_PENDING`, and an API released before B7 has no such route. Both are read results (`UNAVAILABLE` with a reason).
  - The notice says what the API answered ("research schema pending", "no such route in this API") and offers no control. Its title does not start like the error state's ("… unavailable").
  - It says the page reads again by itself, and every read that can return it is polled while it does: a list at its own interval, an evidence item, an experiment and a cell every 30 s.
  - The M4 section of Approvals, the M5 parts of Agents and the other System rows are unaffected.
- **Labels.** `MODELED REPLAY`, `SHADOW — deferred replay`, `HOLDOUT — locked`, `HYPOTHETICAL COST SCENARIO`, `HISTORICAL — the model may know later events`, `MODEL-AUTHORED — UNTRUSTED` and `SOURCE TEXT — UNTRUSTED`.
  - What the API marks with `holdout`, `shadow` or `locked_for` carries a text mark wherever it is shown: jobs, cells, shadows, reviews, promotions, a hypothesis's and a dataset's holdout figures, candidates and their events, ledger rows, tool results, completions and artifacts. A mark is never color alone.
  - A mark is made from fields of the row it stands on, never worked out from a kind, a purpose or a state. A row that carries `locked_for` only (a lifecycle event, a dataset, a promotion, a refused request with no job) gets the general mark `LOCKED — rests on the holdout or a shadow`. Every cell of a locked job is marked; its holdout cells carry the holdout mark.
  - The roles a value is locked for are shown where the API returns them. A tool result and an artifact carry `holdout` and `shadow` only, so their mark names no roles.
- **Recorded values, not defaults.** A value the API did not record reads "Not recorded" or "Not stated", never a word that could be a value ("Unset", "not final", "No holdout partition"). A count is named for what the API counts: `jobs` is "Screenings and full tests".
- **Untrusted text.** A publisher's title, extract and address, and a model's statement, declaration, proposal and rationale are React text nodes with their line breaks kept. Nothing is parsed: no HTML, no Markdown, and an address is never an anchor.
  - A title that would draw nothing (empty, white space, invisible characters) is not used as link text: the link is named by the item's ID and the page says the publisher supplied no visible title.
  - The application's own placeholder words never stand inside a container of publisher text.
- **Requests, not effects.** A refresh, a job cancel, a shadow stop and an approval decision are same-origin server functions behind the Host and CSRF middleware. Nothing is optimistic: the page then reads again and shows what the read model says.
  - The idempotency key is fixed before the call. The answer is "Recorded", "Refused: <code>" or "Outcome unknown", and an unknown outcome is resolved by its key.
  - A page has one owner request at a time, held by the page, so its outcome stays when the view changes. An unknown outcome and its key stay on the page until resolved: another dialog can be opened and read, but nothing can be confirmed before that.
  - After a confirmed request focus moves to the outcome, which also scrolls it into view; after Back or Escape it returns to the button that opened the dialog.
  - A request refused because the research schema is pending is "Refused", not "Outcome unknown": the API answers before it writes anything. This also holds for starting an M6 workflow.
- **Consequences first.** Refresh, cancel, stop, approve, reject and revoke open a confirmation dialog that states the consequence list the API returned for that action, as sentences made from its codes. Where the API returns none the dialog says so.
  - The stop and cancel dialogs also state the two [owner decisions of 2026-10-06](../../DECISIONS.md#2026-10-06--two-b7-behaviors-kept-an-owner-cancel-lets-the-workflow-go-on-a-recorded-shadow-stop-takes-no-further-mark). The stop dialog says whether the candidate is still `SHADOW_RUNNING` (retired with the shadow) or has left that state (not retired by a stop).
  - An ended job states no cancel consequences. The outcome message follows the status the API returned.
  - The dialog scrolls inside the viewport at 390 px and keeps its own text while it closes.
- **Refresh.** Query keys follow `["research", resource, …, "M6"]`, with `null` for "no filter" and "first page".
  - The research status and a detail whose job is still open are read every 5 s; lists every 30 s.
  - An evidence revision, a stored result cell and an ended job that has its result are not polled. An ended job without a result is read every 30 s, because the bridge records a late result.
  - Every mutation invalidates the research, agents and system keys; so do the Agents page's own controls.
- **URL state.** View, filters, cursors and the selected cell are validated search parameters; a value outside its closed list or exact pattern is dropped. Opening a cell or changing a view does not scroll the page back to its top.
- **Keyboard and names.** Each repeated action button names its target ("Stop shadow 0f01d3fe", "Reject promotion request …", "Approve source version …"). A disabled button is tied to the sentence that says why (`aria-describedby`). A stored text or extract that scrolls is a named region reachable with Tab. A card's heading always has words; it is never badges alone. The shared table primitive's scroll container is not yet such a region (open point in the plan's section 19).
- **The browser holds no secret.** The service key is read by the server functions only. Inputs are closed lists, UUIDs, source IDs and cursors in their exact patterns; a refresh takes a source ID and nothing else. No function takes a URL, a host, a tool name, a declaration or free text. An ID typed in upper case is read in the API's lower-case spelling.
