# Security and trust boundaries

## Threat model

Protect the owner's local machine, Codex account credentials, private research history and financial simulation integrity from prompt injection, malicious external text, untrusted dependencies, browser requests, stale/concurrent workers and accidental misconfiguration. The first release has no live exchange access, reducing but not eliminating risk.

Repository instruction files guide developers; runtime validation/permissions enforce behavior. A prompt saying “never trade badly” is not a security control.

## Local owner access

Bind the UI to loopback and do not expose it to the LAN/internet. Implement a single-owner session/bootstrap flow before financial/control mutations are available. Use a maintained authentication/cryptographic primitive with current official guidance, not home-made password hashing. No public signup, default shared password or hardcoded session secret.

**Since [ExecPlan 0042](../plans/0042-no-owner-sign-in.md) there is no sign-in** (the owner's decision of 2026-10-25, [DECISIONS](../../DECISIONS.md#2026-10-25--no-owner-sign-in-and-no-setup-execplan-0042)): the owner uses the app alone on the PC. The owner boundary is the PC: the web is published on `127.0.0.1:3000` only, refuses a `Host` outside its allowlist (`421`, against DNS rebinding) and a cross-site mutation (Start's CSRF and Origin checks), and is the only holder of the service key the private API requires on every route. Whoever can use a browser or a program on the PC acts as the owner, as anyone who could read the setup key file could before; the app is paper only. The passphrase, the sessions, their tables and the setup key secret are gone; the key file left on the PC is read by nothing. The rest of this section and the M1 table below record the sign-in as it was.

Keep the session in an HttpOnly cookie with restrictive SameSite/path settings; set Secure when using HTTPS and document local HTTP behavior rather than claiming HTTPS exists. Enforce server authorization, CSRF protection, allowed Host/Origin and tight CORS. Apply rate/size limits to login and mutation inputs. Do not put admin tokens in URLs or client bundles.

The private API checks service identity and relevant owner authorization/capability. A network location or guessed account ID is not permission to top up, approve strategies or resume a paused run. No generic LLM tool exposes these controls.

## Dependency and container controls

Review upstream skill/package changes before installation into the coding environment; a skill can execute tooling and deserves dependency-level scrutiny. Record official sources and resolved versions. Do not let runtime jobs install packages or auto-enable plugins to satisfy an injected instruction.

No auth in images/build args/fixtures. Use `.dockerignore`/`.gitignore` to exclude local secrets, auth caches, build outputs, test artifacts with sensitive content and data directories as appropriate. Inspect final image layers and mounts. Pin verified versions/digests when actually known; no fictional audit or digest values.

Do not add a Docker socket or use `--privileged` to make CLI sandboxing convenient. An unsupported sandbox/tool profile is a blocker, not a reason to launch with unrestricted access.

M6 splits the bridge from the candidate runner. The runner joins the research cluster's internal network only and gets research-cluster credentials only; the bridge spans the two private networks, holds `asl_research`, and has no engine credential or Internet route. `asl_source` has source/evidence grants only. Neither identity nor `asl_agent` gains a grant on an M1–M4 table; reads use migration-owned bounded views without pilot evidence pins. Configuration, grant and reachability tests must establish these boundaries. B3 and B4 implement and test the runner and bridge parts in isolated fixture stacks ("M6 B3 research boundary" and "M6 B4 bridge boundary" below); the source fetcher is B5.

## Audit and privacy

Audit approvals, flows, risk changes, pauses, data gaps, model proposals/rejections and execution authority changes with stable correlation IDs. Logs are structured and redact credentials, session cookies and provider tokens. Store concise evidence-linked explanations rather than hidden chain-of-thought transcripts. Account/job data must not be publicly cached.

Retain immutable experiment evidence subject to explicit storage/retention policy. Export reports without auth caches or private infrastructure secrets. Restores/corrections are recorded. A local-only deployment is not a backup strategy.

## Required abuse tests

Try malicious evidence requesting shell/filesystem/network access, fake source IDs, altered risk limits, forged approval, oversized JSON, duplicate funding, stale jobs, client-side balance changes, cross-origin mutations, path traversal/SSRF, concurrent execution and auth/log leakage. Expected outcome is rejection with safe audit evidence and no financial/credential side effect.

## Application-tool and research trust boundaries

Server state assigns role, account, mode, tool catalog, permission epoch, data cutoff and budgets. Model arguments may echo IDs for matching but cannot mint capabilities. Authenticate internal service calls and authorize every handler. Validate current permission again where an order/reservation commits; a cached result or evaluator agreement cannot override revocation.

Treat free-form text inside schemas as untrusted too. JSON structure reduces ambiguous routing but does not eliminate prompt injection [AI-12](REFERENCES.md#ai-12). Use source IDs, typed fields, bounded context and independent financial checks. The autonomy policy is this project's design; vendor safety guidance does not certify unattended trading or waive approvals for third-party MCP services.

External evidence stays in a constrained ingestion adapter. Validate approved hosts, resolved addresses and redirects, block private/link-local/metadata destinations and avoid attacker-controlled raw URL tools [SEC-01](REFERENCES.md#sec-01). Respect source rights, limits and retention. Disable active HTML/remote embeds in the UI; treat downloaded content and model-written links as untrusted.

Research accepts only registered bounded declarations. No arbitrary code execution, filesystem path arguments, raw SQL, dynamic imports, runtime package installation or LLM-generated scripts. Keep research data/DB credentials apart from main financial authority and Codex auth. Protect locked evaluation partitions from tuning roles and keep all attempts in the trial ledger.

Review artifacts bind their immutable target hash. The evaluator role cannot approve itself for main execution; peer agreement is not authorization. Grants must not be passed through untrusted messages, reassigned to a sibling role or amplified by tool chaining. Add privilege-escalation and cross-role confusion tests to every new tool.

Audit revocation, canceled children, raced/unknown commits, repeated requests, blocked source fetches, budget exhaustion and all proposal-to-order outcomes. Redact provider credentials and raw secret-bearing process output; do not store hidden chain-of-thought. Retain evidence-linked decision summaries and actual tool operation records.

### M3 execution boundary and scoped review

- **Roles.** `asl_execution` (NOLOGIN until M4) has SELECT on market and ledger tables, INSERT on M3 tables, fill-sourced journals, audit, outbox and evidence pins, and column-scoped UPDATE on the lease, projections, order status/reservation terms, positions and obligations. It has no access to `owner`/`owner_sessions` and cannot change units, contributions or initialization. `asl_api` gains SELECT on M3 tables and loses reservation INSERT/UPDATE and `fencing_epoch` UPDATE. The market role is denied every M3 table.
- **Triggers instead of RLS** (RLS default-deny would hide rows from reconciliation and the deferred balance trigger): journal source by role; postings only in their header's transaction; `account_state` guard (latches never clear, until M8's migration `0011` lets `asl_execution` alone clear both flags together after a passing reconciliation, as [RUNTIME_AGENTS](../RUNTIME_AGENTS.md#m8-runtime-in-force-records-the-model-table-and-pauses-that-end-execplan-0031) describes; high-water never falls, the fencing epoch never decreases); order transition table with immutable identity/decision fields and one-time reservation terms; immutable closed positions and completed obligations; append-only definitions, evaluations, decisions, mandates, events, fills, valuations, references, latches and breaches; non-main modes refused outside `asl_m1_` databases; fixture definitions refused outside `asl_m1_` databases.
- **Fencing.** A single 10 s execution lease (2 s renewal on a separate connection, `UNIQUE(id, owner_id, epoch)`) raises `account_state.fencing_epoch` on acquisition. Every step locks lease (`FOR KEY SHARE`) → account (`FOR UPDATE`) → rows, and rechecks authority immediately before COMMIT; the worker stops issuing work once its last successful renewal is older than 7 s. The execution identity has 2 s statement, 1 s lock and 3 s idle-in-transaction timeouts.
- **Process.** `execution-worker` runs the engine runtime image on the private network only (no egress), read-only root, tmpfs `/tmp`, 1 CPU / 512 MiB / 128 PIDs, only the `execution_db_password` secret and no published port; it is built but not started on the owner installation.
- **API.** Six read-only routes require both identities, strict bounded parameters and no-store responses; no mutation route exists (verified by a 405 test). Relevant ASVS 5.0.0 areas: V1.2.4/V2.2.1 (typed bounded input, parameterized SQL), V3.5.1/V7.2 (existing authenticated BFF/session), V8.2 (function-level authorization: owner-only reads, role-scoped database grants), V14.3 (private no-store responses). This is a scoped review, not a penetration test or full ASVS claim.

This scoped review covers the M5 surface only. Controls are listed as designed; [ExecPlan 0020](../plans/0020-m5-agent-runtime.md) §15 records which are verified and by what evidence. The OWASP ASVS 5.0.0 mapping is in [§17](../plans/0020-m5-agent-runtime.md#17-completion-evidence): chapter names were checked against the `v5.0.0` tag on 2026-10-01, and the mapping is at chapter level. - **Codex credentials.**

  - `codex_home` is never backed up or restored; recovery is a fresh login.

  - allows only hostnames on port 443 that are pinned in the approved profile;

### M6 B5 source and evidence boundary (ExecPlan 0023)

IMPLEMENTED; the isolated evidence is in [ExecPlan 0023 §18](../plans/0023-m6-research-investigations.md#18-completion-evidence). This is a scoped review of the B5 surface, not a penetration test or a full ASVS claim. The real publisher path is NOT RUN.

- **One outbound path, built from the registry.** `source-fetcher` is the only process that fetches a source. A request is the registered constant path plus that version's typed integer filters, on the registered host. No function accepts a URL, a host or a path, so neither a model, a browser nor source text can name a destination (invariant 8).
- **Destination checks** ([SEC-01](REFERENCES.md#sec-01), the M2 transport technique):
  - The registry refuses a host that is an IP literal, an integer, octal, hexadecimal or short dotted form, a single label, or a special-use name. A real source may not use `.test`; a fixture must.
  - The fetcher resolves the registered host itself. Every answer must be a public unicast address, including what an IPv4-mapped, 6to4, Teredo or NAT64 form embeds. Loopback, private, shared, link-local, metadata, host-gateway, multicast, documentation and unspecified addresses refuse the whole set, also when mixed with a public one.
  - The socket connects to the checked address. TLS (SNI and certificate name) and the `Host` header keep the registered name, so a certificate for another name is refused.
  - No proxy from the environment, no redirect (the target is never read, resolved or stored), no cookie, no credential.
- **Answer checks.** The registered media type, no content coding, the registered byte limit by declared and by actual size, and one deadline that covers DNS, connection and body. Reading stops at the limit.
- **Budget.** Each version has its own hourly budget, at most half of the publisher's declared allowance for the address. A stated reset is honored for every source of the host and on every kind of failure, not only on a limit; a limit without a readable reset waits the registered default; a stated reset more than a day away is capped and recorded as capped. The header names of policy `GITHUB_REST_V1` follow the B0 record of the publisher's documentation and have not been observed on a real answer.
- **A hostile answer cannot stall a source.** A publisher time is a time only in the exact RFC 3339 form; any other text is sanitized before it is stored. An answer the database still refuses is recorded as one `STORE_FAILED` fetch with no item, and the back-off applies; the request is not left running to be repeated at every poll.
- **Untrusted text.** An item is bounded plain text with markup, scripts and invisible characters removed, stored with the label `UNTRUSTED_SOURCE_TEXT`. Fetch records, request outcomes and triggers hold identifiers, counts and hashes, never source text. A search query is bound as a parameter and parsed as plain terms.
- **Identity.** `asl_source` (NOLOGIN until the owner's M6-B step) reads the registry and approvals, inserts requests, fetches, items, triggers and completions, and updates only a request's state columns. It has no grant on any M1–M4 table, on `agent_read` or `research_read`, and none to insert an approval, a definition, a workflow or a tool call. It may execute the fixed read `research_hold_permission_epoch()`. A database guard binds each request's actor to the connecting identity.
- **Process.** The Compose block runs the engine image as UID 10001 with a read-only root, `noexec` tmpfs, all capabilities dropped, `no-new-privileges`, 0.5 CPU, 256 MiB and 64 PIDs, on `private` and `source_egress` only, with one secret and no published port, volume or Docker socket. It defaults to disabled and then opens no database connection.
- **Test seams.** The resolver, dial, trust and clock overrides are constructor arguments that only tests pass, and they are refused unless `ASL_TEST_ISOLATED=1`. The deployed entry point passes none. The mock source and its throwaway certificate live in the test tree and exist in no runtime image.
- **Chapter-level ASVS 5.0.0 mapping** (names as recorded in [INTEGRATION_EVIDENCE](INTEGRATION_EVIDENCE.md#owasp-asvs-500-chapter-names-b7-2026-10-01); no requirement ID is cited): V1 Encoding and Sanitization (the extract), V2 Validation and Business Logic (definitions, filters, budgets), V8 Authorization (approval state and grants), V12 Secure Communication (name-checked TLS to a checked address), V13 Configuration (container hardening), V15 Secure Coding and Architecture (the single outbound path) and V16 Security Logging and Error Handling (immutable outcome records without source text).
- **Decision and publication are serialized.** The approval guard takes the publication lock for a source-version decision, so a revocation waits for a result being recorded, and a result recorded later sees the revocation. Search and open join the registry's usable set, so an approved version the code no longer accepts returns nothing.
- **Review.** An independent read-only review of the B5 modules found eight defects; each was fixed and has a test ([ExecPlan 0023 §16](../plans/0023-m6-research-investigations.md#16-progress)).
- **Open.** The tools, dispatcher and workflows that hand this text to a role were B6 ([below](#m6-b6-dispatcher-and-workflow-boundary-execplan-0023)); the owner routes are B7; the secret scan is B9. A revocation route must raise the permission epoch in the transaction that records it, which cancels queued requests.

### M6 B6 dispatcher and workflow boundary (ExecPlan 0023)

- **Identity comes from stored rows.** The role, template, generation, grants, cutoff and scope of a workflow are read from its row and from the definitions hashed into its capability grant. A revocation during a model step blocks every later effect of that step.

Neither is truncated into a different document, and neither can stall the worker. A result that the next prompt could not show is refused the same way. A tool handler runs in a savepoint: its unexpected failure is rolled back and recorded as `TOOL_FAILED`.

### M6 B7 owner API boundary (ExecPlan 0023)

IMPLEMENTED; the isolated evidence is in [ExecPlan 0023 §18](../plans/0023-m6-research-investigations.md#18-completion-evidence). This is a scoped review of the B7 surface, not a penetration test or a full ASVS claim. Every test used a synthetic owner, fixture data, a scripted model on the recorded provider and the loopback mock source.

- **Who can call a route.** The M6 routes are private-API routes with the M4 and M5 controls: the service key and an owner session together, a `Host` on the private allowlist, strict bodies and queries, the 8 KiB cap and `no-store`. A request with a valid session and no service key, which is all a browser could send, is refused. **No browser path exists yet:** the same-origin BFF functions, with their Origin and CSRF checks, arrive with the pages in B8, so B7 has no CSRF surface to test and claims none.
- **What a route accepts.** A source ID, a job, shadow, candidate or evidence UUID, a template name from a closed list, symbols from a closed list, bounded integers, an exact hash, an action from a closed list, an idempotency key. No route accepts a tool name, a URL, a host, a path, a role, a candidate declaration or free text. A test sends each of these and counts the affected tables afterwards.
- **What a route can change.** The API identity holds exactly what migration 0008 gave it: SELECT on the research, source and evidence relations, INSERT on refresh requests, and UPDATE of `version` and the one request column of a job and of a shadow. Everything else is another identity's: the fetcher moves a refresh request and writes fetches and items, the research identity moves jobs and shadows, the agent worker moves a promotion and records a candidate transition. Tests attempt those writes as the API identity and expect the database to refuse each.
- **Requests, not effects.** A refresh, a cancel and a stop answer with the recorded request. A cancel or a stop is one immutable value on its row; database guards refuse a second value, a cleared value and any other column. They only remove work, so a stale version does not block them.
- **Exact-hash approvals.** An envelope or source decision names the stored definition's ID and exact hash. A stale hash, another kind's ID, an envelope the code does not run and a source version the registry holds invalid are refused before anything is written. A target ID in another spelling than the stored row's is refused, because a state is looked up by that spelling. This now also holds for a runtime profile: INFERRED from the M5 code, an approval sent with another spelling of a profile's UUID was recorded and authorized nothing.
- **Revocation.** Revoking the envelope or a source version raises the permission epoch in the transaction that records the decision, after the publication lock for a source. The epoch is one number, so every queued job and refresh is canceled and a late result is history only, whichever was revoked (invariant 10). An approval or a rejection moves no epoch.
- **Promotions** (invariant 7, R15). The only action a promotion takes is `REJECT`, by the API's check and by the database guard. The rejection is the owner's record; the agent worker applies it as SYSTEM, once, to the promotion and its candidate. No route, role, identity or statement approves a promotion, and `MAIN_APPROVED` stays unreachable.
- **Idempotency across stores.** One advisory lock serializes every owner mutation of M5 and M6, and a key is looked up in all of them before anything is written, so a key used for one kind of request cannot be replayed as another. A refresh equal to one already requested in the same refresh interval is refused, because the row that answers it would not carry the owner's key. While another transaction holds the lock, every mutation answers `503 TRY_AGAIN` before it has read anything, also for a target that does not exist.
- **What the read models show.** The owner is not a tuning role and reads holdout and shadow results (section 5.5 of the plan). What rests on them carries a server-computed mark wherever it is shown, in a detail and in a summary: jobs, cells, shadows, reviews, promotions, a hypothesis's and a dataset's holdout figures, a candidate and its events once a full test exists, a ledger row that asked for a full test, and generation-2 tool results, completions and artifacts. Anything but an explicit false, and a missing mark, is shown as restricted. A generation-1 (M5) result has no such bounds and is shown with none, not as locked. A candidate review's bound target is shown as references; its statement and its holdout-derived figures are not part of a workflow summary. Nothing the owner reads flows back to a tuning role: an owner start carries symbols or a candidate ID only. No read model returns a credential, a session token, a prompt, model reasoning or provider stderr; prompts and outputs appear as hashes. What is stored with an owner request (session, request hash, correlation ID) is not part of any read model.
- **Untrusted text.** A publisher's title and extract and a model-authored statement, proposal or rationale are returned as JSON strings with their labels. The API interprets none of it; a test stores a hostile document and checks that it added no approval, workflow, promotion or request.
- **Bounded responses.** Every list has a limit of at most 100 and a cursor whose pattern is checked before any query; a cursor is a position, never a column or SQL. A result's evaluation documents are read one cell at a time.
- **Rollout.** Before migration 0008 every M6 route answers `503 RESEARCH_SCHEMA_PENDING` and `SystemStatus` reports `unconfigured`; the M5 routes do not depend on the M6 tables.
- **Chapter-level ASVS 5.0.0 mapping** (names as recorded in [INTEGRATION_EVIDENCE](INTEGRATION_EVIDENCE.md#owasp-asvs-500-chapter-names-b7-2026-10-01); no requirement ID is cited): V2 Validation and Business Logic (strict bodies, closed lists, state rules), V4 API and Web Service (the route contract, generated schema, no-store), V7 Session Management (the owner session on every route), V8 Authorization (the dual identity, exact-hash approvals, the API identity's grants) and V16 Security Logging and Error Handling (stable codes, no SQL or secret in an error, request logs without bodies).
- **Independent review (2026-10-05).** Two read-only reviews read the B7 tree after the first full pass: one of the routes (authorization, session and CSRF handling, strict bodies, idempotency and locking), one of the read models and the harness. Neither found a path by which holdout or shadow data reaches a tuning role, a credential or a session value in a read model, or a route that writes beyond its grants. What they found was changed with a test for each (the tests are listed in [TESTING](../TESTING.md#m6-b7-owner-api-openapi-and-generated-types-execplan-0023)):
  - An owner's cancel of one job was recorded as a revocation and ended the waiting workflow as revoked. It is now recorded as `OWNER_CANCEL` and the workflow goes on.
  - An advance result that arrived after a recorded shadow stop, before the stop was applied, could become a mark and make the candidate `EVIDENCE_READY`. A recorded stop now takes no further mark.
  - The owner start route answered a lock timeout with an unhandled error instead of `503 TRY_AGAIN`. The new bodies accepted coerced integers, and the new mutations ignored a query string.
  - Marks were missing where holdout-derived facts are summarized, a candidate review's bound target put such figures and model-authored text into every workflow summary without a mark, and every M5 tool result was shown as locked.
  - `research` could read `idle` or `running` with no working bridge, and `sources` could read `unavailable` after a refresh that was refused before anything was sent.
  - A cursor beyond a sequence's range and a slow read ended as unhandled errors.
  - `Generate` and the web checks compared an image with a working tree that could have changed after Build.
- **Left as recorded risks** (plan §19), each rated low by the review:
  - INFERRED, not reproduced: a source revocation and an agent worker fixing a cutoff take the publication lock and the epoch in opposite orders. The API waits at most one second, answers `503 TRY_AGAIN`, records nothing, and the request can be sent again.
  - Another database identity that holds INSERT on jobs or shadows could insert a row that reads as owner-canceled or owner-stopped, or occupy an idempotency key. It could only remove work, no tool path sets those columns, and closing it needs a guard change in a migration, which B7 does not make.
  - The M4 and M5 request bodies keep their integer coercion, and a JSON body with a duplicate key is read as its last value, as before B7.
- **Open after B7, closed by B8.** The BFF functions with their Origin and CSRF checks, and the pages: see the B8 section below. The secret scan, `PerformanceApi` and `MixedVersion` are B9.

### M6 B8 owner pages and same-origin functions (ExecPlan 0023)

IMPLEMENTED; the isolated evidence is in [ExecPlan 0023 §18](../plans/0023-m6-research-investigations.md#b8--owner-pages-and-same-origin-functions). This is a scoped review of the B8 surface, not a penetration test, a full ASVS claim or an accessibility audit. Every test used a synthetic owner, fixture data, a scripted model on the recorded provider and the loopback mock source.

- **The only browser path.** The browser reaches an M6 route through a same-origin server function of `apps/web/src/research/research.functions.ts` (or the workflow start in `src/agents/`). Each runs behind the web's Host allowlist and, as a server function, behind Start's CSRF middleware. The private API still requires the service key and the owner session together; the browser holds only the session cookie (HttpOnly, SameSite=Strict) and never the key.
- **What the mutation functions refuse.** OBSERVED in `BrowserResearch` for each of the four mutation functions an M6 page uses (refresh, research request, decision, workflow start), on the request the page itself sent. The test driver sends that request again with its own headers and body and the browser's session cookie; these are forged requests from the driver, not requests a page on another origin made.
  - The unchanged request is accepted (`200`; the API answers an equal request with the same key by the recorded one). Each refusal below therefore follows from the one header that differs.
  - Another `Origin`: `403`. Cross-site fetch metadata: `403`.
  - Another port of the same host with `Sec-Fetch-Site: same-site`: `403`. This is the caller SameSite=Strict does not stop, since the cookie is sent to every origin of the same site.
  - Another `Host`: `421`.
  - A GET to the function's address with the body in the query: a `4xx` status; a mutation function does not run from a GET.
- **What a function accepts.** Strict Zod objects that are validated before the private API is called: a UUID, a source ID in its pattern, a closed list (view, state, kind, subject, purpose, template, action), a cursor in its exact pattern, a cell index from 0 to 63, an integer version, an idempotency key.
  - No function takes a URL, a host, a path, a tool name, a role, a declaration or free text. A refresh takes a source ID and a key and nothing else: no filter can be sent from the browser.
  - A promotion decision can only be validated as `REJECT`: `APPROVE` and `REVOKE` are not a shape the function accepts, and the API refuses them again.
  - A UUID is lower-cased before it is sent or compared, as the API spells it.
- **What reaches the browser.** A function returns the parsed read model or a result of three kinds: recorded, refused with the API's code, or unknown with the key that was sent.
  - Every response is parsed by a strict schema first. An object the API defines refuses an unknown field. About twenty fields are stored JSON values the API passes through (`resources`, `outcome`, `attribution`, `gate_evidence`, `document`, `evaluation`, staging gaps); their inner shape is not checked by the web, and they are drawn as text. No secret was found in what the current views put there.
  - A read that fails sends the browser the API's filtered code (`[A-Z_]+`) or a fixed sentence written in the web's own code. A response that is not its contract, and a body that is not JSON, name no private field, key or value.
  - No function returns the service key, the session token, a request hash, a correlation ID, a prompt or provider output. A detail read, and a recorded request, are refused when the row, the actor or the key returned is not the one that was asked for.
- **Requests, not effects.** A refresh, a cancel, a stop and a decision answer with the recorded request. The page then reads again and shows what the read model says: a canceled job stays `QUEUED` and a rejected promotion stays `PENDING` until another identity has applied the request, and the page says who applies it. Nothing is optimistic.
  - An unknown outcome and its key stay on the page until resolved, and nothing else can be confirmed before that: the key is never lost and a request is never repeated blind.
  - A request refused because the research schema is pending is a refusal, never an unknown outcome; this includes the start of an M6 workflow.
  - Values from a read that could not be refreshed are marked stale, and no owner action is offered on them.
- **Consequences before confirmation.** Refresh, cancel, stop, approve, reject and revoke open a dialog that names the exact target (hash, ID, the version the owner saw) and states the consequence list the API returned for that action. The envelope, a source version and a promotion carry `decision_consequences` and a source `refresh_consequences` for this (`app/agents/approvals.py`, code-owned codes that grant nothing); a job and a shadow already carried theirs. Where the API returns no list the dialog says so.
  - The first B8 lists understated a revocation: they named waiting generation-2 workflows only. A revocation fails every started workflow of either generation, cancels a model call in flight and cancels what the system had queued, and a job canceled this way is final. The lists now say so, and an engine test drives a revocation through the route and compares the outcome with the list.
- **A promotion can only be rejected,** now also in what is drawn: its card has one button, Reject, and states why (invariant 7, M6-OD5). The web schema refuses a promotion whose `approval` is anything but `NOT_AVAILABLE_IN_THIS_RELEASE`, a state other than `PENDING`, `REJECTED` or `WITHDRAWN`, and a recorded decision other than `REJECT`.
- **Untrusted text.** A publisher's title, extract, address and attribution and a model's statement, declaration, proposal, rationale and review are rendered as React text nodes. Nothing is parsed as HTML or Markdown, `dangerouslySetInnerHTML` is not used, and an address is shown in a `code` element and is never an anchor, so it cannot be followed by a click and sends no referrer.
  - Unit tests draw text with an `img` and `script` element, an anchor, Markdown emphasis and a link, a bare address and an instruction addressed to a model, in an evidence item, the evidence list, a hypothesis and a promotion, and assert that the page contains none of those elements and no link out of the application. The source parser stores a publisher's text already stripped of markup, so the browser phase can show this for model text only; for publisher text it shows that a bare address is not linked.
  - A title made only of white space or invisible characters is not used as link text.
  - An instruction in source or model text changes nothing: the pages take no action from text they display.
- **Holdout and shadow.** The owner is not a tuning role and reads these results. Whatever the API marks (`holdout`, `shadow`, `locked_for`) carries a text label wherever it is shown, including tool results, completions, artifacts and a candidate review's target on the workflow page. A mark is made from fields of the row and never from a kind or a state. Nothing the owner reads flows back to a tuning role through the pages: an owner start sends a template name, symbols, a bounded horizon or a registered candidate's ID.
- **URL state.** View, filters, cursors and the selected cell are parsed against closed lists and exact patterns before they reach a query; anything else is dropped. A cursor is a position and is never interpolated into anything but a query string built with `URLSearchParams`.
- **Before migration 0008,** and against an API released before B7, every M6 read is a named pending state with no control, an M6 mutation is refused, and the start dialog offers no M6 template. The notice says what the API answered and does not assert a cause. The M4 section of Approvals and the M5 parts of Agents and System keep working.
- **Not changed, and open.** The web sets no `X-Frame-Options` header and no `frame-ancestors` policy (older than B8): a page on another local origin could frame the application, including the new confirmation dialogs. The scheduler's promotion start is not gated on the envelope's approval, so a promotion workflow can still start after the envelope is revoked. Both are recorded in the plan's section 19 for the owner.
- **Chapter-level ASVS 5.0.0 mapping** (names as recorded in [INTEGRATION_EVIDENCE](INTEGRATION_EVIDENCE.md#owasp-asvs-500-chapter-names-b7-2026-10-01); no requirement ID is cited): V1 Encoding and Sanitization (untrusted text rendered as text), V2 Validation and Business Logic (strict inputs, closed lists, Reject-only promotions), V3 Web Frontend Security (same-origin functions, Host and CSRF checks, no link out of the application from untrusted text), V4 API and Web Service (strict response schemas, no-store), V7 Session Management (the owner session on every function) and V8 Authorization (exact-hash decisions with the version the owner saw).

A stopped run says and records what it left, how to return, and whether the pilot is as it was at the start. The rehearsal produces four stopped states (a migration that fails on the restored copy, a blocked migration, a stopped web, real research rows before a rollback) and the way out of each.
- **The rollback images cannot be replaced by a second run.** The `:pre-m6` tags are created once, before anything is built, and are never moved. A tag is created only from an image the caller names for it in `-ExpectedPreM6Images`, and an existing tag must point to the image named there; this holds for the names `migrate` and `agent-admin` too, which have no service container. A run that starts when M6 images already serve therefore cannot turn the rollback image into the release it rolls back from.
- **The way back works from a broken release.** `-Rollback` accepts any state of `api`, `web` and the agent worker and does not depend on `git` or on a new backup when no data changes. A service counts as replaced from the moment its recreation is asked for. When the guarded downgrade refuses, the agent worker the script stopped is started again by its container ID (a Compose start would resolve its dependencies), nothing has been replaced, and the script says that the way is forward.
- **The env file is read as Compose reads it.** The three scripts read a key with one reader (quotes, a comment after a space, `KEY: value`, the `export` prefix). A key that is assigned twice is refused by the deployment and the activation, because Compose takes the last assignment and another reader would take another; the deactivation refuses nothing Compose can read and reads the last one. Interpolation and escapes are refused rather than evaluated. Three more readings of Compose were found on 2026-10-07 and OBSERVED by rendering scratch files with Docker Compose 5.5.1 on this host. The reader as B9 first wrote it did not follow them: a key in another letter case is the key when the exact spelling is absent (so `asl_research_enabled=1` hands the research services their flag as 1, while that reader took the flag for unset and reported the installation as inert; the deployment starts none of those services, so nothing would have started and the report would have been false); a quoted value that does not end on its line goes on over the next lines, and no line inside it is an assignment; a carriage return without a line feed does not end a line. The deployment and the activation now refuse a key in another letter case, a value over more than one line, a carriage return inside a line and a file that is not UTF-8; the deactivation reads each as Compose does. A flag is written to the resolved path every read uses, in every assignment and every spelling of it, with the other bytes of the file kept, by replacing the file in one step with the old file kept under another name until the step is done.
- **The pilot check reads more than identity.** Before and after: each pilot container's ID, image, start time, restart count and state, the lease epoch and that it is still held, the open experiment's state and version, the counts of segments, downtime events and execution incidents, and the image each pilot image name points to. A new execution incident stops the run and is named by its code, with one exception the owner decided on 2026-10-07 ([DECISIONS](../../DECISIONS.md#2026-10-07--m6-b9-what-stops-a-test-run-beside-the-pilot-the-owner-scripts-and-the-pilots-own-rows-the-schema-change-in-0008-and-the-market-workers-log)): `PROTECTION_UNAVAILABLE`, which the pilot writes on its own (22 rows in the first four hours of a sixteen-hour series with no test running), is printed and recorded by its code and count and stops nothing. A count of that code that fell, a code that is new and a total that no code accounts for still stop the run. The market worker's incidents during the run and the age of its newest publication are reported and not judged.
- **What stops a test run beside the pilot is a rule in code with its own cases.** `Get-PilotWatchVerdict`, `Get-MarketRestartCause` and `Get-ReportVerdict` in `tools/lib/Research.psm1` hold the owner's rule; `tools/m6-pilot-watch.ps1` applies it to read-only readings and can only stop the isolated run. The rehearsal runs 57 cases on synthetic readings, and the 161 readings of the series with no test running give no stop under it. The rule is the owner's to change: nothing in the harness relaxes it.
- **The watch reads the market worker's log, and only for a restart.** By the owner's decision of the evening of 2026-10-07 the watch may issue one read-only `docker logs` call with a time range on the normal market-worker container for each restart of that container a reading shows for the first time, outside HH:58–HH:07 UTC. It names the container by the id of the reading, keeps the text under `.cache/m6` (ignored by git, outside the run's directory) and reads from it only whether the slice holds exactly one `market_worker_fatal` event and a statement of `asl_prune_market_evidence` canceled by its statement timeout (the first function the database names after the cancellation, before any other traceback begins). A log that could not be read, or that shows anything else, stops the test run. The watch issues no other command of its own against the normal application, and the owner scripts read no log.
- **A lost research cluster cannot be put back by a role.** The bridge records the loss once and the catalog then refuses every new job, shadow advance and scheduled research on that store. Only the owner's command records the permission to retire the store: `python -m app.research.identity replace-store --main --store <name>` in the one-shot `research-admin` service, with the runner and the bridge stopped first and started again after (the command refuses a store that is not recorded as lost). The M6 script that wrapped it, `research-activate.ps1 -ReplaceLostStore`, was removed by ExecPlan 0034; on the owner's request a thread prepares these steps as one file the owner runs. The next version gets a name that was never used, so a store dropped once cannot come back under its name.
- **Nothing is sent into a cluster that came back empty.** A bridge pass relays before it stages, and stages nothing in the quiet window. The bridge therefore compares a store with the catalog before it sends a job to it, asks for a full test on it, advances a shadow on it or starts the daily work on it, not only when it stages: at its start, hourly, and whenever the store is empty or shows less than the bridge last saw. A bridge that starts later reads the recorded losses before its first relay. B9's first review found the earlier form of this check, which ran with staging only and kept the loss in memory; it is fixed and tested in the order of a real pass.
- **A healthy store is not declared lost.** B9's second review found that a second bridge process (an on-demand advance) reads the store before the catalog, so staging between the two reads looked like a store that is behind. A loss would then have been recorded for good, and the only way out retires the store. The store is now read once more before a loss is recorded; a test gives the second process the older reading.
- **Secrets.** The activation script creates only the research-only secret files that are missing and never reads or rewrites an existing one. A missing secret file would be created by Compose as an empty directory when a service that mounts it starts; the activation refuses such a path instead of using it, and the deactivation starts no service that mounts a secret.
- **A candidate strategy on the main database (R08).** On a main-shaped database with the M6 release a candidate is refused at each place that could take one: its installation as an execution definition, as configured and when the process claims replay isolation (the database's own name decides); the execution engine, under the main activation, as a replay on the live market view and as a replay kind in forward mode; and a forward or offline-test manifest that names it. `PilotCoexistence` requires each refusal by its own text.
- **Process death.** With real containers killed or restarted, no completion, result or staged row was recorded twice, and no result was recorded as valid for a job that never finished ([TESTING](../TESTING.md#m6-b9-rollout-saturation-performance-faults-and-final-acceptance-execplan-0023)).
- **Secret scan.** `SecretScan` searches for every fixture secret of the run in seven forms and for the M5 canary markers: in the whole plain dump (definitions and rows) and the roles of every database of every PostgreSQL volume, in every other volume, in every file of the runtime images and of the images the rehearsal's deployments built, in what `docker inspect` holds about every container and image name of the run, and, on the host and also as UTF-16, in every container log, evidence file and source file. A value is held in memory and in temporary pattern files under the run directory and in each database container's `/tmp`; they are removed, the removal inside a container is verified, and a file that stays fails the phase. For the duration of its search a plain dump of each database lies in a directory of that database's own data volume, written by the database's own container and searched by a second container that has no network and no capability, runs as the owner of the data directory and has the volume read-only. One dump lies there at a time; its removal is verified, also after the phase's deadline, and a dump that stays fails the phase. A dump is written only when twice the database's size and 2 GiB are free, because every volume of this host shares one disk with the real pilot's database. A value is never put on a command line, in a record or in a log; out of a container come counts, exit statuses and table names. A recursive search counts only when `grep` itself ended without error and listed a control file planted in the tree it searched, and a database search only when it counted the control file beside the dump exactly once, so a search that silently read nothing fails the phase; the control is not one of the searched values, so the scan cannot find its own control in the command log. A file or a container log that cannot be read fails the phase. `Report` requires the scan to have started after every other phase ended.
  - **What it cannot cover.** The owner's `.env`, secrets and runtime home are never read, so their values cannot be searched for. It does not search memory, a value in another encoding, UTF-16 inside databases, volumes and images, archives other than zip beyond their stored bytes, dead row versions and WAL, a database or an unnamed image that is gone at scan time, the build cache, git history or ignored files; the record's `not_covered` list names each. No real model or source was called, so it says nothing about text they could produce.
- **Chapter-level ASVS 5.0.0 mapping** (names as recorded in [INTEGRATION_EVIDENCE](INTEGRATION_EVIDENCE.md#owasp-asvs-500-chapter-names-b7-2026-10-01); no requirement ID is cited): V6 Authentication (service identities enabled only by an owner command, with client-side verifiers), V8 Authorization (the store replacement and the activation as owner-only steps; a candidate refused on the main database), V13 Configuration (inert defaults, flags and identities off after deployment, secret files), V14 Data Protection (the secret scan and its stated limits) and V16 Security Logging and Error Handling (the loss, the replacement and each fault recorded once, with its cause).

- **Frame policy (B8a, IMPLEMENTED and tested in Chromium on an isolated stack).** Every response of the web's server entry, pages, server functions, refusals, `404`s and errors, is sent with `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'`; an error that escapes Start becomes a framed plain `500` that names nothing. The browser shows no request as applied before the API records it; an unknown outcome is resolved by its key. A resume's answer must name the pause and key sent, and an approval's the key, target, hash and action sent (since B8b's review; M4's approval call did not check); anything else is an unknown outcome. Model-authored text on the risk page (an agent's pause reason and citations) is drawn as text and labeled untrusted.
- **Promotion approval (B6, IMPLEMENTED and tested offline only).** The owner's approval of a `PROMOTION_V2` request is the only way a research candidate becomes an entry basis. It is an `agent_approvals` row that only `asl_api` (or the migration identity) writes, bound to the request's exact hash, checked by the API and again by `0009`'s guard: the request's server-written scope and an installed policy, the candidate waiting for it, and its exit values inside the policy's sets. Only `asl_agent` applies it, and the candidate guard admits `MAIN_APPROVED` only with that row as the latest record. No model output sets the scope or the policy, and a request for consideration (`PROMOTION_V1`) can still only be rejected. A revocation raises the permission epoch when it is recorded; from that moment the submission guard refuses an entry naming the approval, before the worker has applied it. A research suspension raises no epoch: the agent worker withdraws an entry on the suspended candidate that is unanswered or unfilled at its next pass (`UNAPPROVED`, admitted by the withdrawal guard only once the candidate has left `MAIN_APPROVED`), so between the suspension and that pass the engine may still take it.

The engine parses it again with the M6 grammar and evaluates it with the M6 interpreter, both pure functions, and checks the ATR period, stop multiple, hold and symbol itself. A compromised agent identity could submit only a candidate the owner approved, for an entry the policy's sets and limits already admit.
- **The evaluation identity reads decision records through views (B6b, IMPLEMENTED and tested offline only).** `asl_evaluation` gains `USAGE` on the schema `evaluation_read` and `SELECT` on its eleven security-barrier views, owned by the migration identity, and no grant on any `decision_…` or `agent_…` table. A test checks that `asl_evaluation` alone holds each view's grant and is refused the tables (`tests/test_m7_evaluation.py`). The decision measures count a value that is not a code, and a tool name outside the catalog, as `UNRECOGNIZED`, and the tool-call view hides the name of a tool the dispatcher refused as unknown, so text a model chose never reaches a report (a gap B6b's review found and closed).
- **A replay or fixture engine keeps a policy binding without a run (B6b).** Only an engine whose activation is not `MAIN` does, and only while no run or live position of another strategy, the reference's included, is in its mode; it needs a disposable `asl_m1_` database (fixture) or an isolated replay database, as before. The main account's engine still gives way to the reference.

### M9 feed readers (update 1)

IMPLEMENTED; tested offline and on a scratch database with the loopback mock publisher. The real publishers are fetched only on the PC.

- **The same outbound path.** The four feeds are source versions like M6's: an exact HTTPS host, a constant path, no filter a model could set, no redirect, the 1 MiB cap and one 20 s deadline. Their hosts are `www.bls.gov`, `www.federalreserve.gov` and `www.ecb.europa.eu`. A model still cannot name a destination.
- **Answer checks.** Each reader has a closed list of media types (`application/rss+xml`, `application/xml`, `text/xml` for RSS; `text/calendar` for iCalendar). Any other is `WRONG_CONTENT_TYPE`, and the fetch record keeps the media type received, or `UNREADABLE`, never more of the header.
- **XML.** The RSS reader uses Expat and refuses the whole answer at any document type, entity or notation declaration, or an external entity reference, so no entity can expand and nothing outside the answer is read. It also refuses more than 32 levels or 50,000 elements, and anything but one RSS 2.0 channel.
- **iCalendar.** A small reader of the subset the BLS file uses. It refuses non-UTF-8 text, a malformed line, unbalanced or deeper than 8 components, and more than 200,000 lines. A start time that the file's own zone cannot fix (a skipped or repeated local hour, an unknown zone, a floating time) leaves the event out rather than guessing.
- **Text.** Titles and extracts go through the existing plain-text cleaning and keep the label `UNTRUSTED_SOURCE_TEXT`. An RSS item without an `https` link is left out, and a calendar event without one points to the calendar's own address. No link is ever followed.
- **Rate.** None of these publishers states a limit, so `HTTP_RETRY_AFTER_V1` waits only on a 429, or on a 503 with `Retry-After`, and the documents cap themselves at four requests an hour (the calendar one).

- **The archive.** Migration `0041` moves the futures, agents' and research tables into the schema `archive`, which no application identity can use (`REVOKE ALL ON SCHEMA archive FROM PUBLIC`); only the migration role reads it.

## The agents' provider keys (ExecPlan 0049)

[ExecPlan 0049 §5.2 and §9](../plans/0049-choose-the-agents-provider-and-see-usage.md#9-data-and-trust-boundaries). IMPLEMENTED and tested offline; NOT RUN on the owner's PC until the update is installed.
- **Where a key lives.** Only in the runner's `agent_keys` volume, mounted by the runner alone at `/agent-keys` (directory 0700, each secret file 0600), one file per provider, with a small state file (when it was saved, its last four characters, a random id, and for the Claude Code token when it runs out). Never in the database, a backup, a log, an answer, a prompt or an image layer; the threads never read or enter one. The isolated `agent-runner-test` mounts its own `agent_keys_test` instead. Inside the runner, the pinned Codex and Claude Code CLIs run as the runner's user, so the vendors' binaries themselves could read the store; no model has a file tool there (the native capability set is empty, a Claude CLI tool call other than its answer kills the job), so a model cannot. The `api` service joined `agent_control` to forward keys; the runner reaching the API is still refused by the service key on its routes.
- **How a key gets there.** The owner pastes it in Settings → Provider. The browser sends it once, in the credential form's same-origin request (Host and CSRF checks as every write); the web server forwards it to the engine, which checks its shape and forwards it to the runner's `PUT /v1/credentials/{provider}` without storing or logging it. A refusal carries a code, never the key.
- **Who can reach the credential routes.** The runner answers `/v1/credentials` only with the credentials key (`agent_credentials_key`, a Docker secret given to the API service, the runner and the isolated test client), apart from the job key the agent worker holds; the worker cannot save, read or remove a key. The runner returns only each key's state; `credential_hash` hashes the random id, so nothing about the secret can be learned from it.
- **Egress.** Each provider's traffic goes through its own gateway port, allowed only its vendor's hosts (`EGRESS_ALLOWLIST_V3`); the gateway still refuses IP literals and private ranges. An API request carries no `tools`, and a Claude CLI tool call other than its structured answer kills the job.
- **Spend.** A paid API runs only when the owner picks it and under the daily cap the owner sets; the vendor's own monthly limit is the backstop the app cannot see. A call that times out or is canceled (a reviewer or the coach giving way to a decision) gets no usage back, so its cost is not counted: the day's total can be under what the vendor bills (INFERRED; whether a vendor bills an aborted request is not verified).
- **A refused key.** The runner marks a key refused (HTTP 401) only when the store still holds the key that call used, so a new key the owner saved meanwhile stays usable.
