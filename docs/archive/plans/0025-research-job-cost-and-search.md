## 5. Design (PROPOSED)

### 5.1 The dataset hash

- **What is hashed.** For the sealed range, in sequence order: every column of each publication, of its observation and of its confirmation, as the database's binary `COPY` output of `SELECT p.*, o.*, c.*`; then every column of each instrument row an observation of the range refers to, in the order of their identifiers. The header and trailer of each `COPY` stream are not hashed, so the value depends on the rows alone and not on how the range was cut. A version line is hashed first.
- **How.** Chunks of a fixed number of sequence numbers, one `COPY` each, far inside the 30 s a statement may take. Beside each chunk one grouped count gives the rows by acquisition and the instrument identifiers, and the rows the chunk sent are compared with the rows counted. The lease is renewed when two seconds have passed: between chunks and, asked every 2,000 rows, while a chunk streams.
- **Errors.** The `COPY` runs on the driver's connection, where SQLAlchemy translates nothing. A driver error is raised as the SQLAlchemy error it would have been, because the bridge handles that family and would otherwise end its process. A stream that is not whole, rows sent that differ from rows counted, a missing instrument row and a client encoding other than UTF-8 are `DatasetStreamError`, of the same family: the runner ends the job on it and the bridge logs a failed seal or advance.
- **What stays.** The guarantee (P1), the row counts, the checks in `runner._execute` and in the bridge's seal, and that no value is decoded into a float: numerics travel in their exact digits.
- **What changes.** Every hash value. A dataset sealed by an earlier build is refused by a later one as `DATASET_CONTENT_MISMATCH`, which fails closed. The normal application holds no sealed dataset.
- **A limit (official source, §7).** PostgreSQL does not promise the binary format across major versions. A store sealed under one major version and read under another could be refused, closed, until the next day's dataset. The old value depended on the session's time zone; the new one depends on one session setting, the client encoding, in which PostgreSQL sends text: it must be UTF-8, as it is for every connection of this application, and is checked.

### 5.2 Held writes in a replay batch

- A replay batch's connection (`replay_path.TrackedConnection`) holds three statements instead of sending them: the valuation insert, the NAV update and the step insert. It sends them, the rows of each statement in the order they were issued, before any other statement of a step and before the commit. One statement of the research replay precedes them at a commit: its fence, which reads the job's queue row and none of these rows.
- **How several rows of one statement are sent.** One waiting row is the statement as it was issued. Several rows of an insert are one statement with one parameter, a JSON document that is the array of the rows' parameter sets: `INSERT ... SELECT ... FROM jsonb_array_elements(:rows) WITH ORDINALITY ... ORDER BY ordinal ON CONFLICT (id) DO NOTHING` (`store.VALUATION_INSERT_MANY_SQL`, `STEP_INSERT_MANY_SQL`, `store.held_rows`; §7). Each value is read back from text exactly: a decimal in plain notation, a time with its offset and microseconds, an identifier as text, and the JSON columns as the text the single statement casts. The rows are inserted in the order they were issued, so of an identifier issued twice the first stays, as with the single statements; P14 compares the stored rows of both forms. An earlier form of this statement took one array a column (`unnest`); the driver dumped every array element by element in Python, 9.5 s of a 211 s profile (§14). Of several NAV updates only the last is sent: the statement sets the one account row to the values it is given, so the row is then what sending each would have left, and the guard on that row has compared the same first and last state. The first figures were taken with `executemany` instead, which sent the rows one statement each in a pipeline: 29 s of a 213 s profile went to it (§14).
- **Why nothing can observe the difference.** Within the transaction every other statement finds the rows already there. Outside it nothing sees them before the commit, as now. None of the three tables has a trigger that reads another table (`0005_m3_paper_broker.py`: `asl_account_state_guard` compares old and new values of its own row; the others are the immutability and mode guards), so the order between the three groups cannot matter. Each row's own order within its table is kept.
- **Failure.** A held write the database refuses raises at the statement that sends it or at the commit. Either way the batch is rolled back and the engine's memory returns to the batch's start, as for any failed step today.
- A switch on `FastPath` turns holding off; the tests compare both.
- The forward engine has no batch and no such connection. `store.py` gains named constants for statements it already issues, whose text is unchanged, and the two multi-row forms, which only a replay batch sends.

### 5.3 Smaller costs on the replay path

- `replay_path.clone` returns a value of an immutable type at once and tests a container's members before calling itself. What it returns is unchanged.
- `numbers.mul`, `div`, `add` and `sub` ask the one context directly (`CONTEXT.multiply` and so on) instead of entering a copy of it for every operation; a step with a position asks about thirty of them. The context's methods compute what the operators compute inside it: the same digits, exponent, rounding and traps (P21 holds each against the operator, exactly as the helper was written before, a sum beginning at zero and a product at one). This is the one change of this plan in code the forward engine runs; it changes no statement and no value. The helpers that quantize are unchanged.
- The read cache works out once, when it keeps a value, how to copy it (`replay_path.copier`): which of its members are containers. Every later read copies each container in one call and visits only those members, where `clone` asks about every member at every read. The kept value is never edited, so what was worked out stays true; the copy is what `clone` returns for the same object, a new container at every level (P19).
- `runner.FencedReplay` renews the research lease when one second has passed since it last did, not at every batch. It still takes the fence, with its lock, at every batch's open and commit. The renewing thread of `runner.execute` is unchanged. Should that thread have stopped, the lease now holds at least 14 s after a batch opened, where it held 15.
- A research replay's batch may last a second and 4,000 steps (`runner.BATCH_STEPS`, `BATCH_SECONDS`), where the default is a quarter second and 500: a batch's open, its first step's reads and its commit cost the same however many steps it holds. A batch holds the job's queue row shared until it commits, and the renewing thread waits for that row for at most the 2 s of its lock timeout; the transaction's idle limit is 3 s. `run.replay` and `run.fast_path` take the length; every other replay keeps the default.

### 5.6 Quiet stretches (added after the first figures)

OBSERVED in the profile of the multi-row build (§14): of 715,961 triggers of one cell, 541,193 took no step. Each still cost a row read from the database, a `Publication` and quote row built, and the calls of `needs_step`, `next_deadline` and the quote tracker.

- **When nothing can happen.** `ExecutionEngine.idle`: no owner request, run completion or approval change waits; a live run's flow marks are captured; there is no open order, position, stop, obligation, pending signal, holding or depleted price level. Then `needs_step` depends on a publication's kind and its decision time alone: it is true for a confirmation or a final candle (when the strategy is enabled), when a live run's hourly capture is due, and, for an engine that may open exposure, when the UTC day has no reference yet. `quiet_bound` gives the time before which neither of the last two can become true and before which `next_deadline` names no timer: the next hour of a live run or of an enabled strategy's checkpoint, the next UTC day, the next deadline. None of these moves while no step is taken.
- **What the driver does.** With a fast path that reuses state, and a clock, it limits that bound by the next timed input and by the end of the run, and asks the database for the first publication after the last one handled that must be handed over: one available at or after the bound, a confirmation, a final candle, or a quote the tracker cannot take as visible from its own availability on (no event or receipt time, or an event time further ahead of its availability than the event lead). One more read gives, by kind and symbol, how many publications lie before it, the last sequence, the latest availability, and the latest availability of each symbol's quotes (`MarketView.quiet_stretch`; both reads look at most 20,000 sequences ahead, so a statement's work is bounded whatever the bound: the execution role's statements end after 2 s). The engine records the stretch as `observe` would each publication: the last quote availability of each symbol, the last sequence, the last decision time, which is the larger of the clock and the latest availability; a full batch is committed first, as before a publication. Where a stretch has just ended the driver reads a page of eight publications instead of a thousand, hands them over, and asks again; and it leaves a whole page as soon as the engine is idle again, instead of handing the rest of it over first.
- **Why the result is the same.** Every publication of a stretch would have reached `handle`, found `needs_step` false and been recorded; no timer or timed input falls before any of them; the clock afterwards is the same. The decision times of all later triggers are therefore the same, and so is every step.
- **The quote tracker** never saw the quotes of a stretch. It is told (`passed`) and declines for that symbol; the engine then reads the latest quote from the database, as it does whenever the tracker declines, and hands the answer back (`refresh`). The tracker takes it only at a decision time by which every quote passed over is visible (each is, from its own availability on, by the rule that made it part of a stretch), when no folded row is still invisible and the time did not go back. The answer is then the newest of everything visible, seen or passed over, and the rows it still holds back are exactly the ones not yet visible. The final-candle memo sees every final candle: none is passed over.
- **A research window** scopes both reads to its sealed range like a page of publications, after the same lease check.
- **Verification.** With `verify` the publications of a stretch are handed over one by one, and the driver compares the number of steps and of triggers handed over, the clock, the last sequence and the quote availabilities with what the stretch said; a difference fails the run. `FastPath.quiet_skip` turns the stretches off; the replay report states the option.
- **A page that ends the run.** With an end time, a page none of whose publications is available by then ends the run. The page of eight asks again with a whole page before it ends one, so a run ends where it did unless availability goes back across a whole page, where the old end already depended on where a page began.
- **Limit.** A buy's fee is taken in the base asset, so a closed position usually leaves dust, and with a holding every quote is a step: after its first exit a run is not idle again. The stretches are the time before a cell's start, before the first entry, and between positions that close without dust.

### 5.7 The breach check of a step (added after the first figures)

`StepContext._breaches` asks `risk.breached_caps` in every step with a position: about 15 exact multiplications and sums, 17 s of the 211 s profile. While a position is held, every quote that moves no held bid asks what the step before asked. On the fast path with state reuse the engine keeps the last question and its answer (`ExecutionEngine.breached_caps`): an equal portfolio, the same scenario and the same ticks get the kept answer as a new set. The function reads nothing else but the engine's fixed policy and decides by comparing values, so an equal question has the same answer; equal decimals of different scale compare equal and give equal products. With `verify` it is computed anyway and compared. The forward engine computes it in every step.

A quote that moves a held bid asks a new question, of which one part is still the old one: the planned open risk (`risk.planned_open_risk`) reads the positions, the pending entries, the scenario and the ticks, and no price. The engine keeps it while those are equal and hands it to `risk.breached_caps` through a new optional argument; without the argument the function computes it, as the forward engine has it do. With `verify` it is computed anyway and compared. In a cell that holds both symbols while prices rise, every quote is such a question.

### 5.8 A step that can do nothing is not taken (added after the first figures)

OBSERVED: while anything is held, `needs_step` makes every quote of every symbol a step, because the scheduling summary knows only that some holding is not zero. MEASURED after §5.6 and §5.7 (§14): a cell with one day in a position still took 174,768 steps in about 80 s, half of them for the quotes of the symbol that is not held.

- **What is foretold.** On the fast path with reused reads, before a step is taken, `ExecutionEngine._inert` says whether it can do anything. It says no only when all of this holds, each read from what the batch already holds:
  - the trigger is a quote, not one handled late, of a symbol whose asset the account does not hold and in which no position is open, and no depleted price level of that symbol is remembered;
  - no bar became evaluable (the evaluations prepared for the step are empty);
  - every read the step would reuse is there, so no write has changed it since: holdings, positions, orders, obligations, latches, breaches, the run, pending signals, the summary, the day's reference; and there is no open order, no obligation, no pending signal, no owner request, the account is sound, and a live run is in a state no step changes (`RUNNING` without a cause or `PAUSED`, no drawdown cause);
  - nothing is due by time: the day has its reference, the last valuation is less than a minute old, no deadline has passed (a time exit among them), and a live run's hour and its flows are captured;
  - every position is open with a first fill, and every symbol that is held or has a position has, at this decision time, the same latest quote in the same quality as in the last step that was taken in this batch, with the protection gap of each position as that quality says it should be. The engine's quote tracker and the recorded quality rule give both without a statement.
- **Why the step would then do nothing.** Phase by phase (`StepContext.phases`): no request to apply; no order to fill or expire, and no depleted level of the trigger's symbol to reset; the trigger is not a quote of a position's symbol, so no stop is crossed by it, no time exit is due, and each position's quote is as usable as before; no evaluation; no obligation to turn into an order; the valuation sees the cash, holdings and bids of the last step taken, so the NAV is that step's NAV, which is not above the high-water mark that step left, breaks no latch that step did not break, and gives the breach check the question that step asked (the trigger's own bid enters it only through an asset that is not held); no hourly or flow capture; no start or resume; no signal to enter on or to expire; no change of the run's state. A write that changed any of these reads would have cleared them, and the foretelling needs them all.
- **What is done instead.** What `persist` and `_adopt` leave of a step without effects: the batch's checkpoint (the trigger's watermark and decision time, the unchanged memory), the last sequence and the last decision time. The step is counted as a step. A step row is written only for a step with effects, so none is missing.
- **Verification.** With `verify` the step is taken anyway, and it must have issued no statement that is not a read, have no effect, and leave the checkpoint and the outcome that were foretold; anything else fails the run (`replay_cache_divergence:inert_step`). Every scenario test runs in that mode too. `FastPath.inert_skip` turns the foretelling off; the replay report states the option.
- **What it does not cover.** A quote of a held symbol is always a step. So is everything else: timers, candles, confirmations. The forward engine takes every step.

### 5.9 The constant costs of a held step (added 2026-10-18, after gate run `m7-g1a`)

OBSERVED in gate run `m7-g1a` on the owner's PC (2026-10-17, [ExecPlan 0026 §18](0026-m7-agent-driven-main-decisions.md#the-m6-b-gate-run-m7-g1a-and-the-held-steps-cost-2026-10-17-and-18)): the shadow advance over 21 days is projected at 3,781.4 s against 3,600, because its 38 stepped days are charged at 87.03 s each, the rate of a day with a position. MEASURED in a profile here (a 64-hour replay of the M3 density fixture holding a position for 24 hours): a quote of a held symbol is always a step (§5.8), and such a step costs about 0.42 ms, nearly all of it Python; the database's part (the valuations' and steps' statements, the quote pages) is small. So the rate falls only by making each held step cheaper. Seven changes do that, each leaving a cell's rows, ids and step record identical, each with a test (`test_m3_throughput.py`, `test_m3_unit.py`):

- **The run's manifest is shared, not copied.** The read cache copied the whole `pilot.Run` at every read of every step (`copier`), and most of that copy was its manifest, the run's frozen documents: about 6% of a held step's CPU. Nothing edits a run's manifest once `pilot.load` has built it (every use in `app/` reads it), so `pilot.Run.SHARED` names it, and the read cache hands every copy of a kept run the same manifest; every other field is still each step's own copy. With `verify` the kept run is compared with the database's at each read, so an edit of the shared manifest fails the run (`replay_cache_divergence:run`), and a test holds that. This revisits §13's "kept values handed out without a copy", for this one field only.
- **A statement's kind is worked out once.** The batch asks of every statement whether it reads and, if not, whether it clears kept reads (`affects_reads`, a scan of the text). The answer depends on the text alone, so `statement_kind` keeps it per text (at most 4,096 texts, then it starts over) and forgets it when `SELF_CONTAINED` is replaced, as one of the runner's tests does.
- **No bar to evaluate, no evaluation prepared.** On the fast path with reused reads, when the final-candle memo is usable for every symbol and holds no final bar after the last one evaluated, `_prepare_evaluations` returns no evaluations without building its connection and ranges: every range it would build is then empty. With `verify` it takes the long way, which compares the memo with the database.
- **A stable id without `uuid5`'s overhead.** `lifecycle.stable_id` computes the same UUID version 5 (SHA-1 of the namespace and the name, its version and variant bits set) with `hashlib` and integer operations; a property test compares it with `uuid.uuid5` on generated kinds and parts.
- **A plain copy without `copy.copy`'s dispatch.** For a class with an instance dictionary (on Python 3.13 an ordinary class's is a managed one) and none of the hooks `copy.copy` consults (`__copy__`, `__reduce_ex__`, `__reduce__`, `__getstate__`, `__setstate__`, `__getnewargs__`, `__getnewargs_ex__`, an entry in `copyreg`'s table, slots, its own `__new__`), `shallow_copier` makes a new instance and copies its dictionary: what `copy.copy` makes of it. Any other class keeps `copy.copy`. The batch's summary is copied that way instead of `dataclasses.replace`, which would run its `__init__` for the same fields.
- **The JSON encoders are kept.** `store.jdump` and `store.held_rows` encode with a module-level `json.JSONEncoder` of the same options instead of building one per call; the encoder keeps no state between calls.
- **The held check first.** `_inert` asked whether the trigger's asset is held after reading every kept value; it now asks first, so a quote of a held symbol leaves at once.

MEASURED here (scratch PostgreSQL 16, one process, code identity pinned so that the experiment's id stays the same; §14): the 64-hour replay took a median 51.71 s on `main` and 46.33 s with the changes (CPU 39.55 and 34.10 s), with the same portable, full and trace fingerprints and 86,298 valuations. The forward engine shares two of the changes, the stable id and the JSON encoders, which give the same bytes; the other five are on the replay batch's path only.
