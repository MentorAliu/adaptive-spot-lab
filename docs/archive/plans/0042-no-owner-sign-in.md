## 2. What the app has today

`OBSERVED` at `92c7b7e`:

- **Owner records.** Owner requests resolve the session from the token hash (`app/agents/approvals.py` and `app/experiments/approvals.py`, `session_id`), and seven checks make an `OWNER` row carry a session: `owner_approvals` and `agent_approvals` (`*_actor_session`, plus a foreign key from `owner_approvals.session_id` to `owner_sessions`), `agent_runtime_profiles` (`agent_profile_owner_key`), `agent_workflows` (`agent_workflow_owner_key`), `agent_runtime_requests` (`agent_request_owner_session`), `source_refresh_requests` and `decision_pause_requests` (unnamed checks). `futures_owner_requests` and `owner_decisions` (funding) carry no session.

- **The agents' switch.** The runtime starts `DISABLED` (reason `INITIAL`); the owner's Turn on records an `OWNER` `ENABLE` request that the agent worker applies (`PROBE_ONLY` with `CHECK_PENDING`), and the agents' check enables it when it passes. `in_force.switched_on` reads the owner's latest switch request.
- **Web.** `apps/web/src/account/account.server.ts` keeps the session in the `asl_owner` cookie and gives each page a `SETUP`, `LOGIN` or `ACCOUNT` phase; `owner-access.tsx` draws the setup and sign-in forms on Home and Settings.

## 4. Design

### 4.1 No sign-in

`app/owner.py` and the five `/v1/owner/*` routes are removed. Every route that took `require_owner_session` takes the service key only (`require_service_key`): the web's server functions are the only holder of that key, and the web is reachable only from the PC. The owner functions lose their `token_hash` argument; an owner row carries no session (`session_id` stays `NULL`). The web drops the cookie, the phases and the setup and sign-in forms, and every page reads the account directly.

### 4.2 Migration `0021_no_owner`

- Drops `owner_approvals.session_id`'s foreign key, then the tables `owner_sessions` and `owner` (and their grants).
- Rewrites the seven checks so an `OWNER` row needs no session, while every other requirement stays: an owner request still needs its idempotency key and request hash (and the correlation id where it did), and a row that is not the owner's still carries no session. The `session_id` columns stay, nullable, as the history of rows written before; nothing writes them.
- Downgrade restores the tables, the foreign key and the old checks, and refuses while an `OWNER` row without a session exists (the old checks cannot hold for it).

### 4.3 The account funds itself

`accounting.fund_by_itself()` runs in the API's startup, after the reconciliation it already runs there. A funded account is read first without a lock, so a start after the first takes no lock on the account. Under the account's row lock: if the account is initialized it does nothing; otherwise it records the initial funding request under the fixed key `SYSTEM:INITIALIZE` (exactly 10,000 USDT, the draft and request hashes as the owner's confirmation computed them) and posts it through the same `_post_funding` as before: one journal transaction (`OWNER_CASH` +10,000, `VIRTUAL_CAPITAL` −10,000), NAV 100, 100 units, high-water NAV 100. It records no owner decision: the audit and outbox events say `SYSTEM`. A reconciliation failure or the account's pause leaves it unfunded with a log line, as they refused the owner's confirmation; a request left `PENDING_VALUATION` by an operator's valuation override is posted at a later start. A second API process waits on the lock and finds the account funded. The owner's initialization routes are removed, and the funding draft takes `TOPUP` only; top-ups stay the owner's.

`IMPLEMENTED` after review of the first draft: canceling the pending initial contribution would leave nothing that could ever fund the account, so `resolve_pending` refuses it while the account is not funded (`INITIAL_FUNDING_NOT_CANCELABLE`, 409) and the web shows no Cancel on it (Retry stays). An initialization the browser saved before this update (its funding intent, kind `INITIALIZE`) is cleared on the account page's first read, so top-ups are not held behind it.

`IMPLEMENTED` after the independent review: a contribution refused at the start (a reconciliation latch, which an engine clears once a later reconciliation passes, or the account's pause) or held for a valuation is tried again every minute while the API runs (`main.keep_funding`), where the owner sent the confirmation again before. The refusal of a cancel comes after the request's status, so a cancel sent again answers as before, and an initialization an older app left pending beside the funded account (it can never post) can be canceled, with Cancel shown for it. `GET /v1/account/requests/SYSTEM:INITIALIZE` reads the app's request (the key's colon is outside the owner's key pattern).

### 4.4 The agents switch themselves on

The owner's switch has three positions: on, off, and no word yet. "No word yet" now counts as on: `in_force.switched_on` is true when no owner switch request exists. The worker's `carry_switch` also takes a runtime in its first state (`DISABLED`, reason `INITIAL`, no `first_left_disabled_at`) to `PROBE_ONLY` with `CHECK_PENDING` on the profile in force, recording `PROFILE_IN_FORCE` as `SYSTEM`; the agents' check then enables it, as after the owner's Turn on. The owner's Turn off (`DISABLE`) stays final until the owner's Turn on. Nothing here clears a latch or enables without a passing check.

`IMPLEMENTED` after the browser suites: a runtime switching itself on reads as on, so Settings offers its Turn off from the first state too (`views.runtime_view`'s `disable`). The owner's `DISABLE` there leaves the row in its first state (the reason stays `INITIAL`) and the switch off, so nothing discovers or carries it until the owner's Turn on. After the independent review: Turn off is offered there only once the app has the profile in force, because the Turn on afterwards names that profile and a runtime turned off in its first state is not discovered; before it (the worker's first tick, or a runner with no sign-in) nothing runs and nothing is offered.

`IMPLEMENTED` after a gap found in the first draft: the worker ran the runner's discovery (no model call) only while the runtime was not `DISABLED`, and the app composes the profile in force only from a discovery, so a runtime in its first state never got a profile to be carried to. It is the PC's case: `OBSERVED` on the PC at 07:18 UTC on 2026-10-25 ([ExecPlan 0039 §15](0039-bitcoin-futures-on-paper.md#15-progress)), the clean start's empty database has its runtime in its first state with no runtime event (not read since the install of 07:38 UTC), and `OBSERVED` in code, only the M5 administrator's `ACTIVATE` or the owner's Turn on, which needs that profile, moved a runtime out of it. The worker now also discovers the runner while the runtime is in its first state and the switch is on (`Worker.waking`, `in_force.waking`); a runtime the owner turned off is not discovered.

### 4.5 Install

`compose.yaml` drops the `owner_setup_key` secret; `tools/setup-local.ps1` stops creating it; the update's read-out says the account and the agents start by themselves. The migration runs in the update's ordinary migration step.

`IMPLEMENTED` in `tools/update.ps1`: the check after the update accepts, from a switch in its first state (and on a clean start's empty database), the switch still in its first state or `LOGIN_REQUIRED`, `PROBE_ONLY` or `ENABLED` (`Test-NeverOn`, `Test-SwitchingOn`); off for another reason fails the check, as on to off always did. While the agent worker runs with the agents enabled, it waits up to two minutes for the switch to leave its first state, and then says whether it is on, waiting for the runner's sign-in, or not there yet. The read-out of the futures account names the starting contribution's status when the account is not funded. The new API accepts schema `0020` too, so the update replaces it before the migration (expand), and its start funds the account on `0020`: the funding tables are the same in both. After the independent review: on `0020` the owner's requests that record an owner row (the agents' switch, a workflow's cancel, approvals, a source refresh, an entry pause's resume) answer `503` `OWNER_SCHEMA_PENDING` and record nothing until the migration (`agent_views.require_owner_schema`), instead of failing on `0020`'s session checks; the reads, the futures controls and top-ups answer. That lasts from the API's replacement to the migration: about a minute, and up to about twelve when the update waits for a quiet minute near the hour. The update also reads the owner's last switch request (`Get-RuntimeState`'s `owner`): a first state the owner turned off is read out as off, with no wait, and an update that turns it on fails its check. After the first install stopped ([§13](#13-progress)), the update replaces the api before the web, both before the migration and in the recreation's order: the new web reads the account through the api with the service key alone, which the old api refuses (`401`), so the new web's health check, which reads its home page, passes only once the new api runs.

## 10. Failure and rollback

A failed update stops as before and leaves the old app. Migration `0021` drops the sign-in's two tables, the passphrase hash and the sessions (the update's backup keeps them); nothing else is deleted. If the self-funding cannot post (reconciliation failure, the account's pause), the account stays unfunded and the API logs why; the update's read-out shows the account not funded. A rollback to `0020` restores the sign-in's tables empty; the old app would then ask for the setup key, which is still in `secrets\`. The downgrade is refused once the owner has made a request the old checks cannot hold (an `OWNER` row without a session, for example turning the agents off): then the way back is forward, as for every migration since `0011`.
