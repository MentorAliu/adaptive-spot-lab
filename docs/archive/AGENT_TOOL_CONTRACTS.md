# Application agent tool contracts

## Scope and status

These are **application tools**, not Binance endpoints or vendor-provided Codex functions. M5 implements catalog v1 below. M6 catalog v2 is the approved contract of [ExecPlan 0023](plans/0023-m6-research-investigations.md), with implementation and verification recorded per batch. The trading tools are catalog v3, the approved contract of [ExecPlan 0026](plans/0026-m7-agent-driven-main-decisions.md) for M7, implemented in B5 and tested offline only ([below](#m7-tool-catalog-v3-approved-contract-execplan-0026)). The default transport is the structured action loop in [RUNTIME_AGENTS.md](RUNTIME_AGENTS.md). Only the trusted dispatcher executes registered handlers. A future MCP adapter must preserve the same authorization and semantics.

[AUTONOMY_MATRIX.md](../AUTONOMY_MATRIX.md) owns permission policy. [DATA_CONTRACTS.md](../DATA_CONTRACTS.md) owns shared records; [API_CONTRACTS.md](../API_CONTRACTS.md) owns owner/BFF routes. Never expose a generic SQL, shell, HTTP, file-read, code-execution, balance-write or policy-edit tool.

## Common request and response

The dispatcher resolves authenticated role/account/mode/policy/job from trusted state. Model-supplied echoes cannot choose another identity. Every dispatch binds a server request ID, parent workflow/step, capability/permission epoch, policy/envelope and schema versions, input hash, evidence cutoff, deadline and budget reservation.

Inputs use finite canonical decimal strings, bounded strings/lists, UTC timestamps and enums. Reject unknown fields. Schemas use explicit tagged unions rather than arbitrary dictionaries. References must exist and be visible to the role, mode, experiment and as-of window. A user-provided display name is not an ID.

Response: `request_id`, `tool_name`, `schema_version`, `status` (`SUCCEEDED`, `ACCEPTED`, `REJECTED`, `UNAVAILABLE`), bounded `data` or safe `error`, authoritative artifact IDs/versions, input/output hashes, creation/availability timestamps, provenance/quality and consumption metadata. `ACCEPTED` means a queued job or intent, never a fill.

Side effects require a server-generated durable operation key and canonical input hash. Repeated same operation returns its original result; changed payload conflicts. Deduplicate equivalent outstanding actions at the domain level as well, so new request IDs cannot bypass exposure/turnover/experiment limits. At-least-once delivery is expected; there is no blanket exactly-once transport claim.

## TradeIntent discriminated union

Common fields: decision policy/version, account snapshot/version, mode, position/instrument IDs where applicable, evidence/assessment IDs, decision as-of, expiry, rationale, uncertainty/invalidation, cost-model reference and expected management-template version. Server injects role/approval authority. An evaluator review binds the canonical draft hash, evidence snapshot and policy version.

| Action | Required action-specific content | Engine meaning |
|---|---|---|
| `ENTER` | Approved symbol; desired target fraction/maximum spend bound; approved horizon; protective mandate inputs with evidence; permitted execution envelope | Derive executable size with current equity, risk, fees, liquidity, filters and pending reservations; never exceed requested bound or policy caps |
| `HOLD` / `ABSTAIN` | Scoped instrument/position or portfolio and reason | Recorded decision only; cannot extend an exit deadline or alter protection. In M7 a per-symbol entry of the coordinator's PortfolioDecision, not an intent |
| `REDUCE` | Position ID; reduction bound or target remaining quantity; mandate permission | Sell only valid owned/reserved-available quantity; no shorting or assumed proceeds. Not built in M7 (M7-OD7): it needs a fill deadline, must never delay a protective exit and must not leave dust; it gets a plan of its own |
| `EXIT` | Position ID and permitted exit reason | Queue a capped closing intent; reconcile simultaneous protective exits to avoid double sell |
| `CANCEL_ENTRY` | Own pending discretionary order ID/version | Cancel only remaining cancellable entry; atomically release unused reservations; filled amount retains its protection |
| `TIGHTEN_STOP` | Position ID, permitted new stop input, evidence and expected mandate version; in M7 the input is a template choice (`BREAKEVEN` or the policy's stop template), never a stop level | Validate monotonic long-stop tightening and current execution semantics; never remove old protection before atomic replacement |

Do not let a coordinator modify instrument universe, risk budgets, an original maximum-hold deadline, fee model or account denomination inside a trade payload. Reject nonsensical/nonpositive stop geometry. If a tighter long stop is already crossed, follow the mandate's executable exit behavior rather than install an impossible passive protection.

An approved agent-driven policy may authorize discretionary entry/exit; it need not reproduce the EMA reference signal. Its declared management, evidence, action domain and hard caps still apply. One position owner per symbol and no pyramiding remain the pilot constraints.

## Commit-time checks, order and fill semantics

Submission recomputes permissions/revocation, job/intent expiry, policy approval, current snapshot validity, source quality, reviewer binding, strategy eligibility, portfolio state, current valuation, risk, spendable cash, pending commitments, turnover and order filters. Never trust agent-supplied measured prices or confidence as sizing facts.

Lock/fence the financial aggregate before reservations. Two simultaneous intents cannot consume the same headroom. Treat sell-then-buy as separate transitions: a requested sale does not fund a purchase until relevant modeled fills settle. Multi-asset targets are not assumed atomically filled. Return actual acceptance/partial/rejection states, not a fabricated balanced allocation.

Fresh market execution evidence is required at submission/fill even when the agent reasoned over older completed candles. A bounded intent validity window and permissible deviation are policy inputs; a timestamp alone cannot make obsolete analysis current. Material changes require new evidence/review, not silently reusing an old draft.

The paper broker produces fill records under [PAPER_EXECUTION.md](../PAPER_EXECUTION.md); accounting posts under [LEDGER.md](../LEDGER.md). The tool cannot directly submit a fill, choose its historical timestamp or claim execution at a last-trade price.

## Research validation and resources

`register_candidate` accepts only a versioned declarative grammar: registered indicators/operators/templates, bounded constants and finite rule graphs. M6 uses the flat, non-recursive `CANDIDATE_GRAMMAR_V1` and domains of [ExecPlan 0023 §5.3–5.5](plans/0023-m6-research-investigations.md#53-candidate-grammar-and-the-strategy-interface). No eval, imports, code strings, regex with unbounded work, arbitrary SQL or file paths. Reject unsupported operators and excessive complexity. Novel executable code remains a reviewed development task, not automatic runtime execution.

`request_experiment` reserves workflow/trial/concurrency/CPU/time/storage budgets before queueing. Bind exact candidate/dataset/split/cost/evaluation hashes. The research runner has no route or credential to the main database, provider credential or arbitrary network access. Checkpoint/cancel on bounds; record incomplete results honestly. Experiment results never become main cash or a new approval.

A long-running tool response is an artifact/job ID. Suspend the workflow and release the inference slot; do not ask the LLM to poll continuously. M6 keeps the initial immutable tool result and adds one immutable `agent_tool_completions` row per call, with a distinct citable `result_ref`. Resume once only if the workflow, epoch and wait deadline remain valid. Count model-running time separately from waiting time; the cutoff stays fixed. Results arriving after revocation/deadline remain historical artifacts and resume nothing.

## Approved-source fetching

`request_source_refresh` accepts source IDs and supported filters, not arbitrary URLs. The ingestion adapter resolves the exact approved HTTPS host and constructs GET paths only from its registered typed templates. Every resolved address must be global; connect to the checked address with the original TLS name. Disable redirects and environment proxies; block IP literals, loopback, private, link-local, metadata and host-gateway destinations; bound size/type/time; remove markup; and record supplied publication/update times separately from receipt/availability. See [SEC-01](../REFERENCES.md#sec-01). Search/fetch provenance cannot be created by the model.

Discovered links outside the approved source definition create a source proposal, not an automatic fetch. New paid providers or source permissions require owner approval. Duplicated syndicated reports are not independent confirmation.

**B5 (ExecPlan 0023) implemented the fetch and search functions; B6 added the two tools on top of them** ([catalog v2](#m6-tool-catalog-v2-execplan-0023)). Until definitions v2 existed, `request_source_refresh` and `search_evidence` were absent from the catalog and refused. What the tools call:

- `app.sources.store.enqueue` accepts a registered source ID and that source's typed integer filters. An unknown, unapproved or invalid source returns `SOURCE_UNAVAILABLE`; any other key, a string, a URL or an out-of-range value returns `FILTER_INVALID`. A refusal writes no row. The database guard binds the row's actor to the connecting identity. A repeated tool call or owner key returns its first request; the same key with other content returns `IDEMPOTENCY_CONFLICT`. An equal request inside the refresh interval returns the existing request, whatever state it reached.
- A request that cannot run is ended without a network exchange: `CANCELED` when its source is no longer approved or its permission epoch has changed, `EXPIRED` after the six-hour wait deadline, `FAILED` with `BUDGET_EXHAUSTED` or `BACKOFF_ACTIVE` and the time at which to ask again.
- `app.sources.evidence.search`, `open_item` and `search_artifacts` take a server-owned scope (role and cutoff). Malformed arguments return `SCHEMA_INVALID`; a window past the cutoff returns `ASOF_VIOLATION`; a hidden, unapproved or unknown item returns `EVIDENCE_UNAVAILABLE`, the same code for each.
- Fetch outcome codes: `SUCCEEDED`, `DNS_FAILED`, `DNS_NOT_PUBLIC`, `CONNECT_FAILED`, `TLS_FAILED`, `TIMEOUT`, `REDIRECT_REFUSED`, `HTTP_ERROR`, `RATE_LIMITED`, `WRONG_CONTENT_TYPE`, `ENCODING_REFUSED`, `TOO_LARGE`, `TRANSPORT_FAILED`, `PARSE_FAILED`, `STORE_FAILED`, `WORKER_LOST`, `LATE_REVOKED`, and the two refusals above.

B6 maps these to the stable tool codes, writes the completion for a waiting workflow, and applies the `RESEARCH_V1` cutoff to what a completion may contain: an enqueue refusal becomes `SOURCE_UNAVAILABLE` or `SCHEMA_INVALID`, and the fetch outcome code is reported in the completion.

## Errors, retry and abuse

Stable codes include `ROLE_DENIED`, `CAPABILITY_REVOKED`, `SCOPE_DENIED`, `SCHEMA_INVALID`, `EVIDENCE_UNAVAILABLE`, `ASOF_VIOLATION`, `REVIEW_REQUIRED`, `REVIEW_STALE`, `DATA_STALE`, `INTENT_EXPIRED`, `POLICY_PAUSED`, `COST_MODEL_UNSET`, `RISK_REJECTED`, `TURNOVER_BLOCKED`, `BUDGET_EXHAUSTED`, `IDEMPOTENCY_CONFLICT`, `RECONCILIATION_REQUIRED`, `PROVIDER_UNAVAILABLE`. Return safe reasons, retryability and resource IDs, not sensitive traces.

A retry is permitted only by code and within the original authority/budget. Do not repeatedly reissue a rejected order as smaller pieces to evade a portfolio cap. Protective exits are exempt from discretionary turnover/model budgets, not from available holdings, idempotency or valid execution observations.

## Required contract tests

At least one valid and one forbidden case per tool; role spoofing; references to other modes/accounts/locked datasets; permission revoked during a pending tool; changed payload under same key; unknown commits; malicious external instructions; parallel exposure requests; stale evaluator hashes; exceeded experiment budgets; loop termination; cancellation propagation; and no native shell/file/network fallback. [ACCEPTANCE_CHECKLIST.md](../ACCEPTANCE_CHECKLIST.md) records these as implementation gates.

## Time-scoped reads and typed completions

In historical/test contexts, `get_snapshot` and every related read resolve only the authorized simulation clock; a request for a current view cannot escape the job's cutoff. A new external refresh cannot retroactively enter an earlier historical decision. Tool-result projections, summaries and cached memories obey the same data-partition/availability checks as raw records.

M6 clarification approved on 2026-10-03: `RESEARCH_V1` applies the hypothesis cutoff to source-content fields in its own refresh completion and to initial/follow-on source context, including assessment/research-question text derived from late evidence. A completion may acknowledge the queued job's status, but withholds post-cutoff source content; a summary or artifact cannot restore it. `EVENT_INVESTIGATION_V1` may receive what its own refresh fetched through that completion; its fixed cutoff still governs other reads/searches. A typed research artifact derived exclusively from authorized pre-cutoff data is not excluded merely because it was created later. See the [owner decision](../DECISIONS.md#2026-10-03--m6-b0-research-cutoff-clarification).

An `EvaluationReview` declares its reviewed artifact type and purpose, including candidate, trade-intent or outcome review. An `OutcomeReview` is a typed outcome-review projection linked to the same immutable evaluation record, not a new privileged action. A FINISH artifact is processed through its role's validated recording handler; it cannot enqueue trades, approve policies or execute experiments unless the corresponding explicit tool request passed its own contract.

The authenticated source of truth owns IDs and lifecycle transitions. M5 implements and tests the concrete JSON/Pydantic schemas from these fields; the role prompt receives those actual schemas, not a separately maintained approximate copy.

## M5 tool catalog v1 (ExecPlan 0020)

M5 implements only the read and assessment subset below, in [ExecPlan 0020](plans/0020-m5-agent-runtime.md). Every other tool in the catalog above is **absent**: a request for one returns `UNKNOWN_TOOL`, and no route, grant or handler exists for it. The registry refuses a handler whose effect class is not `READ` or `RECORD_AGENT_ARTIFACT`. Catalog v1, role grants v1 and the templates are code-owned, canonical and hashed, and the approved runtime profile binds those hashes.

| Tool | Roles | Effect | Arguments (all others `null`) | Denials tested |
|---|---|---|---|---|
| `get_snapshot` | all | `READ` | `view` = `MARKET`; optional `as_of` | `PORTFOLIO` or `ACCOUNT` view: `SCOPE_DENIED`; `as_of` after the job cutoff: `ASOF_VIOLATION` |
| `query_market_features` | all | `READ` | `symbol` (BTCUSDT or SOLUSDT); `feature_ids` (1–6 registered IDs); `window_hours` (1–168); optional `as_of` | unregistered ID or oversized window: `SCHEMA_INVALID`; other symbol: `SCOPE_DENIED`; future `as_of`: `ASOF_VIOLATION` |
| `read_artifact` | all | `READ` | `artifact_id` | an artifact outside the workflow's own artifacts and its review target, or an unknown ID: `SCOPE_DENIED` (the same code, so existence is not revealed) |
| `record_assessment` | ANALYST | `RECORD_AGENT_ARTIFACT`, FINISH only | the `finish.assessment` object | another role: `ROLE_DENIED`; a citation of a result not in this workflow: `EVIDENCE_UNAVAILABLE` |
| `record_review` | EVALUATOR | `RECORD_AGENT_ARTIFACT`, FINISH only | the `finish.review` object | another role: `ROLE_DENIED`; a target hash that is not the bound one: `REVIEW_STALE` |

- **One argument object for every tool.** `tool_request.arguments` has a fixed set of nullable fields (`view`, `as_of`, `symbol`, `feature_ids`, `window_hours`, `artifact_id`). This keeps the model's output schema strict-compatible. The dispatcher then validates the arguments for the named tool, and any field that tool does not use must be `null`.
- **FINISH-only tools.** A `TOOL_REQUEST` naming `record_assessment` or `record_review` is rejected (`SCHEMA_INVALID`, reason `FINISH_ONLY`), or `ROLE_DENIED` if the role lacks the tool.
- **Registered features.** Registered features are computed only from finalized 1h candles over the `agent_read` views, reusing the engine's indicator module: `OHLCV_1H_V1`, `RETURN_1H_V1`, `RETURN_24H_V1`, `EMA20_1H_V1`, `EMA50_1H_V1` and `ATR14_1H_V1`. Each result is a FeatureSnapshot ([DATA_CONTRACTS](../DATA_CONTRACTS.md)): the definition and version, the first and last input bars with their evidence sequences, the warm-up, the quality with its reason, and exact decimal strings.
- **Time scope.** A workflow's cutoff (time and publication watermark) is fixed when it starts, together with the feed states observed then. Every read resolves only publications at or below the watermark and available by the cutoff, so a rerun with the same database state and cutoff reproduces the same result hash. Quote age is measured at the cutoff.

**Response envelope.** Each response has these fields:
- `request_id`, `tool_name`, `schema_version` and `status` (`SUCCEEDED`, `REJECTED` or `UNAVAILABLE`);
- bounded `data`, or a safe `error` with `code`, `message` and `retryable`;
- `result_ref`, a server-issued random reference;
- the input and output hashes;
- `created_at`;
- provenance and consumption.

The model cites results by `result_ref`, and artifacts may cite only references issued in their own workflow (invariant J5). The live probe CP-01 checks that the refs cited are the ones the tools actually returned.

**Artifacts.**
- `MarketAssessment`: symbols; a summary; observations, each labeled `OBSERVATION` or `CALCULATION` with citations; hypotheses with citations and invalidation conditions; uncertainty (`LOW`, `MEDIUM` or `HIGH`) with reasons; missing evidence; and an expiry of 1–72 h.
- `EvaluationReview` of type `ASSESSMENT_REVIEW`: the target artifact ID and SHA-256; supported and unsupported claims; deficiencies; citations; and a verdict of `ACCEPTABLE`, `NEEDS_EVIDENCE` or `REJECT`.
- **Abstaining.** Either role may abstain (`INSUFFICIENT_EVIDENCE`, `DATA_STALE`, `CAPABILITY_UNAVAILABLE` or `OTHER`, with a short note).
- **Status.** Artifacts are model-authored and untrusted. A review is not owner approval or executable permission.
- **Limits.** All text fields are bounded, and the artifact is stored immutably under a server operation key.

**New stable codes:** `UNKNOWN_TOOL`, `CAPABILITY_VIOLATION`, `RUNTIME_DISABLED`, `PROFILE_UNAPPROVED`, `PROFILE_MISMATCH`, `OUTPUT_REJECTED` and `OUTCOME_UNKNOWN`. They join the codes above; `ROLE_DENIED`, `CAPABILITY_REVOKED`, `SCOPE_DENIED`, `SCHEMA_INVALID`, `EVIDENCE_UNAVAILABLE`, `ASOF_VIOLATION`, `REVIEW_STALE`, `BUDGET_EXHAUSTED`, `IDEMPOTENCY_CONFLICT` and `PROVIDER_UNAVAILABLE` keep their meaning.

**Model input scope** (external-data permission, [PLANS](../PLANS.md)). Model inputs contain only:
- public market observations and features derived from them;
- the versioned role prompt;
- the schemas;
- agent-authored artifacts;
- the environment context Codex itself adds; since [ExecPlan 0046](#m11-tool-catalog-v11-execplan-0046), none, and the runner's own base instructions instead (the runtime profile's `provider_added_context`).

They never contain account, ledger, owner, pilot, evidence-pin or secret data. The `agent_read` views exclude `market_evidence_pins`, because pins would reveal pilot trades, and raw payloads.

- **What a `SOURCES` search ranks (ExecPlan 0025, owner decision of 2026-10-09).** The newest 500 matching items the workflow may see, by the time each became available to this installation; the results are the best-ranked of those, at most `limit`. Every visibility rule (approved source version, cutoff, window, source, symbol) is applied before that bound, so an item the workflow may not see is neither ranked nor a reason another is left out. A query that fewer than 500 items match is ranked over all of them. For a word that more items hold, an older item is not returned however often it holds the word. The arguments, the result and the refusals are unchanged. `ARTIFACTS` has ranked the newest 500 visible artifacts since B5.
- **Absent tools.** `request_review`, `draft_trade_intent`, `submit_trade_intent` and `request_entry_pause` are not in catalog v2. A request for one returns `UNKNOWN_TOOL`; no handler, grant or route exists.
- **Effect classes.** The registry accepts only `READ`, `RECORD_AGENT_ARTIFACT`, `RECORD_RESEARCH`, `QUEUE_SOURCE_REFRESH`, `QUEUE_RESEARCH_JOB` and `QUEUE_OWNER_PROPOSAL`, and the worker refuses to start with a handler of any other class. A static test fails if a tool handler module imports the accounting module, an execution engine, store, risk, fill, lifecycle, pilot, activation or replay module, the owner module or the research runner, directly or through another application module.
- **One argument object.** Seventeen nullable fields: the six of v1 and `search_scope`, `query`, `source_id`, `filters`, `limit`, `hypothesis_id`, `hypothesis`, `candidate`, `candidate_id`, `dataset_id`, `experiment_id`. A field the named tool does not use must be `null`. An ID reference is 1–64 characters of letters, digits, `_` and `-`, so a path or a URL in one is rejected with the whole step.
- **Schema v2 against the B0 preview.** The engine re-validates every step with the Pydantic model; the JSON schema sent to the provider only shapes output. The differences from the B0 preview are deliberate. Grammar and comparison operators, the grammar version, a candidate's symbols and its timeframe are plain strings: the grammar refuses an unregistered value and records the refusal as a trial, which an enumeration in the output schema would hide. `filters` and the proposal `summary` were added. Review `deficiency_codes` is an enumeration, and a review claim may also point at the `proposal` and `results` sections. The comparison and the transmission through the pinned CLI are recorded in [INTEGRATION_EVIDENCE](contracts/INTEGRATION_EVIDENCE.md#m6-b6-agentstep-schema-v2-and-queries--2026-10-05).

**Response envelope v2.** The v1 fields, plus:
- `status` may also be `ACCEPTED` for a queued call. The stored result row then has status `QUEUED`, and the envelope carries `wait`: `SOURCE_REFRESH` or `RESEARCH_JOB`, and the request or job ID.
- `provenance`: `available_through`, `holdout` and `shadow`. The server computes them from the records the result was built from, never from model text. `available_through` is the newest availability instant the result actually carries (an item, a quote, a candle, a result), not merely the cutoff it was asked at. Every instant a model is shown is in the `Z` form that `as_of` accepts.
- `citable`: the IDs this result lets the workflow cite or open. `evidence`: the evidence items among them.
- A result over its size bound is refused whole with `RESULT_TOO_LARGE`; nothing is cut into a different result. The bound is the smaller of four times `tool_result_max_bytes` and 60,000 characters. A result that the next prompt could not show beside the role prompt, the schema and the job context is refused the same way, so a model never sees a successful result as "omitted".

**Waiting and completions.** A queued call moves the workflow to `WAITING_TOOL` in the same transaction and releases the inference slot. When the queued work ends, the orchestrator writes exactly one `agent_tool_completions` row for the call, with its own reference (prefix `c-`), `completes` (the initial result's reference) and `late`. In that transaction it resumes the workflow once, provided the lease, the permission epoch, the workflow state and the wait deadline still hold. Otherwise the completion is stored with `late = true` and resumes nothing. A completion that does not fit its size bound is stored in a reduced form (how the work ended, and its ID) and still resumes the workflow. If the awaited work ended `CANCELED` because its source, the envelope or the runtime was revoked, the workflow ends `FAILED` with `CAPABILITY_REVOKED`. If it ended `CANCELED` because the owner canceled that one job (reason `OWNER_CANCEL`, B7), nothing was revoked: the workflow is resumed with the `CANCELED` completion and takes its next step.

**What a completion may contain.** `EVENT_INVESTIGATION_V1` receives the items its own refresh stored, including ones that became available after its cutoff. Its other reads and searches stay at the cutoff, and such an item is opened as of the moment it was delivered. `RESEARCH_V1` receives only items available by its hypothesis cutoff, and no count of what was withheld. A screening completion carries the role's projection of the result.

**Citations.** An artifact may cite initial result references, completion references, and the item, artifact, candidate and experiment IDs that results returned to its own workflow. Any other reference is `EVIDENCE_UNAVAILABLE`.

**Artifacts v2.** Every v2 artifact stores the server-computed `provenance` of what its workflow was given.
- `MarketAssessment` v2: the v1 fields and an optional `research_question`.
- `EvaluationReview` v2: `review_type` `ASSESSMENT_REVIEW` or `CANDIDATE_REVIEW`; the target artifact ID and SHA-256; for a candidate review, `results`, each a job ID with the SHA-256 of its recorded result; a verdict; free-text deficiencies; and `deficiency_codes` from a fixed list (`INSUFFICIENT_SAMPLE`, `DATA_GAPS`, `INTEGRITY_FAILURE`, `COST_UNCERTAINTY`, `HISTORICAL_CONTAMINATION`, `MISSING_BASELINE`, `INCOMPLETE_TEST_SET`, `UNSUPPORTED_CLAIM`). A tuning role is shown only the verdict and the codes of a review that consulted holdout or shadow results.
- `ResearchProposal`: the hypothesis, a summary, the workflow's candidates, citations and at most one nominated candidate.
- `PromotionRequest`: the candidate ID, its normalized hash and its evidence references. It creates one `research_promotions` row in state `PENDING`.

**New stable codes:** `HOLDOUT_LOCKED`, `SOURCE_UNAVAILABLE`, `RESEARCH_UNAVAILABLE`, `EVIDENCE_NOT_READY`, `RESULT_TOO_LARGE` and `TOOL_FAILED`. The v1 codes keep their meaning.

**Rules added after the independent review of 2026-10-05** ([ExecPlan 0023 §18](plans/0023-m6-research-investigations.md#18-completion-evidence)):

- **A step PostgreSQL could not store is rejected.** A string with U+0000 anywhere in a step, or a control character in `query`, `source_id`, a constant or the stop multiple, makes the step `REJECTED_OUTPUT` (`SCHEMA_INVALID`). It never reaches an insert that would fail.
- **A handler that fails is one recorded result.** Each handler runs inside a savepoint. A refusal it raises keeps what it recorded, such as a refused trial. Any other failure rolls its writes back and is recorded as `UNAVAILABLE` with `TOOL_FAILED`; the workflow goes on.
- **Provenance covers what the server binds.** A candidate review is `holdout` whatever its author read, because it is bound to the full test and carries figures the application read from that result. A promotion request is `holdout` and `shadow`. A review also takes over its target's bounds. Unreadable stored provenance is treated as `holdout` and `shadow`.
- **A review's target is in its job context** (`review_target.target.document`, labeled model-authored and untrusted). The reviewer needs no call to fetch it, which leaves a step in reserve for a finish the application refuses.
- **Dataset gaps by role.** A tuning role is told only how many recorded gaps had ended by its cutoff; the count for other roles covers the whole dataset.
- **A canceled request that was not the caller's own.** A refresh or a job reused from an earlier permission epoch may already be canceled as revoked. The reusing workflow is told `CANCELED` in its completion and goes on; only work it queued itself, or under its own epoch, ends it as `CAPABILITY_REVOKED`.
- **Refusals name the hypothesis.** A registration refused after the hypothesis was recorded states the hypothesis ID, and the job context shows it under `research.hypothesis`.
- **A probe records no promotion,** whatever candidate it names.
- **Kept as the contract states it, by the owner's decision of 2026-10-05** ([DECISIONS](../DECISIONS.md#2026-10-05--m6-b7-experiment-read-codes-canceled-jobs-and-rejected-promotions)): `read_experiment` answers an unknown ID with `SCOPE_DENIED` and an existing full test or shadow with `HOLDOUT_LOCKED`, so a tuning role that holds such an ID learns that it exists. The IDs are random and no result a tuning role receives carries one. `HOLDOUT_LOCKED` in a workflow's recorded tool results is the owner's signal that a tuning role reached for locked results.

**Model input scope.** As in M5, and additionally: bounded excerpts of approved public-source items, labeled untrusted; research declarations, hypotheses and the role's projection of experiment results; and typed artifacts in the workflow's scope. Never account, ledger, owner, pilot, evidence-pin or secret data, and never a holdout or shadow result for ANALYST or RESEARCHER. This stays true for generations 1 and 2; generation 3 adds the portfolio snapshot of the policy's own run for COORDINATOR and the intent reviewer only (M7-OD6, [below](#m7-tool-catalog-v3-approved-contract-execplan-0026)).

- **What the engine takes from a draft (B3, 2026-10-11).** B3 built the engine's side ahead of these tools. It reads the choices from the document's `choices` object only, with exactly the action's keys (`expiry_minutes`; for `ENTER` also `exposure_fraction` and `stop_multiple` as the policy's decimal text, and `max_hold_hours`; for `TIGHTEN_STOP` also `tightening`, the template, since B4), so `draft_trade_intent` (B5) must write them there. `submit_trade_intent`'s answer is the engine's `decision_events` row, whose kinds and codes [DATA_CONTRACTS](contracts/DATA_CONTRACTS.md#m7-agent-driven-decision-records-approved-contract-execplan-0026) lists. Neither writes a financial table: a handler writes `decision_…` rows and imports no broker, accounting or engine module, and the static import test keeps saying so. - **Probes.** The capability suite gains CP-21 and CP-22, which need no policy. The decision suite, CP-23 to CP-27, needs the approved policy and its running run. A probe never writes a submission or a pause request: the dispatcher records the code of its ordinary checks, then refuses the write because it is a probe's.

**What B5 built (2026-10-11).** The handlers are `app/agents/tools/decisions.py`; the FINISH handlers `app/agents/artifacts_v3.py`. A handler that refuses gives one of the codes below and writes nothing; the database guards of migration `0009` check the same bindings again, and the engine checks everything against current state.

- **`draft_trade_intent`.** The model supplies `action`, `symbol`, `position_id` (for `EXIT` and `TIGHTEN_STOP`), `expiry_minutes`, for `ENTER` `exposure_fraction` and `stop_multiple` (the policy's decimal text) and `max_hold_hours`, for `TIGHTEN_STOP` `tightening`, for `ENTER` `entry_basis` and `basis_ref`, and `cites`, `rationale`, `invalidation` and `uncertainty_level`.
