# Runtime agents, orchestration and Codex CLI

## Purpose and separation

This is an agent-driven application, not merely a daily classifier. Models can choose permitted next steps, request evidence/experiments, assess results and submit policy-bounded trade intents. The application executes their tools and independently validates side effects. [AUTONOMY_MATRIX.md](../AUTONOMY_MATRIX.md) and [AGENT_TOOL_CONTRACTS.md](AGENT_TOOL_CONTRACTS.md) are authoritative.

Codex or Claude Code builds the app in the development environment. Runtime Codex has a separate minimal home/config/work directory and no inherited repository AGENTS/CLAUDE instructions, development skills, hooks, MCP servers, account files or source checkout. Approved role prompt templates under `services/agent-runner/prompts/` are explicitly versioned runtime inputs; they are not auto-loaded developer instructions.

## Model roles

| Role | Primary work | Typed completion artifact |
|---|---|---|
| `ANALYST` | Investigate approved observations/events, seek missing evidence, state competing explanations and uncertainty | `MarketAssessment` |
| `RESEARCHER` | Form testable hypotheses, submit registered declarative candidates, request experiments, compare recorded results | `ResearchProposal` |
| `EVALUATOR` | Inspect evidence and exact draft artifacts in an independent context; challenge claims and report deficiencies | `EvaluationReview` |
| `COORDINATOR` | Choose actions under the main policy; request target exposure/position management; submit reviewed intents and promotion proposals | `PortfolioDecision` |

One initial concurrent **inference step** across roles is a local design choice, not a provider limit. The scheduler interleaves steps, gives financial safety its own non-model path, and avoids running every role on every tick. Role parallelism may be added only within measured resources and approved budgets. The same model across roles is not independent statistical confirmation.

## Default provider integration: application-brokered action loop

Use a `RecordedResponseProvider` for isolated tests and an authorized `CodexCliProvider` for private runtime inference. The project proposes the following loop around the documented `codex exec` structured-output interface [AI-02](contracts/REFERENCES.md#ai-02):

1. Orchestrator supplies the trusted role prompt, immutable job context, a bounded tool catalog and selected sanitized prior tool results.
2. Codex returns exactly one `AgentStep`: either `TOOL_REQUEST` with a named application tool and typed arguments, or `FINISH` with a role-specific artifact/abstention.
3. The application checks schema, role, task capability, as-of scope, budget, expiry and argument semantics. It dispatches only a registered handler, never a command string or generic URL.
4. Persist the result and append its bounded typed representation to the next step. A long job becomes `WAITING_TOOL`; no repeated model polling is needed.
5. Resume when the result is committed and the workflow remains valid. Stop at the approved step/deadline/budget limit, on cancellation or a valid finish.

This brokered loop is **our application protocol**, not a claim that `--output-schema` automatically supplies native function calling. Native CLI shell/browser/file tools remain disabled while application tools are available through the gateway. This replaces v1's blanket no-tool workflow without handing the model general machine access.

Optional later native Codex MCP transport can expose the same restricted contracts [AI-11](contracts/REFERENCES.md#ai-11). It is not required for v2, must not duplicate execution paths, and requires a compatibility/security decision. MCP allowlists alone do not replace server authorization. Do not install an orchestration SDK merely to obtain subscription access; provider access/billing is separately verified.

## Bounded step and job protocol

Server-owned context includes job/workflow/step IDs, parent and trigger IDs, role, account/experiment/mode, policy/research-envelope/tool-catalog versions, permission epoch, snapshot/input hash, evidence as-of cutoff, creation/deadline/expiry, model/prompt/schema versions, remaining budgets and allowed artifact IDs.

M6 research contexts and refresh completions obey the hypothesis cutoff for all source content, including follow-on assessment/question text and summaries. An event investigation may receive its own refresh through completion while other reads keep its fixed cutoff. Context construction applies the same provenance filter as artifact reads; cached or parent-authored text cannot bypass it. See [time-scoped completions](AGENT_TOOL_CONTRACTS.md#time-scoped-reads-and-typed-completions).

`AgentStep` uses a discriminated schema, rejects unknown fields and contains:
- echoed `schema_version`, `job_id`, `step_id` and `input_hash` for matching (never trusted as identity);
- exactly one `TOOL_REQUEST` with `tool_name`, request arguments and a bounded evidence-linked purpose, or `FINISH` with the expected artifact;
- no shell, SQL, source URL outside the source service, executable patch, self-assigned role, credentials or authoritative balance fields.

Separate immutable provider events, validated agent outputs and accepted domain artifacts. Parse the final schema object separately from CLI JSONL progress. Reject multiple objects, truncation, nonfinite/oversized values, unsupported versions and unknown references. A schema-conformant claim is still untrusted.

## Orchestration and finite states

Workflow states: `QUEUED`, `RUNNING`, `WAITING_TOOL`, `WAITING_REVIEW`, `SUCCEEDED`, `ABSTAINED`, `REJECTED_OUTPUT`, `EXPIRED`, `AUTH_REQUIRED`, `QUOTA_BLOCKED`, `FAILED`, `CANCELED`. Domain proposals/experiments have their own state machines; a successful model job does not mean an order filled.

The orchestrator may schedule an evaluator for an immutable draft or a researcher for a hypothesis, but never accepts arbitrary agent delegation graphs. Depth/step/concurrency/daily limits and repeated-request fingerprints prevent recursive work. Children inherit the template's data scope and cutoff. M5 children draw on the parent's deadline and budget; M6's fixed children have their own bounded budget, with model-running time separate from waits, as [ExecPlan 0023 §5.8](plans/0023-m6-research-investigations.md#58-agent-runtime-definitions-v2) specifies. Their role-specific grants are issued by the server from the approved workflow graph: an evaluator may receive its distinct review-write capability, never arbitrary privileges delegated by the parent model. A parent cannot choose extra tools or impersonate that child. Cancel/revoke cascades to children and makes late results unusable for new effects.

Before increasing main exposure, the pilot policy requires a completed evaluator review of the exact intent/evidence hash. `NEEDS_EVIDENCE` or `REJECT` blocks that draft; `ACCEPTABLE` is necessary but not sufficient. A revision needs a new review. Read-only analysis and research do not require a human per step. Early reduction/exit/stop tightening permitted by the existing mandate follows its declared review policy; deterministic protection never waits for a model.

## Memory and reproducibility

Persist evidence items, assessments, hypotheses, experiment IDs/results, reviewed intents, decisions and outcome links. Server-supplied account/market snapshots replace model recollection. Every note declares author role, creation/as-of time, source IDs, validity/expiry and whether it is observation, calculation or hypothesis. Outdated notes cannot silently become current facts.

Use bounded curated retrieval, not the full historical transcript. Keep decision explanations concise; do not request/store hidden chain-of-thought. Evaluator input prioritizes source records and deterministic results over researcher marketing language. Provider-generated text is not primary data. Record visible model/version settings; when backend model revision is not exposed, state that limit and segment observed behavior changes.

Financial replay uses recorded accepted outputs/tool results/observations. Calling today's model again is a new run, even with the same prompt and seed. Historical model contamination remains a disclosed limitation; forward observations are primary AI evidence.

## Authentication and capacity

OpenAI documents Codex ChatGPT authentication and a device-login route, subject to account/environment availability [AI-01](contracts/REFERENCES.md#ai-01). Owner setup may use `codex login --device-auth` after checking current support. This pack has not logged into the user's account.

Saved authentication can support trusted automation; the documented advanced route requires protecting refreshable auth state, while API keys remain the vendor's default recommendation for automation [AI-02](contracts/REFERENCES.md#ai-02). This project chooses a private local subscription prototype. It has no promise of continuous capacity. Never transfer auth into public CI or untrusted repository code.

Keep auth in a narrowly mounted writable private store; serialize refresh when needed. No tokens in Git, build layers, prompts, artifacts or logs. A static read-only secret does not replace state requiring refresh. No cookie scraping, quota bypass, automatic API purchasing, or inferred reset time. No paid fallback is implemented. Quota exhaustion can prevent autonomous decisions even though the app remains running.

## Process and capability isolation

Invoke CLI with an argv array and stdin, never shell interpolation. Stage bounded schemas/prompts in a job-only directory. Enforce process-tree cancellation, deadlines, stdout/stderr limits, minimal environment and resource limits. Only the runner has model auth; research tools do not inherit it.

At M5 verify actual CLI/help/effective configuration and complete native tool inventory. Official configuration documents controls including shell/unified exec, web search, forced login method and history/verbosity [AI-07](contracts/REFERENCES.md#ai-07); verify exact keys and behavior before writing config. Do not assume disabling one shell feature disables file-read, patch, delegation or plugin paths. Reject unexpected native tool events. Never grant unrestricted mode to fix a failing sandbox.

The approved **native capability set is empty** for the default brokered transport; the approved **application tool set is role-scoped and nonempty**. Read-only sandboxing is insufficient if a tool can read auth files. Test that injected content cannot access files, spawn processes, use native web search, install skills/plugins, invoke inherited MCP, read environment secrets or modify code. Failure to demonstrate isolation blocks subscription runtime activation, not recorded testing or the financial foundation.

Provider egress required by Codex is distinct from arbitrary model browsing. Keep role tools on the engine side; the runner sees sanitized results. Do not give the runner DB, Docker socket, code mounts or owner-control tokens. OS/network isolation and capability checks are defense in depth, not a universal security guarantee [AI-12](contracts/REFERENCES.md#ai-12).

## Failure behavior

A failed/expired model step cannot open an AI-dependent position. A permitted deterministic fallback requires its own approved policy and evaluation; never silently substitute one. Protection continues in code when current observations and the running engine permit it. Disconnecting or exhausting the model does not erase obligations.

Tool failures return safe typed errors. Invalid/forbidden requests consume the configured retry/work budget; repeated attempts cannot route through another role or reveal limits to bypass. Unknown financial commits are reconciled by intent/order IDs. Tool timeout is not proof of no side effect. Provider auth/quota blocks pause relevant work until actual recovery; automatic clearing of a transient availability block never clears a latched risk/owner pause.

## Verification

Required evidence includes actual login persistence, native-tool isolation, end-to-end application tools, bounded role handoffs, malformed/stale input rejection, auth/quota UI, replay, cancellation/revocation, unknown-commit recovery, no cross-account writes and no paid fallback. Use [ACCEPTANCE_CHECKLIST.md](../ACCEPTANCE_CHECKLIST.md). No provider call or application test was run while preparing this pack.

## Recorded-provider restriction

Recorded responses are for OFFLINE_TEST, controlled HISTORICAL_RESEARCH and explicitly labeled replay/fixture checks. They may not impersonate fresh model decisions in a new FORWARD_PAPER or live SHADOW agent workflow. Without configured live inference, that capability remains unavailable; a separately approved fixed non-AI policy may still run. Never recycle a favorable recorded answer against current observations.

## M5 runtime (ExecPlan 0020)

[ExecPlan 0020](plans/0020-m5-agent-runtime.md) implements the first slice of this contract. Its §15 records what is implemented and verified. M5 adds **no financial, approval or trading authority**.

**Providers.** One `Provider` interface with two implementations:
- `RecordedProvider`: serves stored AgentStep outputs. The mode guard allows it only for `OFFLINE_TEST` workflows in `asl_m1_` databases.
- `CodexProvider`: calls the isolated `agent-runner` over the internal `agent_control` network. In isolated tests the runner may wrap a fake CLI or the real pinned binary against a mock Responses provider; both are `OFFLINE_TEST` only.

**Workflows.** The registered template `MARKET_ASSESSMENT_V1` runs one ANALYST workflow. On a valid FINISH, the orchestrator itself creates one fixed EVALUATOR child, `ASSESSMENT_REVIEW_V1`, bound to the assessment's exact hash. The child draws on its parent's budget, and there is no model-chosen delegation. Probe workflows (`PROBE`) exist only for the capability probes. COORDINATOR and RESEARCHER have code-owned grants (read tools only) so denial tests can run; they have no template or prompt in the M5 profile.

**AgentStep.** The output schema is one strict-compatible JSON object with these fields: `schema_version`, `job_id`, `step_id`, `input_hash`, `kind` (`TOOL_REQUEST` or `FINISH`), `tool_request` and `finish` (exactly one non-null).
- The engine parses the final object strictly: exactly one JSON value, no duplicate keys, no NaN or Infinity, no trailing data, and a size limit.
- It then re-validates the object with Pydantic, forbidding unknown fields.
- Echoed identifiers must match the server's context, but they are used for matching only. The role, workflow, grants and cutoff always come from server state.
- The concrete schemas are in [AGENT_TOOL_CONTRACTS](AGENT_TOOL_CONTRACTS.md#m5-tool-catalog-v1-execplan-0020).

**Durable records.** Workflows, capability grants, steps, provider calls and outcomes, tool calls and results, artifacts and prompt blobs live in agent tables ([DATA_CONTRACTS](contracts/DATA_CONTRACTS.md#m5-agent-runtime-records-execplan-0020)). Provider calls, tool calls, artifacts and events are immutable. A step has exactly one terminal outcome. A provider call carries a durable call key: after a crash or a lost lease, the worker asks the runner about that same key and never sends a second call for it.

**Authority checks.** One orchestrator lease with a fencing epoch applies (2 s renewal, 7 s stop rule). The owner's permission epoch lives in its own row, and every agent commit takes `FOR KEY SHARE` on it. The worker checks the following before the runner call, when it accepts a result, before a dispatch, and inside the tool-result and FINISH commits:
- the runtime state allows this work;
- the epoch is unchanged;
- the profile is still approved;
- the capability record is VERIFIED (or PROBE_ONLY for probes);
- the workflow is open;
- the deadline has not passed;
- the budget is reserved.

A result that arrives after any of these changes is stored as `late` and never dispatches or creates an artifact.

**Runtime states.** The states are `DISABLED` → `LOGIN_REQUIRED` → `PROBE_ONLY` → `ENABLED`, with the orthogonal blocks `AUTH_REQUIRED`, `QUOTA_BLOCKED` and `CAPABILITY_LATCHED`.
- Owner DISABLE is immediate: the API increments the permission epoch in the same transaction.
- ENABLE is only an owner UI action, bound to the approved runtime-profile hash and a VERIFIED capability record. The worker re-checks both before applying it. Since M8 update 1 ENABLE needs only the approved profile: without a matching verification the worker applies it as `PROBE_ONLY` and the agents' check enables the runtime when it passes ([M8 runtime](#m8-runtime-the-agents-check-the-usage-limit-and-one-switch-execplan-0031)).
- A change to the binary digest, config hash, account-id hash or inventory hash returns the runtime to `PROBE_ONLY`.
- Blocks affect only new model work. Nothing else in the application depends on the model.

**Budgets.** Budget values come from the approved runtime profile. The proposals are:
- step deadline 120 s and workflow deadline 20 minutes;
- 8 model steps and 6 tool calls per workflow;
- handoff depth 1 and a 64 KiB prompt;
- 12 parent workflows per UTC day;
- a probe budget of at most 40 live calls;
- queued requests expire after 10 minutes.

`REJECTED_OUTPUT` gets one retry, which consumes budget. Exhaustion ends as `ABSTAINED` with `BUDGET_EXHAUSTED`. One inference slot is shared by all roles. No new model step starts between HH:59:30 and HH:06:00 UTC, which keeps clear of the pilot's hourly and snapshot work.

**Prompt size bound.** The job context lists prior tool results newest first. When a prompt would exceed its bound, the oldest results give way first, so the result a step has just asked for is the last to go:
- A hidden result keeps its reference, tool name and status. Only its data is replaced, by `{"omitted": "PROMPT_BUDGET"}`.
- `input_hash` is the hash of the context actually shown.
- An M5 workflow whose prompt does not fit with every result hidden ends as `ABSTAINED` with `BUDGET_EXHAUSTED:PROMPT`.
- Both generations use this order. Until 2026-10-05 generation 1 hid the newest result first; the owner approved the correction ([DECISIONS](../DECISIONS.md#2026-10-05--generation-1-prompt-trimming-drops-the-oldest-result-first)).

**Runner isolation.** The runner holds the only copy of Codex auth, in the `codex_home` volume. It has no database, repository, Docker socket or owner credential. Each job gets:
- a pristine `CODEX_HOME` in tmpfs, containing only a copy of `auth.json`;
- an empty working directory;
- a fixed argv and configuration baked into the image and reported as `config_hash` (since [ExecPlan 0046](#m11-generation-11-leaner-agents-execplan-0046) also the runner's own base instructions file and its hash);
- a minimal environment, with `HTTPS_PROXY` pointing at the `agent-egress` gateway.

The job is killed on the first JSONL item other than `agent_message` or `error`, and on any child process. Refreshed auth is copied back by compare-and-swap under a file lock, and never after a violation. The native capability set stays **empty**; §"Process and capability isolation" above is unchanged. Offline evidence comes from the pinned binary's inventory and a mock Responses provider. Live evidence comes from the owner-started M5-B probes CP-01 to CP-14.

**Allowed models (M5-OD1, [owner decision 2026-09-30](../DECISIONS.md#2026-09-30--m5-od1-resolved-code-mode-only-models-execplan-0020-b3)).**
- Only a model whose authenticated catalog entry is `tool_mode: code_mode_only` can be put in a runtime profile.
- The pinned Codex offers `apply_patch` to other models, and configuration cannot remove it. For `code_mode_only` models, Codex offers no tool at all: the baked `features.code_mode_host=false` (and the host binary's absence from the image) makes Code Mode fail closed.
- Profile composition refuses any other model with `MODEL_EXPOSES_NATIVE_TOOLS`.
- A newer discovery whose catalog or native-tool inventory differs from the approved profile invalidates the capability record and returns `ENABLED` to `PROBE_ONLY`.

## M6 runtime: definitions v2, workflows and waiting (ExecPlan 0023)

B6 of [ExecPlan 0023](plans/0023-m6-research-investigations.md) adds a second definition generation beside M5's. It is IMPLEMENTED and VERIFIED offline only: scripted and recorded providers, the pinned CLI against the loopback mock for the schema, synthetic fixtures. No model call was made; probes CP-01 to CP-20 against a real model are NOT RUN and are an owner action in M6-B. M6 adds **no financial, approval or trading authority**.

**Generations.** A workflow belongs to the generation of its template, read from the stored row.
- Generation 1: `MARKET_ASSESSMENT_V1` and `ASSESSMENT_REVIEW_V1`, exactly as M5 accepted them.
- Generation 2: the five templates below, under catalog v2, role grants v2, AgentStep schema v2 and budgets v2 ([AGENT_TOOL_CONTRACTS](AGENT_TOOL_CONTRACTS.md#m6-tool-catalog-v2-execplan-0023)).
- Definitions are append-only rows. Migration 0008 seeds the v2 rows beside the v1 rows; the worker refuses to start if the code and the stored rows of either generation differ.
- The runtime profile (version 2) binds the hashes of both generations and `budgets_v2`. The M5-approved profile therefore no longer matches after deployment. The worker removes it from the runtime state at its first pass (`LOGIN_REQUIRED`), and nothing runs until the owner approves a new profile and a probe run passes.

**Workflow graph (code-owned).** A model never names a template, a child, a role or a delegation.

| Template | Role | Started by | Then |
|---|---|---|---|
| `EVENT_INVESTIGATION_V1` | ANALYST | Owner; a `SOURCE_REVISION` trigger | A recorded assessment creates the fixed child `ASSESSMENT_REVIEW_V2`. If the assessment names a research question and the review is not `REJECT`, one `FOLLOW_ON` trigger is recorded |
| `ASSESSMENT_REVIEW_V2` | EVALUATOR | Orchestrator | A review bound to the assessment's exact hash |
| `RESEARCH_V1` | RESEARCHER | Owner; the schedule; a `FOLLOW_ON` trigger | A proposal that nominates a candidate leaves the workflow `WAITING_REVIEW`. SYSTEM queues the full test once; when its result is recorded the orchestrator creates the fixed child `CANDIDATE_REVIEW_V1` |
| `CANDIDATE_REVIEW_V1` | EVALUATOR | Orchestrator | A review bound to the proposal's hash and to the hashes of the candidate's screening and full-test results |
| `PROMOTION_V1` | COORDINATOR | Owner; SYSTEM when a candidate becomes `EVIDENCE_READY` | One `PENDING` promotion, or an abstention. Nothing approves it in M6 |

- **The full test.** Only the research identity (`asl_research`, the bridge) may queue a `FULL` job; the agent worker, which executes the model's requests, cannot. The bridge queues it once for a nominated candidate, and once more if the first evaluation ended `FAILED` or `EXPIRED`. If it never produces a valid result, the parent ends `SUCCEEDED` with `review_status = UNAVAILABLE` and the reason; no review is created and the candidate stays `TESTED`.
- **Storage for a screening job.** The agent worker cannot see the research cluster. The bridge records each store's allocated and free bytes once an hour; `request_experiment` reserves against the latest record and refuses with `RESEARCH_UNAVAILABLE` when none is younger than 2 h 10 min.

**Cutoff.** Fixed when a workflow starts and immutable afterwards (the database refuses a change).
- `EVENT_INVESTIGATION_V1`, `CANDIDATE_REVIEW_V1` and `PROMOTION_V1`: the start time, taken so that no evidence still uncommitted at that moment can precede it.
- `ASSESSMENT_REVIEW_V2`: its parent's cutoff, plus the items the parent's own refresh delivered.
- `RESEARCH_V1`: the holdout start of the newest sealed research dataset, which is bound to the workflow with its hash. Without an approved envelope, a sealed dataset or its store, the workflow ends `FAILED` (`ENVELOPE_UNAPPROVED`, `NO_DATASET`, `STORE_UNAVAILABLE`) before any model step.
- A follow-on research workflow is shown the question that caused it only if the assessment's recorded provenance is at or before the research cutoff. An investigation runs at the present and research at an earlier holdout start, so in practice the question text is withheld and the researcher receives only the symbols.

**Waiting.** A call with a queue effect returns `ACCEPTED`, moves the workflow to `WAITING_TOOL` and releases the inference slot in one transaction. The unused running time is kept; the workflow's deadline becomes the wait deadline. One completion row per call resumes it exactly once ([AGENT_TOOL_CONTRACTS](AGENT_TOOL_CONTRACTS.md#m6-tool-catalog-v2-execplan-0023)); the running deadline then continues from what was left. A wait that outlasts its deadline ends the workflow `EXPIRED` with `WAIT_DEADLINE`; the job's result, if it arrives, is history and stays readable by a later workflow.

**Budgets v2 (PROPOSED values, bound by the profile hash).**
- A parent: 12 model steps, 10 tool calls and at most 3 experiments. A child has its own 4 steps and 3 tool calls.
- Step deadline 120 s. Running deadline 20 minutes for a parent and 10 minutes for a child; wait deadline 6 h.
- 24 parent workflows per UTC day. The count covers parents of both generations and no probes; a workflow is held to its own generation's cap, so an M5 assessment is refused once 12 parents of any kind have started that day. The scheduler also counts queued parents before it adds one.
- A queued owner request expires after 10 minutes; a workflow queued by the scheduler or the orchestrator after 6 h; a trigger older than 6 h is refused as `STALE`.
- A probe run may make at most 60 live calls (20 probes). This value is this batch's proposal and has not been measured.
- Exhaustion ends as `ABSTAINED` with `BUDGET_EXHAUSTED`, as in M5.

**Priority (code-owned).** With one inference slot, the next step goes to: probes; then workflows whose root was started by the owner; then promotion; then investigations and assessments; then research. The class is computed from stored rows. Within a class the M5 order holds.

**Scheduler.** Every 15 s, under the orchestrator lease, the worker turns recorded triggers into workflows. A trigger is a record; only this code starts work from one.
- `SOURCE_REVISION` starts `EVENT_INVESTIGATION_V1` for the trigger's symbol with a 24 h horizon. One open investigation per source and symbol: a second trigger is refused as `INVESTIGATION_OPEN`.
- `FOLLOW_ON` starts `RESEARCH_V1`.
- `SCHEDULED_RESEARCH`: one per newly sealed dataset, at most one per UTC day, only while the runtime is `ENABLED` and the envelope is approved.
- SYSTEM starts one `PROMOTION_V1` for each candidate that became `EVIDENCE_READY`.
- A trigger whose source is no longer approved is `CANCELED`; with the runtime `DISABLED` it is `CANCELED`; while the runtime is not enabled or is blocked it stays queued until it is stale; over the daily budget it is refused.

**Owner decisions on promotions (B7).** Every tick, under the orchestrator lease, the worker applies an owner's rejection of a pending promotion: the promotion becomes `REJECTED` and its candidate `REJECTED`, with the owner's approval record as gate evidence ([RESEARCH_WORKFLOWS](RESEARCH_WORKFLOWS.md#b7-implementation-boundary-execplan-0023)). This is SYSTEM code, not a model step: it needs no runtime state, profile or permission epoch, so it also runs while the runtime is `DISABLED`, and its failure does not stop the step loop. It is applied once, and nothing in it or elsewhere approves a promotion.

**Owner-started generation-2 workflows (B7).** The owner may queue `EVENT_INVESTIGATION_V1`, `RESEARCH_V1` and `PROMOTION_V1` through the API, each with the parameters its template registers. Such a row is `QUEUED` without an epoch or a cutoff; the worker binds both when it starts the workflow and checks the template's start conditions again (the approved envelope and a sealed dataset for research). It expires after ten minutes if it does not start, as an M5 assessment does. The owner read models show each workflow under the budget of its own generation.

**Prompts.** `services/agent-runner/prompts/m6/`: `analyst.v2.md`, `researcher.v1.md`, `evaluator.v2.md`, `coordinator.v1.md`. Each is versioned, hashed into a definition row and packaged into the engine image like the M5 prompts. A prompt names only tools its role is granted. A prompt is a template, not a permission.

**Probes CP-15 to CP-20.** They run in the same run as CP-01 to CP-14, as generation-2 `PROBE` workflows, and are judged from recorded rows: an unregistered source (CP-15), an unregistered operator (CP-16), a holdout request by the researcher (CP-17), a read past the information cutoff (CP-18), a promotion without evidence (CP-19) and one positive chain (CP-20). The research probes need an approved envelope and a sealed dataset; without them the run fails with that reason. Offline they are VERIFIED with scripted models; live they are NOT RUN.

**Rules added after the independent review of 2026-10-05** ([ExecPlan 0023 §18](plans/0023-m6-research-investigations.md#18-completion-evidence)):

- **A profile must bind the code's definitions.** A stored profile is current only if its version and every definition hash of both generations (schema, catalog, grants, templates, budgets, prompts) are the code's and it carries `budgets_v2`. An approval of any other document, such as the M5 profile, authorizes nothing:
  - a Probe or Enable request that names it is rejected with `PROFILE_MISMATCH`;
  - a runtime state still bound to it is moved to `LOGIN_REQUIRED` with reason `PROFILE_DEFINITIONS_CHANGED` at the worker's next pass, with a `PROFILE_DRIFT` event;
  - no model step and no scheduler start is permitted under it, and the owner view offers no Probe or Enable for it.
- **Queued work carries its permission epoch.** A workflow the scheduler queues is stamped with the epoch of that moment. An owner Disable or a revocation that follows cancels it before it starts (`CANCELED`, `CAPABILITY_REVOKED`); it does not start after a later Enable. The scheduler also reads the runtime state inside its own transaction.
- **Running time is counted while a workflow can be served.** With one slot and waits, several workflows can be `RUNNING` at once. While another workflow's step holds the slot, each displaced workflow's running deadline moves by that time. Priority stays as above: a higher class is served first, and a lower one does not expire unserved for it.
- **The full test needs a parent with authority.** The bridge queues it only for a parent that waits under the current permission epoch and has more than five minutes of wait left. If the one retry is refused for a reason that cannot change (both attempts used by a lost runner, a changed code identity, a dropped store), the parent ends `SUCCEEDED` with `review_status = UNAVAILABLE` at once instead of at its wait deadline.
- **One failing item does not stop the rest.** A completion, a review advance or a trigger that raises is logged and left for the next pass (a malformed trigger is refused as `TRIGGER_INVALID`); the other items and the model steps go on. Completions and review advances are selected by "the awaited work has ended" before any limit, so requests that never end cannot hide finished ones.
- **A store is kept for an open research workflow** bound to one of its datasets, also between that workflow's jobs.
- **Not changed:** a failure while a model step's own result is committed is retried at every tick until that workflow's running deadline (at most 20 minutes) and holds the slot meanwhile. The known cause, a string PostgreSQL cannot store, is now rejected before that point.

## M7 runtime: generation 3, decisions and their triggers (ExecPlan 0026)

B5 of [ExecPlan 0026](plans/0026-m7-agent-driven-main-decisions.md) adds a third definition generation. It is IMPLEMENTED and tested offline only, with scripted and recorded providers and synthetic fixtures on scratch PostgreSQL 16 ([plan §18, B5](plans/0026-m7-agent-driven-main-decisions.md#b5--generation-3-the-decision-loop-its-triggers-and-both-probe-suites-2026-10-11)). No model call was made. CP-21 to CP-27 against a real model are owner actions in M7-B. The agents gain **no financial authority of their own**: a submission is a row the execution engine checks again in its fenced step ([AGENT_TOOL_CONTRACTS](AGENT_TOOL_CONTRACTS.md#m7-tool-catalog-v3-approved-contract-execplan-0026)).

**Generations.** Generation 3 holds five templates under catalog v3, role grants v3, AgentStep schema v3, templates v3 and budgets v3, with the prompts `services/agent-runner/prompts/m7/` (`analyst.v3.md`, `evaluator.v3.md`, `coordinator.v2.md`). The runtime profile is version 3: it binds every hash of the three generations, budgets under `budgets`, `budgets_v2` and `budgets_v3`, a data scope per generation and a consequence text that names the decision authority. The owner's decision names nothing: the server writes the universe of the policy its run trades, and the API refuses the start for the reasons the worker would.

**Promotions under generation 3 (B6, 2026-10-12).** Before the policy is installed, SYSTEM starts `PROMOTION_V1` as in M6. Once it is, SYSTEM starts `PROMOTION_V2` instead (at most four a pass, within the daily parents of generations 1 and 2, which promotion work has always counted against), and none for a candidate whose ATR period, stop multiple or hold lies outside the policy's sets. The owner's approval, rejection or revocation is recorded through `/v1/agent-approvals`; the worker applies the latest record each pass: `APPROVED` and `MAIN_APPROVED`, `REJECTED`, or `REVOKED` and `SUSPENDED` (the epoch rose when the revocation was recorded). An approval whose candidate left `MAIN_APPROVAL_PENDING` in the meantime is `WITHDRAWN` and grants nothing, and cannot be revoked. A pending `PROMOTION_V1` the owner has rejected is not superseded: SYSTEM applies the rejection first. A decision's start then puts up to four approved candidates into its snapshot and scope ([AGENT_TOOL_CONTRACTS](AGENT_TOOL_CONTRACTS.md#m7-tool-catalog-v3-approved-contract-execplan-0026)); a probe's start puts none.

**A decision's start.** The worker binds, once, into the workflow's cutoff: the operating policy's live run; the policy, which must be installed, bind this build's generation-3 hashes, be approved by the owner, and have its run `RUNNING`; a `VERIFIED` decision suite for the approved profile and that policy (since M8 update 1: a passing agents' check, or something the run can exit, [M8 runtime](#m8-runtime-the-agents-check-the-usage-limit-and-one-switch-execplan-0031)); the snapshot, stored in `decision_snapshots` with its hash and state key; the latest finalized bar of each symbol; and the scope the decision may cite (the newest reviewed brief of each symbol within the policy's age and the brief's own expiry, and the four newest outcome reviews of the run's own positions). A start that cannot bind ends the workflow `FAILED` with the reason (`POLICY_RUN_NOT_LIVE`, `POLICY_UNAPPROVED`, `POLICY_RUN_NOT_RUNNING`, `DECISION_SUITE_NOT_VERIFIED`, `SNAPSHOT_TOO_LARGE`, …) and stores no snapshot. The intent review takes its parent's cutoff and binding.

**What a decision is shown** (the job context's `decision` block): the policy's sets and limits, the stored snapshot (at most 8 KiB: older history is dropped and labeled, never the state; otherwise the start fails), the decision bars, the briefs and outcome reviews in scope (labeled model-authored), and its drafts with what became of each. The snapshot shows account values only while the run is live, each position with its mandate stop and the stop in force, open orders, pauses, blockers, the action limits used, the last eight drafts of the run's decisions (not a probe's) and the last four outcome records. It does not show risk headroom (`RISK_HEADROOM_NOT_SHOWN`); the engine computes it at the submission.

**Waiting.** `request_review` and `submit_trade_intent` return `ACCEPTED` and the decision waits in `WAITING_TOOL`, each for one completion: the review child's end, or the engine's `decision_events` row. A review wait lasts at most the queue time plus the review's running time plus 60 s; an answer wait lasts until the draft's expiry plus 60 s. Each is also capped at 5,040 s; with at most two reviews and two submissions the waits add up to 5,040 s at most by construction, and no check adds them up.

**Ending.** A decision that ends `CANCELED`, `EXPIRED` or `FAILED` (an owner cancel, a deadline, a revocation, a latch) writes a `decision_withdrawals` row, in the transaction that ends it, for each of its submissions the engine has not answered and for each entry the engine accepted that has no fill: the engine then cancels its order or ends its waiting signal (`WITHDRAWN`). A refusal, an exit, a cancellation or a tightening the engine answered, and an entry that has filled, are final and are not withdrawn. A decision that ends `SUCCEEDED` withdraws nothing. Apart from any decision's end, each worker pass withdraws an entry on a candidate (B6) once the candidate has left `MAIN_APPROVED`, whatever its decision's state, if the engine has not answered it or accepted it without a fill (reason `UNAPPROVED`): a research suspension raises no epoch, and the engine reads no research table. A decision that has not submitted ends `EXPIRED` with `BAR_SUPERSEDED` once a newer bar finalizes for one of its symbols.

**Triggers** (from the `agent_read` views, every scheduler pass while the runtime is enabled and the policy's run is live):
- `BAR_CLOSE` once per bar while a position or an entry of the run is open; the bar is the newest one finalized for every symbol.
- `POSITION_EVENT` once per entry fill and once per position end.
- `ASSESSMENT_READY` once per reviewed assessment (above).
- An event older than 24 hours is not written. Staleness is judged from the event's own time: 20 minutes for `BAR_CLOSE`, 30 for the others; a stale trigger is `REFUSED` `STALE` and starts nothing.
- Of the waiting triggers of the run, the one of the newest event is kept and stands for the others: when its decision starts, each other is `REFUSED` `SUPERSEDED`, naming it; until then all wait, and a position event among them exempts the start from the cooldown. With the runtime `DISABLED` they are `CANCELED`; while it is not enabled or is blocked they wait.
- One open decision at a time; at least 10 minutes between two starts except after a position event; at most 36 decisions a UTC day (queued ones counted; past the cap the waiting triggers are `REFUSED` `DAILY_BUDGET_EXHAUSTED`). A trigger for another run is `REFUSED` `ANOTHER_RUN`; under a policy that is not ready every waiting trigger is refused with the reason.
- A decision queued from a trigger leaves the queue when its trigger would have become stale.

**Outcomes.** For each closed position of a policy run the worker stores one outcome record with its hash, built from the financial views only, and SYSTEM queues one `OUTCOME_REVIEW_V1` (at most 8 a day). The record names the intent and its review, the risk decision, each order and fill with fees and cost scenario, the realized result, the mandate's stop and unit risk, and how and when the position ended.

**Budgets v3 (PROPOSED values, bound by the profile hash).** Each template has its own: a brief 8 steps, 6 tool calls, 1,200 s; a brief's review 4, 3, 600 s; a decision 10, 8, 900 s, two drafts and two submissions; an intent review 4, 3, 300 s; an outcome review 4, 3, 600 s; an entry-basis promotion request 12, 10, 1,200 s (B6). A UTC day: 36 decisions, 4 briefs and 8 outcome reviews, counted apart from the 24 parents of generations 1 and 2. The capability run may make 70 live calls; the decision run 40 (the plan proposed 25; scripted, the five probes and the chain's brief took 26 in the offline suite, [plan §17, B5](plans/0026-m7-agent-driven-main-decisions.md#17-decision-log)).

**Priority (code-owned).** Probes; owner-started work; decisions and their reviews; promotion; briefs, investigations and assessments; research and outcome reviews.

**Probes.**
- **CP-21 and CP-22** run in the capability run, need no policy and write no decision row. CP-21 is a decision that reads the `PORTFOLIO` view and ends with a valid abstention; without a live policy run its snapshot is the empty one with a fixed state key. CP-22 is an analyst's brief that asks for the portfolio view and for `draft_trade_intent`; both must be refused.
- **The decision suite** is a second owner-started run (`agent_runtime_requests.kind` `DECISION_PROBE`; `agent_probe_runs.suite` `DECISION` with the policy's ID and hash). It needs `PROBE_ONLY` or `ENABLED`, the approved profile, no latch and no other probe run, and the operating policy as a decision's start needs it; it raises no epoch. It starts with CP-27's brief and its review, then queues CP-23 to CP-27 as decisions of purpose `PROBE`: a value outside a set, a price in the rationale, a submission without a review, a review of another draft, and the positive chain (a draft on the brief and its review, whatever the verdicts). A probe never writes a submission or a pause request (`PROBE_REFUSED` after every ordinary check). The result is one `decision_verifications` row for the profile and the policy together; it is never written into the capability record and never changes the latch. A run that is canceled (the runtime disabled or latched, another profile approved) records `FAILED`.

## M8 runtime: the agents' check, the usage limit and one switch (ExecPlan 0031)

Update 1 of [ExecPlan 0031](plans/0031-m8-simple-app-that-runs-itself.md#9-implementation-sequence) (§4.7, and [ExecPlan 0030 §4.5](plans/0030-agent-models-and-effort-per-role.md#45-the-usage-limit-block)). IMPLEMENTED and tested offline on scratch PostgreSQL 16 with scripted providers; on the owner's PC from its first update on. No hashed definition changes: the catalog, grants, templates, budgets (the capability run's 70 calls and the decision run's 40 among them) and prompts are those of M7, so the approved profile stays approved.

**One switch.** The owner's Enable is the on side of the switch, and needs only the approved profile. Without a verification that matches the runner, the worker applies it as `PROBE_ONLY` with reason `CHECK_PENDING` (the request's outcome names `state` and `requested`), and the agents' check moves the runtime to `ENABLED` when it passes. Disable is unchanged. An owner's Enable with target `PROBE_ONLY` holds the runtime there (`OWNER_ENABLE_PROBE_ONLY`): the check runs but does not enable.

**The agents' check** (`app.agents.check`, actor `SYSTEM`). A probe run with suite `CHECK` (migration `0010`) and a budget of 12 calls, about seven used: `SC-02` first, a decision that reads the `PORTFOLIO` view and holds or abstains for each symbol (CP-21's case, no draft, submission or pause), then `SC-01`, an analyst's brief and the evaluator's review of it (CP-27's chain brief). Each is judged technically from recorded rows, as the probes are; `SC-01`'s assessment may cite only what the tools returned, counted as the brief's own finish counts it (each result's and completion's reference and the IDs its envelope made citable, such as the releases a search found). The researcher has no case: research needs an approved envelope and a sealed dataset, and does not trade. The worker starts it when the runtime is `PROBE_ONLY` or `ENABLED` on an approved, current profile, the login is present, the runner is the real one and matches the profile, no probe run is open, and one of these holds:
- `SWITCH_ON`: the runtime is `PROBE_ONLY` and not held there by the owner (a switch-on, drift, a violation, an old latch);
- `ENTRIES_WAIT`: it is `ENABLED`, a policy is ready, and that policy's entries are not open;
- `USAGE_LIMIT_RETRY`: the usage limit blocks model calls and its retry is due.

No check starts within 5 minutes of the last; after failures the next waits 15 minutes, doubling up to 6 hours. A pass records a `VERIFIED` capability verification (the runner's identity and the profile) and, when a policy was bound, a `VERIFIED` decision verification; it clears an old latch and turns `PROBE_ONLY` into `ENABLED` unless the owner holds it there. A failure records a `FAILED` decision verification when a policy was bound, and nothing else: no latch, no state change, and the next check comes by itself. The check runs while an old latch or the usage-limit block stands, since it is how both end. The newest check and each of its cases' results show in Settings' Agents section (on the Agents page until [ExecPlan 0035](plans/0035-a-simpler-app-that-trades-by-itself.md)).

**Entries wait, exits never do.** A policy's entries are open when the newest check (or decision suite) for the approved profile and that policy passed and no runner violation came after it. Until then a decision starts only while its run has a live position or an open entry order (otherwise `CHECK_PENDING`), and `draft_trade_intent` and `submit_trade_intent` refuse an `ENTER` with `POLICY_PAUSED`. Exits, cancels and stop tightening never wait for the check while the runtime is `ENABLED`; while it is `PROBE_ONLY` (a switch-on without a verification, a runner change, a violation) no decision runs until the check passes, and the engine's own stops, which never depend on the model, protect the positions. The refusal `DECISION_SUITE_NOT_VERIFIED` is gone.

**No latch.** A runner violation fails its own workflow (`CAPABILITY_VIOLATION`) and every open decision (`CAPABILITY_VIOLATION_ELSEWHERE`), so that what those submitted and the engine has not finished with, an accepted entry without a fill among it, is withdrawn at once, as the M7 latch withdrew it. Other work stays queued. An `ENABLED` runtime returns to `PROBE_ONLY` (a `STATE_CHANGED` event whose detail names the call), and the check runs again before decisions resume and entries reopen. A failed capability or decision probe run latches nothing. The capability run (70 calls) and the decision run (40 calls) stay as an on-request diagnostic through their API routes; the page has no buttons for them.

**The usage limit** (`app.agents.usage`). A call the provider refuses for the usage limit (the runner's `QUOTA_BLOCKED` class, or its candidate where the class reads `PROVIDER_UNAVAILABLE`) ends its workflow `QUOTA_BLOCKED`, sets the runtime's `quota_state` to `BLOCKED` and records `QUOTA_BLOCKED` with actor `SYSTEM`. Nothing latches and no retry is spent. While it stands no model step starts except the check, whose run is canceled with reason `USAGE_LIMIT` at the refusal and retried 10 minutes after the first refusal, doubling up to 2 hours. The first completed call clears it (`QUOTA_CLEARED`). The runner's two usage-limit patterns are marked verified by observation: on the owner's PC (2026-10-19, read-only) every one of the 50 failed calls between 08:26 and 12:06 UTC, while the plan's limit was reached, was stored with this candidate, and none without it. The runner now keeps up to five of the failure's own messages (500 characters each) so a later refusal can be read. Since [ExecPlan 0054](plans/0054-the-scorer-expects-the-schedule-and-a-second-usage-signal.md) the runner's Codex reading (every 10 minutes while Codex runs the agents) is a second signal: a good reading whose main snapshot names a reached limit, or that says ordinary usage is not allowed, sets the same block once (`QUOTA_BLOCKED` with `source` `CODEX_APP_SERVER`, its `reason` and the reading's id), never over a block that stands; the check retries and clears it as after a refusal. A completed call that cleared a reading's block contradicts the reading: readings set no block again until a later good reading names no reached limit, so a reading that says "reached" while calls work holds the agents back at most once, for the check's 10 minutes (the reading's meaning while the limit holds is `NOT VERIFIED`).

## M8 runtime: in-force records, the model table and pauses that end (ExecPlan 0031)

Update 2 of [ExecPlan 0031](plans/0031-m8-simple-app-that-runs-itself.md#9-implementation-sequence) (§4.2, §4.5, and [ExecPlan 0030 §4.1 and §4.2](plans/0030-agent-models-and-effort-per-role.md)). IMPLEMENTED and tested offline on scratch PostgreSQL 16 with scripted providers; on the owner's PC from its second update on. Migration `0011` is additive.

**In-force records** (`app.agents.in_force`, actor `SYSTEM`). Once per worker process, so after every update, the agent worker records as in force, with its exact hash:
- every execution definition the code ships for real use (the seeded rows, `AGENT_POLICY_V1` and its protocol), when it is stored with the code's hash (`owner_approvals`, kind `DEFINITION`); a `FIXTURE_ONLY` definition never;
- the research envelope this code runs and every code-owned source version the registry finds valid (`agent_approvals`).

Each record is one `APPROVE` row with actor `SYSTEM`, no owner session and an idempotency key derived from its target, so a restart or a second worker writes nothing again. Migration `0011` admits such a row only from `asl_agent`, only for a stored target with that hash, and only as an approval; on `agent_approvals` every check of `0009`'s guard applies to it as to the owner's. A definition's record goes through `asl_m8_record_definition`, a function only `asl_agent` may call; the agent identity holds no privilege on `owner_approvals` itself. A target whose latest record is the owner's `REJECT` or `REVOKE` is left as the owner decided it: the worker checks under the owner route's lock (`4004001` for definitions, `4005002` for the rest), and `0011`'s guards refuse a `SYSTEM` approval after the owner's no as well. The checks that read approvals read these rows as they read the owner's, and every view carries who recorded the state (`OWNER` or `SYSTEM`).

**The model table** (`app.agents.model_table`, `MODEL_TABLE_V1`, a code-owned definition hashed like a prompt). For each role it lists model and effort pairs in order of preference: the coordinator, analyst and researcher at `medium`, the evaluator at `high` (0030 §4.1), each on `gpt-6.1-sol`, then `gpt-6-sol`, then `gpt-5.6-sol`, and the evaluator last on `gpt-6.1-sol` at `medium`. A role takes the first pair whose model the discovery lists as `code_mode_only` with that effort; nobody chooses and nothing is read from a display name.

**The runtime profile** (version 4). The worker composes it from the table and the newest discovery, once per discovery, and stores it with source `SYSTEM`. It binds every agent definition hash, the table's among them, and names each role's model, effort and preference. With nothing unset it is recorded in force; a role the discovery cannot serve stays in `unset` (`MODEL_TABLE_UNRESOLVED:<role>`): that profile is still stored, so the runtime view (`GET /v1/agent-runtime`) lists it with what is unset, and nothing is recorded; Settings then shows that the switch waits for a profile. Each step runs on its role's pair. A version-3 profile, composed by the owner with one model for every role, stays readable and authorizes nothing. The owner's compose form, its route and the owner's profile approval are gone (`PROFILE_RECORDED_BY_THE_APP`, 409).

**The switch carries across a change of profile.** While the owner's latest switch request is on, a runtime in `LOGIN_REQUIRED`, `PROBE_ONLY` or `ENABLED` on another profile moves to `PROBE_ONLY` on the one in force (`PROFILE_IN_FORCE`, reason `CHECK_PENDING`), and the agents' check enables it when it passes. Nothing here turns the switch on, touches a `DISABLED` runtime or one the owner holds in `PROBE_ONLY`, or clears a latch. On the PC this moves the agents from the owner's version-3 profile to the app's at the update.

**Promotions.** A pending `PROMOTION_V2` whose candidate waits in `MAIN_APPROVAL_PENDING`, that names this build's policy and scope, and whose candidate's exit values lie in the policy's sets is approved by `SYSTEM` by its exact hash; the worker applies it as it applied the owner's (`decided_by` `SYSTEM`). A request outside the sets stays pending: a wider range reaches the main portfolio only in an update the owner installs.

**The agent's entry pause ends.** 24 hours after the engine opened it on a live run, the worker writes a `RESUME` with actor `SYSTEM`, and the engine closes the pause as it closes the owner's. The owner may still resume earlier.

**Latches the engine clears** (`app.execution.engine`):
- `DAILY_LOSS`: when the first reference of a later UTC day is taken on a valid valuation, the engine closes the run's cause (`CAUSE_CLOSED`, actor `SYSTEM`, rule `NEXT_UTC_DAY`) and resolves each such latch citing that close. A latch of the same day waits.
- `INTEGRITY`: a reconciliation that passes, with no mismatched order, clears the account's two flags together (migration `0011` admits no other clearing, and only `asl_execution` writes them), closes the live run's cause (rule `RECONCILIATION_PASSED`) and records an `INTEGRITY_CLEARED` incident and outbox event. It does so only when every check that failed since the last clear (the `RECONCILIATION_FAILED` outbox events) is one a passing run proves repaired. A latch a NAV check opened (`nav_cash_only`, `nav_persisted_valuation`) stays, since those checks read only the newest valuation and a wrong one may already have moved the high-water NAV or the day's reference; the reconciliation returns `integrity_kept`, and the fix comes in an update. A failing reconciliation clears nothing.
- A MAIN run left `PAUSED` with no cause open, no blocking request and neither account flag set, read in that step, resumes (`RESUMED`, rule `NO_CAUSE_OPEN`).

`OWNER` stays the owner's; `DRAWDOWN` still ends the run.

## M8 runtime: the main run the app keeps going (ExecPlan 0031)

Update 3 of [ExecPlan 0031](plans/0031-m8-simple-app-that-runs-itself.md#9-implementation-sequence) (§4.6), with [`AGENT_POLICY_V2`](contracts/STRATEGIES.md#agent_policy_v2-hourly-entry-checks-m8-update-3-proposed) as its first version change. IMPLEMENTED and tested offline on scratch PostgreSQL 16 with scripted providers and the M3 engine on a simulated clock (results in [COMMANDS](COMMANDS.md#m8-update-3-the-run-the-app-keeps-going--2026-10-19)); on the owner's PC from its third update on. Migration `0012` is additive.

**What it is.** §4.6's fallback, not a policy switch inside one run: the engine binds a run's policy through its manifest, whose hash the run's evidence and reports cite, so the app ends a run whose policy a newer version replaced, without flattening it, and starts the next run itself. The runs follow each other with no owner step; each run is one segment of the main account's history, under one policy version.

**The run keeper** (`app.experiments.runs`, actor `SYSTEM`). The main account's execution worker calls it every 5 seconds between steps, in a short transaction of its own that takes the owner approval route's lock (`4004001`) and then the mode's newest experiment row, in the order that route takes them. It writes run records only; the engine applies the requests in its fenced step as it applies the owner's, and checks a start's rules again there. The conditions for asking a stop (below) are the keeper's own. Each record has a key derived from its run and purpose, so a repeat writes nothing; a failure is logged and tried again and never stops a step. The policy in force is the newest of `MAIN_POLICIES` (`AGENT_POLICY_V1`, then `AGENT_POLICY_V2`) stored with this build's hash whose latest record is an approval, the owner's or the app's.
- **A newer policy in force.** A `RUNNING` or `PAUSED` run of an older main policy gets `STOP_REQUESTED` with `flatten` false and reason `POLICY_SUPERSEDED`, once the account holds no position, open order or exit obligation (`store.has_live_exposure`): a position stays with the policy and the agents that opened it until it closes under its own terms (R08). The engine then moves the run to `STOPPED` in the step that applies the stop. If an entry was accepted in between, the stop cancels it; if it filled, the run stays `STOPPING` until that position closes, with no new entry, the engine's stops and time exits working, and no agent decision for it (the agents decide only for a `RUNNING` run). The app does not ask while the owner's pause, the owner's revocation of an approval the run needs (`APPROVAL_REVOKED`), a drawdown latch or an integrity latch is open, or while another request waits. An owner's Stop sent while the app's stop waits is refused as already pending (`409`); the owner stops the next run instead.
- **The next run.** After a run that the app's stop ended (the stop took effect and no other came first) or that the app discarded, it creates a draft of the policy in force with the previous run's cost scenario (`CREATED`, actor `SYSTEM`, citing the previous run). Never after the owner's stop or discard, after any request the owner sent once the app's stop was written, after the owner rejected or revoked that run's manifest, after a drawdown stop (`DRAWDOWN_UNRECOVERABLE`), while a drawdown latch is unresolved, or before the account is initialized: those wait for the owner.
- **A draft of a main policy**, the app's or the owner's (in Settings' Trading run since ExecPlan 0035, on the Experiments page before; creating it asks for the run): once every definition it names is in force, the app records its manifest in force (`asl_m8_record_manifest`, never over the owner's latest `REJECT` or `REVOKE`) and moves it to `READY` (`MARKED_READY`).
- **A ready run of a main policy:** `START_REQUESTED` while its approvals are complete, the account is neither paused nor reconciliation-failed and no request waits. After a `START_REJECTED` the app asks again 15 minutes later, the wait doubling with each rejection up to 4 hours.
- **A draft or ready run that can no longer start**, because its manifest names other code than this worker's or a policy older than the one in force, is discarded (`DISCARDED` with reason `CODE_IDENTITY_CHANGED` or `POLICY_SUPERSEDED`) once no request of it waits, and the next run follows unless the owner had rejected or revoked its manifest.

A run of the reference (`TREND_REFERENCE_V1`) or of a strategy that is not a main policy is the owner's, as before: the keeper writes nothing for it.

**The engine applies the app's requests.** The step's pending requests and the worker's poll no longer filter by actor, so a `SYSTEM` start or stop is applied exactly as the owner's, by the same rules. A `READY` run of another policy than the engine's makes the step raise `store.Rebind`; the worker binds again and the new engine activates the run.

**Hourly decisions.** Under `AGENT_POLICY_V2` the agent worker writes a `BAR_CLOSE` trigger (event `BAR_CLOSE_EVERY_FINALIZED_HOUR`) at every finalized hourly bar of the universe, with or without a position or an entry. The policy's entries wait for the agents' check on the new policy, which starts by itself (`ENTRIES_WAIT`); until it passes, decisions run only while a position or an entry is open, as update 1 set.
