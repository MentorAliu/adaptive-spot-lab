## M3 paper execution operations

- **Owner installation after M3:** schema `0005_m3_paper_broker`; `execution-worker` built but not started; `asl_execution` NOLOGIN; main activation blocked; zero orders, fills, positions and latches. Starting the worker, enabling its identity, approving the risk policy, strategy or a cost scenario, and clearing latches are M4 owner actions, not deployment steps.
- **Recovery sequence (execution worker).** On (re)acquiring the lease the worker reconciles (v2), moves implicated open orders to `RECONCILIATION_REQUIRED` and releases their reservations, rebuilds in-memory state from the database (open orders, obligations, positions, level depletion and protection-gap state persisted in its checkpoint), runs a recovery step and resumes publication processing. Missed publications are scanned in sequence order with the current database time: a recorded stop crossing creates the exit obligation *now* (evidence records `fresh_at_detection: false`), fills use only fresh post-restart quotes, and lapsed entry signals become `MISSED`. A graceful stop cancels unfilled entries, keeps exit obligations and releases the lease. A deterministic step failure leaves no partial commit; the worker pauses until its own lease expires and then reacquires with a new epoch.
- **Stale data and outages** block new orders and fills; exits wait; each exposed symbol records a `PROTECTION_UNAVAILABLE` START/END interval. No liquidation price is invented. The hourly quote gap described in [MARKET_DATA](contracts/MARKET_DATA.md#m3-execution-use-of-sampled-quotes) is addressed by ExecPlan 0012, which the M3 release carries forward.
- **Replay** runs only in its own Compose project and PostgreSQL cluster via `tools/m3-replay.ps1` (or the acceptance `Replay` phase), from built-in synthetic scenarios or a market-tables-only data dump restored into the replay cluster. Reports under `.cache/replay/<id>/` and `.cache/m3/<id>/replay/` are labeled "MODELED REPLAY — NOT THE OWNER'S ACCOUNT" and name the cost scenario, clock and eligibility limits.
- **Backup/restore** now includes the M3 tables; acceptance verifies byte-identical execution fingerprints and reconciliation (as `asl_api`) after dump/restore.

## M4 pilot operations (ExecPlan 0015)

- **Experiment state.** `experiments` follow the run-state table above. Owner actions:
  - create a DRAFT, whose manifest the API composes from the hashed definitions, the chosen cost scenario, its code identity and an account snapshot;
  - approve the manifest, which moves the DRAFT to READY once every referenced definition is approved;
  - discard a DRAFT or READY experiment (to STOPPED);
  - the control requests below.

  Only one experiment per mode can be DRAFT, READY, RUNNING, PAUSED or STOPPING.
- **Controls are durable intents.** Start, pause, resume, flatten and stop are recorded as owner requests with an idempotency key and the experiment version the owner saw. The execution worker applies each exactly once inside its fenced step: pause, flatten and stop before fills; start and resume after the step's valuation. The API answers "accepted", and the UI shows the SYSTEM application or rejection when it happens. The API locks only the experiment row, so a request that waits on a slow step fails fast as retryable and is resolved by looking up its key.
- **Pause causes.** Latched causes are `OWNER`, `DAILY_LOSS`, `DRAWDOWN`, `INTEGRITY` and `APPROVAL_REVOKED`; transient blocks are shown but never latched ([RISK_POLICY](contracts/RISK_POLICY.md#m4-latch-resolution-owner-resume)). The first latched cause moves RUNNING to PAUSED; only an owner resume that closes the last cause moves it back (from M8's second update the `SYSTEM` also clears `DAILY_LOSS` at the next UTC day and `INTEGRITY` on a passing reconciliation, and a main run with no cause left resumes by itself: [RISK_POLICY](contracts/RISK_POLICY.md#m8-latch-clears-execplan-0031-update-2)). M7 adds no sixth cause: the agent's entry pause is a pause of its own beside these, which blocks only new discretionary entries of the agent-driven run and is closed only by the owner ([M7 below](#m7-agent-driven-decision-operations-approved-contract-execplan-0026)).
- **Flatten and stop.** Flatten is an owner pause plus one `OWNER_FLATTEN` exit obligation per open position, with precedence `PROTECTIVE_STOP > OWNER_FLATTEN > TIME_EXIT > TREND_EXIT`; without usable quotes it stays unresolved and records `PROTECTION_UNAVAILABLE`. Stop moves the run to STOPPING, cancels unfilled entries and optionally flattens; STOPPED follows when no position, open order or active obligation remains, and COMPLETED follows the final report. A drawdown latch on a flat account cannot recover, so the SYSTEM stops the run (`DRAWDOWN_UNRECOVERABLE`, OD-10).
- **Local downtime (OD-11).** After PC sleep, power loss or a Docker stop the workers restart (`restart: unless-stopped`; Docker documents that `on-failure` does not restart a container after a daemon restart), and the pilot continues once its checks pass. At lease acquisition, a gap longer than 10 s plus the lease period since the checkpoint's last step is recorded as an `EXECUTION_DOWNTIME` incident and experiment event. Nothing is backdated: missed signals are `MISSED`, and exposed hours without a valuation are report gaps.
- **Deployments during a pilot (OD-12).** Deploy outside HH:00–HH:03 UTC, with a graceful worker stop. A changed code identity appends `SEGMENT_STARTED` at the next lease acquisition; segments are never stitched. Since M5 the stricter rule of the M5 and M6 sections below holds until the experiment boundary: no deployment rebuilds, recreates, restarts or stops a pilot service.
- **Activation (M4-B, owner-instructed only).** `tools/pilot-activate.ps1 -ExperimentId <id>`:
  1. refuses HH:00–HH:03 UTC and runs the preflight;
  2. takes a protected backup;
  3. enables both identities with `app.execution.identity enable --main --experiment <id>` through the one-shot `pilot-admin` service (refused unless the experiment is READY or RUNNING with every approval active and reconciliation OK);
  4. sets `ASL_EXECUTION_ENABLED=1` and `ASL_EVALUATION_ENABLED=1` in the env file;
  5. starts both workers and verifies the lease and the awaiting-Start state.

  The owner then presses Start. `tools/pilot-deactivate.ps1 -ExperimentId <id>` reverses it after the run ends: it refuses HH:00–HH:03 UTC, refuses while the experiment is still DRAFT, READY, RUNNING, PAUSED or STOPPING, takes a protected backup, stops both workers gracefully, returns both identities to NOLOGIN and sets both env flags to `0`. Disabling the identities is refused while forward positions are live unless an owner instruction overrides it. Wait for COMPLETED before deactivating: the final report is written only once the execution checkpoint is 5 minutes past the stop (the hourly lateness bound), so both workers must keep running that long.
- **Rehearsal.** `tools/m4-acceptance.ps1 -Phase ActivationRehearsal` runs both tools against an isolated stack with a synthetic owner and experiment. It checks the refusals, the checksummed owner-only backup, both identities and env flags, the workers' hardening (read-only root, limits, `unless-stopped`, private network only, one secret each), the held lease and the READY state, then deactivation back to NOLOGIN.
- **The env file the tools write.** Both pilot tools and both agent tools (`tools/agent-activate.ps1`, `tools/agent-deactivate.ps1`) take `-EnvFile`; the default is the checkout's `.env`. They write their flags to the one resolved path that every Compose call of the same run names. A relative `-EnvFile` means the directory PowerShell stands in.
  - **Corrected on 2026-10-07.** Before, the write took a relative `-EnvFile` from the process directory, which in an interactive session is usually another directory. The flags in the file given then stayed as they were, and a file of that name in the process directory was created or rewritten. The default path was never affected; the M4-B activation used it. `tools/env-file-path-check.ps1` shows both behaviors without Docker ([COMMANDS](COMMANDS.md#owner-tools-write-the-resolved-env-file-2026-10-07)).
  - **A failed write stops the tool, however it is started.** Since 2026-10-07 `tools/lib/Pilot.psm1` stops on an error in its own functions, for every tool that uses it. Before, that held only for a tool started with `powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools\<tool>.ps1 ...`, which is how both owner activations were started and how the rehearsals start the tools. Called by its path from a PowerShell session, a tool printed the error at the flag step and went on: OBSERVED with a read-only temporary env file, both deactivation tools ended with exit code 0 while the flags still read `1`. The `-File` form remains the one the rehearsals cover.
  - **Known limits of the writer and reader, unchanged by the correction** (`Set-EnvFlag` and `Get-EnvValue` in `tools/lib/Pilot.psm1`; OBSERVED on temporary files and with Docker Compose v5.5.1 on 2026-10-07). Keep each flag as one plain `KEY=value` line. Compose reads the last assignment of a key and also takes `KEY: value` and `export KEY=value`; the writer rewrites `KEY=` lines only, so a later line in another form keeps its old value, and that is the value Compose reads. The writer rewrites the whole file with CRLF line ends and without a byte-order mark, drops a comment after a flag's value and does not replace the file in one step. The reader, which gives a backup its database name, returns the first assignment of a key, with its quotes and comment. By the owner's decision their replacement follows the merge of the M6 B9 pull request, on that branch's reader and writer ([decision](../DECISIONS.md#2026-10-07--pilot-and-agent-tools-the-env-file-path-and-what-was-left-out)).
- **Reproducibility (OD-14).** Unpinned quotes are deleted after seven days. `tools/pilot-market-dump.ps1` takes a protected, checksummed data-only dump of the market tables. The owner's decision is weekly dumps, sized after measuring disk; otherwise the experiment is reported as not fully replayable beyond seven days.

## M5 agent runtime operations (ExecPlan 0020)

**Coexistence with the running pilot** ([ExecPlan 0020 §12](plans/0020-m5-agent-runtime.md#12-coexistence-with-the-running-m4-pilot)).
- **What M5 never touches.** M5 never rebuilds, recreates, restarts or reconfigures `postgres`, `market-worker`, `execution-worker`, `evaluation-worker` or `pilot-admin`. It writes no row into, and alters no table, constraint or ACL of, the M1–M4 schema, so it adds no evaluation segment.
- **Identity split.** After M5, `api`, `migrate` and `web` run M5 code while the pilot's workers run their own release. A new experiment drafted by the M5 API would be refused Start by those workers. That cannot happen during the pilot, because only one experiment per mode can be active. The workers are rebuilt at the next experiment boundary. This is a recorded exception to "verify running images" (step 4 of the deployment procedure above).
- **Deploy window.** The M5 deployment runs only between HH:15 and HH:45 UTC, never between HH:00 and HH:13 or 23:50 and 00:20. It names services explicitly with `--no-deps`, never selects the `market`, `execution` or `admin` profiles, neutralizes `COMPOSE_PROFILES`, tags the pilot images and verifies before and after that they are unchanged.
- **Expand, then migrate.** Web is deployed first; it accepts both `SystemStatus` shapes. Then the API: readiness accepts 0006 and 0007, and agent features report "schema pending". Then migration 0007 runs with a 200 ms lock timeout and bounded retries. No worker stop is needed.
- **Rollback.** The guarded downgrade drops only agent objects and refuses if any non-fixture agent row exists. It is rehearsed on a restored owner backup and is valid only before M5-B. Never restore a backup over the running pilot without an explicit owner decision.

**Runtime load.** One codex process at a time; the HH:59:30–HH:06:00 UTC quiet window; role-level timeouts for `asl_agent`; views over existing indexes only; storage caps and retention.

**Agent runbook** (every step is owner-gated or owner-performed; none exposes a credential):
- **Disable.** The UI's Disable is immediate: the epoch increases, in-flight work becomes `CAPABILITY_REVOKED` or `late`, and protection and every non-model function continue. `tools/agent-deactivate.ps1` additionally stops the agent services, returns `asl_agent` to NOLOGIN and sets `ASL_AGENTS_ENABLED=0`. It keeps `codex_home` unless the owner asks for credential destruction. Which env file it and `tools/agent-activate.ps1` write, how to start them and the writer's limits are described under [the env file the tools write](#m4-pilot-operations-execplan-0015).
- **Revoke a profile.** A REVOKE of its exact hash in the UI returns the runtime to `PROBE_ONLY`, or keeps it `DISABLED`.
- **Unknown outcome.** Resolve by the idempotency key (owner requests) or the call key (provider calls). The worker queries the runner for the same call key, then records `OUTCOME_UNKNOWN`; it never sends a blind repeat.
- **Re-login.** The owner runs `tools/agent-login.ps1`, which stops the runner, runs the device-code login in `agent-auth` through the gateway, and restarts the runner. A stale copy-back is refused by compare-and-swap.
- **Destroy credentials.** Owner request only: stop the agent services and remove the `codex_home` volume. Then review the active sessions in the ChatGPT account.
- **Quota recovery.** `QUOTA_BLOCKED` blocks only new model work and clears only on an actual successful call; reset times are shown only if a verified interface reports them. Since M8 the agents' check retries by itself (10 minutes, doubling up to 2 hours) and nothing latches ([RUNTIME_AGENTS](RUNTIME_AGENTS.md#m8-runtime-the-agents-check-the-usage-limit-and-one-switch-execplan-0031)).
- **Capability violation.** Latch `CAPABILITY_LATCHED`, keep the runtime off, withhold the auth copy-back, re-login, and review the active ChatGPT sessions. A fix happens in the runner only (no pilot effect) and needs a new probe run. Since M8 a violation fails its own workflow, latches nothing and returns `ENABLED` to `PROBE_ONLY`; the auth copy-back is still withheld after it, and the agents' check must pass before entries reopen.

**As implemented in B4 (isolated fixture evidence only; nothing is deployed or started).**
- The bridge passes every 5 seconds: relay first, then staging, then store maintenance. A stage that fails is reported in the heartbeat and never stops the stages after it. The daily work (sealing a dataset, starting eligible shadows, advancing shadows) is looked at every 5 minutes, every 30 seconds while an advance waits for an idle runner, and repeats nothing within its UTC day. An owner stop is applied on the next pass.
- A shadow advance is recorded only when no other job is queued or running, because a job's hour runs from the moment it is recorded. Advances therefore run one after another. An advance that was canceled or expired without running is recorded again the same day.
- A staging pass copies at most 20 batches. It records `REFUSED` once per store, reason and hour when a store is at its cap, the runner has published no free-space reading in the last 10 minutes, the research data filesystem has less than 40 GiB free, the two schemas differ, a copy cannot be proven equal, or the store no longer holds what the catalog says was staged into it.
- At a store's 49-day cap, a shadow whose whole window is already staged still gets its last advance; a shadow whose window is not ends `INCOMPLETE`. At the 20 GiB cap the runner refuses every job on that store, so its shadows end.
- A store creation that fails leaves no database behind and is not requested again for an hour.
- **A research cluster that was lost and initialized again** is recognized (`STORE_LOST`) and refused; its shadows end `INCOMPLETE`. B4 only fails closed; the owner step that brings a new store version into service is in the B9 block below.
- A new store version is requested at 28 days or 12,271,335,131 bytes; the runner creates it. The old version is fed only while a running shadow is bound to it and is dropped when nothing uses it.
- A dispatched job with no result five minutes after its deadline is recorded `EXPIRED`. A result that arrives later is stored as history.
- A bridge outage loses nothing while it is shorter than main's 7-day quote retention. After a longer one the unstaged rows are gone from main: the gap is recorded as `RETENTION_LOSS` and the shadows it touches end `INCOMPLETE`. A store older than that can be rebuilt only from the weekly dumps, as an owner step that no tool automates yet.
- The commands that enable the research identities and start the research services were built in B9: see the next block.

**As implemented in B9 (IMPLEMENTED; rehearsed on isolated stacks only, see [ExecPlan 0023 §18](plans/0023-m6-research-investigations.md#18-completion-evidence); none of it has addressed the normal app before B10).**
- **Inert deployment (M6-A, B10, owner-approved in chat).** `tools/m6-deploy.ps1 -BaselineComposeFile <the compose file the pilot's newest container was created from>`. Only its env file decides: it clears every `ASL_`, `COMPOSE_` and `WEB_PORT` variable of the calling shell. The rehearsal starts the M6 owner scripts with `powershell.exe -NoProfile -ExecutionPolicy Bypass -File`, and that is the form to use. Started from a session (`.\tools\m6-deploy.ps1`), a library function does not see the script's `Stop` preference (OBSERVED in Windows PowerShell 5.1 on scratch files). Both libraries of these scripts therefore set `Stop` themselves: `tools/lib/Research.psm1` from this batch, and `tools/lib/Pilot.psm1` since pull request #30 of 2026-10-07, so that a failure inside a library function stops the script in either form. Its steps:
  1. begins only between HH:15 and HH:35 UTC and never between 23:50 and 00:20, so that its backup, its restore rehearsal and its builds are over while the window is open; the window itself (HH:15–HH:45) is asked again before the builds and before the first change. It refuses a product tree that holds an uncommitted change (it records the commit it deploys). A `git` that cannot answer, or that names no commit, is an error and never a clean tree. Refused before any Docker call: a deployment without `-BaselineComposeFile`, `-Rehearsal` for a project whose name does not begin with `asl-m6-` or `asl-model-`, and a `-PilotTag` that a release uses (`latest`, `pre-m6`);
  2. reads the starting state and requires schema `0007_m5_agent_runtime`, running `postgres`, `api` and `web` containers, and each pilot service named by `-ExpectedPilotImages` running on that image (the default names the market, execution and evaluation workers of the running pilot by image ID). When the execution worker runs, the execution lease must be held. A listing that fails is an error, never "no container". A release with a service down is refused: an agent worker that exists and does not run, or an `api` or `web` that does not run, is started, or returned to with `-Rollback`, first. The env file is read as Compose reads it (quotes, a comment after a space, `KEY: value`). Refused, because the script would otherwise decide on a value Compose does not use: a key that is assigned twice, interpolation and escapes, text after a quoted value on the same line, a quoted value that runs over more than one line, a carriage return inside a line, a file that is not UTF-8, and a key written in another letter case. The last matters most: Compose on Windows reads `asl_research_enabled=1` as the flag when the exact spelling is absent (OBSERVED with Docker Compose 5.5.1 on this host, by rendering scratch files), so a reader that looks for the exact spelling alone would report such an installation as inert;
  3. tags the pilot's worker images, and creates the `:pre-m6` rollback tags for `api`, `web` and `agent-worker` from what runs now, and for the names `migrate` and `agent-admin`, which have no service container, from what each name points to now. A tag that exists is never moved. A tag is created only from an image that `-ExpectedPreM6Images` names for it, and an existing tag must point to the image named there: a deployment therefore passes the image IDs of all five names (the default holds the three services' images of 2026-10-06; the two other IDs are read in the read-only look before the deployment). A tag that cannot be read is an error and is never taken for a tag that does not exist. The image each pilot image name points to (`market-worker`, `execution-worker`, `evaluation-worker`, `pilot-admin`) is read here and compared after the builds and at the end: no deployment builds or moves one;
  4. requires the pilot's services, the private network and the `postgres_data` volume to render the same from both compose files, and requires the installation to be inert already. It also reports, without judging it, whether each pilot container was created from the configuration this compose file renders now: where it was not, a plain `docker compose up` that names that service would recreate it, which this script never does;
  5. checks that the Docker VM has room for the backup and its restored copy, takes a protected backup, builds the `migrate` image (once: the image that migrates the restored copy is, by its ID, the one that migrates the installation in step 8), restores the backup into a helper PostgreSQL on an internal-only network (1 CPU and 1 GiB; container, network and named volume removed by name afterwards; anything that is still there is named, and a listing that fails is recorded as `NOT READ`, never as nothing left), applies 0008 there, compares the M1–M4 tables before and after, reconciles as `asl_api`, downgrades and compares again. The comparison is, per table, the row count and the sum of a 64-bit hash of every row, read in one pass; it compares the restored copy with itself and is not a cryptographic digest. Every read is checked: a query that fails stops the run, and its message can never stand in for a fingerprint. **If the migration fails on the restored copy the deployment stops here, with nothing replaced**;
  6. asks the window rule again, then builds, by name, `api`, `web`, `agent-worker`, `agent-admin`, `source-fetcher`, `research-runner`, `research-migrate`, `research-bridge` and `research-admin`, and checks that no pilot image name moved and that the `migrate` name still points to the image of step 5. `migrate` is not built a second time: on this host every build of the same tree gives another image (OBSERVED on run `m6-b9i`);
  7. asks the window rule again, then recreates `web`, then `api`, with `--no-deps`;
  8. applies migration 0008 with its 200 ms lock timeout, in at most five runs with growing pauses, and stops before the agent worker if it does not apply;
  9. recreates `agent-worker` only if it was running;
  10. checks that no research or source service runs and none gained a container, that `asl_research` and `asl_source` exist without login and that neither flag is `1`;
  11. checks that every pilot container, its image, start time, restart count and state, the lease epoch, that the lease is still held, the open experiment's state and version, and the counts of segments and downtime events are what they were; that no execution incident was recorded during the run other than `PROTECTION_UNAVAILABLE`, which the pilot writes on its own and which is printed and recorded by its code and count and stops nothing (owner decision of 2026-10-07, [DECISIONS](../DECISIONS.md#2026-10-07--m6-b9-what-stops-a-test-run-beside-the-pilot-the-owner-scripts-and-the-pilots-own-rows-the-schema-change-in-0008-and-the-market-workers-log); any other code that gained, a new code, a count that fell and a total no code accounts for stop the run here); that the rollback tags and the pilot's image names did not move; and writes `m6-deploy.json` beside the backup. The market worker's incidents recorded during the run and the age of its newest publication are printed and recorded, and not judged: the script changes nothing of the market worker, and the worker records incidents of its own. Its codes are counted without regard to letter case: the normal database holds one code in two spellings (`clock_uncertain`, `CLOCK_UNCERTAIN`), which stopped the first deployment in its preflight on 2026-10-08 before any change ([DECISIONS](../DECISIONS.md#2026-10-08--m6-b10-a-deployment-that-stopped-in-its-read-only-preflight-and-the-fix-of-the-deploy-script)).

  It never builds, recreates, restarts or stops `postgres`, `market-worker`, `execution-worker`, `evaluation-worker` or `pilot-admin`, creates no secret, enables no identity and sets no flag. The agent runner and the egress gateway are not rebuilt.
- **When the deployment stops.** Any failed check stops it where it is. It then prints `STOPPED at stage '<stage>'`, the backup path, the schema, what each of `api`, `web` and `agent-worker` runs now (the tags are read at that moment), how to return, and the pilot: either that its containers, lease, open experiment and incident counts are as at the start of the run, or what differs (`pilot_at_the_stop` in the record). It writes `m6-deploy-failed.json`. A run that stops on an installation at 0008 says that the M6 release is deployed and does not advise a rollback that nothing calls for. Before step 7 no running service was replaced; a run that stops there after it built an image returns every image name it moved (`migrate`, `api`, `web`, `agent-worker`, `agent-admin`) to its `:pre-m6` image and says so, so that no later `docker compose up` starts an M6 image by its name on schema 0007. A service is counted as replaced from the moment its recreation is asked for, also when that recreation fails. From step 7 on, `-Rollback` returns to the pre-M6 release. While the schema is still 0007 and `api` and `web` run, the deployment can instead be run again: it continues, and the `:pre-m6` tags stay where they are.
