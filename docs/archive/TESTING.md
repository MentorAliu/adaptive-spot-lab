> Archived 2026-10-20 by [ExecPlan 0034](plans/0034-app-cleanup.md): the status prose and the milestone evidence maps of `docs/TESTING.md` as they stood, verbatim. The current rules and the requirement-to-test map are in [TESTING](../TESTING.md).

## Status and rule

The original Markdown pack contained no application tests. M0/M1 and the in-progress M2 implementation now have separately recorded local evidence in [COMMANDS.md](COMMANDS.md) and their ExecPlans. Distinguish unit/integration/browser tests, provider connectivity checks, synthetic workload probes, simulation evaluation and packaging checks in every report. A mocked API test cannot establish actual integration or trading profitability.

M2 uses deterministic unit/property tests for exact decimal, UTC, schema and finality rules; real disposable PostgreSQL for least-privilege grants, fencing, two-phase publication, watermark, retention and migration/restore; an isolated synthetic feed for browser state changes; and separate explicitly invoked public read-only checks. Historical ingestion and database-recovery evidence is preserved in [ExecPlan 0003](plans/0003-market-data-charts.md). The completion record revalidates the affected behavior; older measurements are not automatically passes for the new pipeline.

Completion worker faults use a real loopback WebSocket and PostgreSQL through the production reader/parser/queue/store path. Rotation alone uses an injected monotonic clock; queue age, shutdown bounds, memory and workload latency use real elapsed time. Tests exercise close, silence, provider shutdown, 23-hour rotation, failed replacement/restart, rate-limit cooldown, malformed/oversized frames, generation fencing, byte saturation, delayed writes and real database lock timeouts. A foreign-key row lock commits BTC's subgroup before SOL fails, proving that pending capture is reported as an unknown commit outcome rather than invented loss. Independent heartbeat/authority locking, conflict confirmation visibility and cross-page coverage have real-database assertions. The memory fixture settles five warm-ups and 30 measured recoveries without retained tasks/queues. Backup/restore seeds nonempty generations, instrument provenance, telemetry and an independently confirmed candle revision.

The [ExecPlan 0012](plans/0012-market-stream-continuity.md) stream-continuity suite (`tests/test_m2_stream_continuity.py`) runs the same real path with synthetic instruments whose `MARKET_LOT_SIZE.maxQty` drifts. It sends synthetic tickers to each connection's subscribed symbols, and a loopback relay can freeze one connection so it never answers a close or ends TCP. A sampler reads the owner-facing quote and health path every 50 ms.

Sampled VALID continuity is asserted for:
- hourly drift (no new generation or socket)
- scheduled and provider-requested rotations against a provider that never finishes closing
- routine reference refreshes

Other assertions:
- Frames keep the snapshot bound at receipt across an adoption.
- A transient instrument failure fails that feed closed without rotation.
- A non-trading status rotates to the remaining subscription.
- An hourly 720-row backfill under 50 frames/s keeps queue age below one second.
- A silent replacement keeps the current generation and retries.
- A partial replacement fails with its phase recorded.
- An overload during a slow close is recorded as overload, not a timeout.
- An overrunning close still counts toward the two-socket limit.
- Five back-to-back rotations keep the fence.
- A healthy collection resets retry backoff.
- The rotation-age override is refused outside a disposable database.
- Store-level tests cover publication-atomic activation ordering and fail-closed status.

Storage acceptance loads 1,209,600 quotes and 604,800 candle updates (336 finalized bars) via guarded synthetic COPY, then calls the production bounded retention function and measures queries, table/index/WAL growth, pins and references. A separate disposable volume crosses the actual 4/5 GiB thresholds. Neither fixture measures real-time ingestion. The distinct 60-minute normal/five-minute burst uses real loopback WebSockets under production worker resource limits. Explicit browser phases have no allowed required-test skips. `BrowserEmpty` owns a separate fresh run's browser database; it must not precede the normal `Browser` bootstrap/funding journey on that same database. Browser sign-in phases run sequentially because login revokes earlier owner sessions. Manual speech review uses the [Narrator checklist](m2-narrator-review.md).

Neither of those fixtures measures publication against stored history: the 60-minute workload starts on an empty database, and the storage fixture times only candle reads. [ExecPlan 0021](plans/0021-publication-cost-at-density.md) adds that measurement:

- **`PerformanceDensity`** (`app/market_data/performance_density.py`, its own `density` database). A guarded synthetic COPY loads already-published observations in production record shapes, in stages up to 1,800,000 (about seven days of the declared density). The stored timeline starts an hour before the seven-day retention window. At each stage the real worker runs its own loop for a real elapsed window: lease, generation start, reference refresh, 720-row backfill, loopback stream, 45-second maintenance and its own failure recovery. The synthetic frames arrive at four phases inside each second, so the writer publishes several small batches a second, and each REST answer takes an assumed 150 ms.
- **Retention under the stream.** The start-up retention is skipped at every stage. At the last stage the retention becomes due two minutes after the first usable sample, as the hourly retention of a long-lived worker does, and must delete at least 10,000 observations inside the same budgets.
- **Budgets at every stage.** Receipt-to-publication p95 ≤ 250 ms and p99 ≤ 1 s; every sent frame published; no `COLLECTION_GAP` or `QUEUE_OVERLOAD`; no unusable once-per-second health sample after the first usable one; no worker stop. The identity publication statement reads no table sequentially and costs ≤ 50 ms at p95; the recovery scan stays within a quarter of its 20-second deadline.
- **Record-only mode.** `-Observe` records every stage without enforcing the budgets. It reproduced the defect on the unfixed worker.
- **`tests/test_m2_publication_density.py`** (in `WorkerFaults`) covers the rules themselves: identity publication publishes exactly the given revisions in receipt order and is idempotent; a fenced-out owner publishes nothing; its plan reads only the given identities with 20,000 stored rows; a generation start publishes an earlier process's leftovers under its own fence; stream publication never falls back to the scan; revisions stranded by an unknown persistence outcome or a failed publication are recovered by the next generation; the recovery deadline is local to its transaction; and eight slow deleting retention calls under 50 frames a second run on their own thread without delaying the writer.

This is synthetic latency evidence on the owner's host under the production container limits. It is not public-feed evidence.

[ExecPlan 0022](plans/0022-reference-checks-and-rest-budget.md) adds the routine reference checks:

- **`tests/test_m2_reference_checks.py`** (in `WorkerFaults`) runs the real worker, loopback sockets and PostgreSQL with scripted clock readings, and samples the owner-facing quote path every 50 ms. It covers:
  - an imprecise check, a failed clock request of four kinds, and a failed request between two measurements: each keeps the collection and fails closed until the clock is verified;
  - an out-of-bounds offset, and a frame from the future while unverified: each closes the collection;
  - nothing re-opening a feed while unverified, with a history request due and a changed snapshot waiting for adoption;
  - a clock unverified for minutes on one collection, with one check per five seconds and no other request;
  - rotation waiting for a verified clock, whether the failure is met in its own revalidation or before it;
  - every answer to a conflict-confirmation request, and a failed history request beside a failed instrument check;
  - the record of each unverified interval, also when a stop or a teardown ends it.
- **The same file runs the real transport class and its weight budget over an HTTPX mock transport,** with the loopback stream. A 429 inside a running refresh holds the next request for `Retry-After`. Long waits on the IP guard are logged, and recorded once in ten minutes. A stop ends a wait during collection and at start-up.
- **`tests/test_m2_unit.py`** covers the budget with a controlled clock: the own ceiling, the guard from the declared allowance, the fallback before one is read, and the header values of 2026-10-02. It also covers the declared-allowance reader, the back-off block and the clock measure: the locked HTTPX and httpcore emit the trace events the measure uses, and budget wait, DNS and connection set-up lie outside the measured interval.
- **`PerformanceDensity -ReferenceFaults`** injects four imprecise clock checks under the stream at each level. Unusable samples are allowed only between a fault and its reopening. Each fault must close usability within 2.5 s and reopen it within 15 s on the same collection, as the once-per-second sample sees it, and the other budgets hold. REST answers take 150 ms there, so the bound is wider than the worker tests' 12 s with instant answers.

These are loopback and mock-transport tests. They do not contact the provider.

[ExecPlan 0024](plans/0024-retention-failure-keeps-the-worker.md) adds the retention call the database ends:

- **`tests/test_m2_retention_faults.py`** (in `WorkerFaults`) runs the real worker, loopback sockets and PostgreSQL with expired fixture quotes, and samples the owner-facing quote path every 50 ms.
  - A row lock holds the function's payload delete until a statement deadline ends the call (`57014`, the statement and function line of the two exits of 2026-10-06). The same lock on an observation ends the call by the worker's own one-second lock deadline (`55P03`). In both cases the collection, its epoch and its socket stay, every sample is usable, the failed call's deletes are rolled back, the retry completes the pass, and the two records are written through retention's own database thread.
  - A failed call in the start-up pass of `MarketWorker.run()` lets the stream open.
  - A rotation asked for while a retention call still runs waits for that call before it registers its generation, and completes without a gap.
  - A lease that has ended is raised from the retention path and is not counted as a failed attempt. The function's own lease refusal is a lost lease.
- **`tests/test_m2_unit.py`** covers the schedule without a database, on a clock the test moves: the wait after each failed attempt (60 s doubling to an hour), the `RETENTION_STALLED` code from three hours on, the closing record, at most 32 calls in any hour with a retry using what is left, a wait that does not grow while attempts complete calls, a cancelled attempt's call that is still counted and that a new generation waits for, four database error classes, a lost lease and a non-database error raised as before, a stopping worker, and a record that cannot be written.
- **`PerformanceDensity -RetentionFaults`** lets the database end the first call of each of the first two retention attempts by a statement deadline, under the stream at the last density level. A later attempt must delete at least 10,000 observations, on one collection, inside every other budget.

The two deadline cases, the start-up case and the rotation case failed on the unchanged worker: the collection or the process ended with the database's error.

Use isolated test databases/volumes and deterministic labeled fixtures. Remove a finished run's Docker resources once its evidence is recorded ([DOCKER](../DOCKER.md#cleaning-up-disposable-resources)). Production/forward ledger history must not be reset by test setup. Ordinary tests do not contact paid models or private exchange endpoints. Public connectivity checks are explicit, bounded and separate from offline tests.

## Continuous integration

The repository has no hosted CI. The owner had it removed on 2026-10-17 ([DECISIONS](../DECISIONS.md#2026-10-17--github-ci-removed-from-the-repository)): the GitHub Actions workflow of [ExecPlan 0016](plans/0016-ci-checks.md) never ran on GitHub, and its files were deleted. ExecPlan 0016 keeps the design and names the commit to restore it from.

Until CI is added back, the checks run where the code is changed, and a pull request's body records which ran, with their results, and which did not:
- **A cloud session** (no Docker) runs the web lint, typecheck, unit tests and production build, Ruff, the OpenAPI drift check and the database-free pytest.
- **The owner's PC** runs everything that needs Docker: the full PostgreSQL pytest suite, the browser suites and the acceptance harness, whose `Checks` and `Regression` phases run the same containerized commands the removed workflow used.

A check that did not run, or was skipped, is NOT RUN, never a pass. Wherever a contract asks for executed CI checks, the same checks executed by the local harness against the exact release source stand in until CI exists again.
